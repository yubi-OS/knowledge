# 06 - Build substrate and supply chain (ADR-014, ADR-015, ADR-022, ADR-026, ADR-030)

Scope: rootless Docker Buildx as the sole build runtime, digest pinned fedora-bootc base images governed by PINNED.md, the unified per-artifact tag family on 0mniteck/yubios, the TEST-only dev tag guardrails, and ADR-030's indivisible policy gated reproducible workflow pattern.

## One runtime, one audit target (ADR-014)

The source doc (yubi-OS/yubiOS docs/ADR.md, ADR-014, status Accepted) records that the build pipeline needs a rootless container build tool and that Podman and Docker Buildx can both do the job, but the project already depends on Docker Buildx for Build Policies enforcement (`docker buildx bake --file yubiOS-bake.hcl ...`) per the OPA/Rego supply chain strategy. Carrying two runtimes adds redundant tooling and an extra surface in the trust chain. The decision: rootless Docker Buildx as the sole container build runtime, Podman removed from the build dependency chain. The recorded rationale: one dependency means a single audit target because every tool that processes the image before signing is an attack surface; Build Policies with `--policy` are a Buildx/BuildKit feature with no Podman Buildah equivalent; Buildx generates SLSA provenance and SBOM in one flag via `--attest type=provenance,mode=max` and `--attest type=sbom`; and the runtime install path is already Docker CLI and bootc oriented. The accepted trade-off is that Docker requires a daemon or Docker in Docker in CI. Migration: replace `podman build` with `docker buildx bake` targets and `podman run` with `docker run`; the Containerfile syntax is identical. (source doc; cited at https://docs.docker.com/build/policies/intro/ and https://docs.docker.com/build/attestations/)

Docker's own rootless mode documentation corroborates the rootless daemon model where both the daemon and containers run unprivileged, distinct from userns-remap where the daemon keeps root privileges (https://docs.docker.com/engine/security/rootless/, weight 0.54, authoritative). The policies documentation describes how `docker buildx build` resolves all build inputs and matches a policy file to the Dockerfile name (https://docs.docker.com/build/policies/, weight 0.18, weak but primary vendor documentation), and the attestations documentation describes `--provenance` and `--sbom` options (https://docs.docker.com/build/metadata/attestations/, weight 0.21, weak).

## Digest pinned base image (ADR-015)

ADR-015 (source doc, status Accepted) fixes a historical bug: the Containerfile previously used `quay.io/fedora/fedora-bootc:latest`, a mutable tag that silently pulls different content on each build. The decision is to pin the base image by digest, with PINNED.md as the live source of truth for the current digest. Rationale: a SHA256 digest is content addressed and immutable; this brings the Containerfile into compliance with yubiOS.rego; the selected base must satisfy the systemd feature floors required by current docs; and fedora-bootc is purpose built for bootc deployments. Digest update policy: bumps go through tooling or a reviewed manual change when a new Fedora 45 point release publishes, and before bumping the new digest must be verified against required floors including the systemd target, pam-u2f 1.3.1 or later, OpenSSL 3.5 or later, and relevant Go TLS support. Two amendments (2026-07-07 and 2026-07-11, source doc) strengthen this: digests quoted in ADR text are historical, never current pins, and future docs cite PINNED.md rather than embedding digest examples.

## Unified OCI distribution and the dev tag (ADR-022, ADR-026)

ADR-022 (source doc, status Accepted, both firmware and installer tags implemented) makes `0mniteck/yubios` the single distribution surface with one tag family per artifact class: `latest` and `<sha>` for the bootc OS image, `firmware` and `firmware-<sha>` for the ARM64 firmware bundle (live for the CI/QEMU class, with real hardware still needing Path A proof), `installer` and `installer-<sha>` for the mkosi disk image plus UKI, and `dev` and `dev-<sha>` for the TEST-only swu2f enabled image via ADR-026. The recorded caveat: production and TEST-only tags must never be interchangeable, and dev image contents are not allowed in `latest`. (source doc)

ADR-026 (source doc, status Accepted) publishes the TEST-only `dev` tag family layering the swu2f software FIDO2 authenticator onto the same base OS for VM validation, with guardrails: `Containerfile.dev` is never referenced by the production build or push path, dev images carry explicit TEST-only labels, CI asserts `passless --version` before push, and production tags must not include swu2f tooling.

## The indivisible workflow pattern (ADR-030)

ADR-030 (source doc, dated 2026-07-21, status Accepted) standardizes publish capable workflow builds on 7 requirements treated as one indivisible pattern: run the job inside the digest pinned Docker Hardened Image (DHI) base from PINNED.md, where the outer container is privileged only because nested container and image build operations require it (the Docker in Docker boundary, not a claim that the whole stack is rootless); install checksum pinned Docker CLI, rootless extras, and Buildx binaries, create a dedicated unprivileged `docker-rootless` account, and run `dockerd-rootless.sh` on its user owned socket and data directory; create and explicitly select the user scoped Buildx builder named `hardened`, with no workflow relying on an ambient default builder and the BuildKit daemon image pinned independently from the Buildx client; invoke targets through yubiOS-bake.hcl rather than ad hoc buildx commands, with bake owning contexts, platforms, tag families, deterministic exporter settings, subject metadata, and policy attachment; keep yubiOS.rego default deny with `reset=true` and `strict=true`, rejecting unapproved registries and non canonical external image references; pin GitHub Actions to full commit SHAs, container bases to OCI digests, source checkouts to immutable commit refs, and downloads to a reviewed version plus checksum, failing rather than silently falling back to a moving tag, branch, unsigned download, faked firmware blob, or unverified alternate source; and build each supported architecture natively where a runner exists, publishing architecture qualified staging tags and merging the public multi architecture tag only after every leg succeeds. (source doc)

The doc's honesty is explicit: pinning and policy enforcement are necessary for reproducibility but not proof of it. A release may claim bit for bit reproducibility only after two isolated builds from the same declared inputs produce identical intended payload digests, with intentionally variable attestations compared separately and evidence retained. The gate is enforced on ARM64 for production and dev OCI subjects; firmware rebuilds StandaloneMM and every board on a second clean ARM64 lane; the installer's claim covers the canonical unsigned rootfs contents and metadata, initrd, and package manifest after removing the regenerable `ldconfig` auxiliary cache, with the random SoftHSM certificate, signed systemd-boot binary, signed UKI, ESP, Btrfs block serialization, and full disk wrapper recorded as separate envelopes; the QEMU TF-A `CREATE_KEYS=1` envelope and the RK3588 external TPL dependent final image remain outside the complete image claim. Enforcement rules: a new bake target is incomplete until it inherits `_policy` and `_reproducible`, declares its attestation boundary, and has a policy negative test; a source bump must update the pin and its verifier in the same change; rootless in privileged DHI reduces daemon and builder privileges but does not erase the privileged outer container risk. Docker's DHI provenance documentation corroborates the SLSA compliance framing for hardened images (https://docs.docker.com/dhi/explore/security-concepts/provenance/, weight 0.25, weak). (source doc)
