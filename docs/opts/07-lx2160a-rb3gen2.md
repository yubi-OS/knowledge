# 07 LX2160A-RDB (Priority 3) and RB3 Gen 2 (watch)

Scope: the NXP LX2160A-RDB as an architectural reference with split secure-boot and StandaloneMM configs, and the Qualcomm RB3 Gen 2 as a frontier watch item dependent on QTI signing.

Grounding spine: `yubi-OS/yubiOS docs/OPTS.md`, sections "Priority 3, NXP LX2160A-RDB" and "Watch, Qualcomm RB3 Gen 2 (QCS6490)".

## LX2160A-RDB: why it surfaced

The source doc records a strong owner-fuse story (source doc):

- TF-A's Layerscape TBBR guide explicitly requires owner-programmed OTPMK and SRKH fuses, distinguishes permissive development mode from fatal production mode, and documents TF-A BL2 authentication of BL31, BL32, and BL33.
- OP-TEE's Layerscape platform has a maintained LX2160A-RDB flavor.
- U-Boot's `lx2160ardb_tfa_stmm_defconfig` enables OP-TEE, eMMC RPMB, and `CONFIG_EFI_MM_COMM_TEE`; `lx2160ardb_tfa_defconfig` additionally enables the OP-TEE RPMB command; and `lx2160ardb_tfa_SECURE_BOOT_defconfig` enables NXP secure boot.

The hardware itself is a serious reference platform: the LX2160A is a 16-core Layerscape processor with 16 Arm Cortex-A72 cores, datapath acceleration, security offload, and traffic management [https://www.nxp.com/products/LX2160A] (w 0.71), and the LX2160A-RDB reference design board is NXP's evaluation platform for it, shipping with a Linux-kernel BSP [https://www.nxp.com/design/design-center/software/qoriq-developer-resources/layerscape-lx2160a-reference-desig] (w 0.85).

## LX2160A-RDB: what stays unproven

The source doc records the gaps (source doc):

- No single defconfig combines the Secure Boot and StandaloneMM paths; the secure-boot config drops the TEE/RPMB settings.
- No reviewed LX2160 config enables `CONFIG_TPM2_FTPM_TEE`.
- TF-A's Layerscape overview requires a DDR PHY binary for LX2160A.
- The board is a large, specialist networking reference platform, so it is a poor first user-facing device even if the firmware architecture is strong.

## RB3 Gen 2: why it surfaced

This is one of the newest meaningful additions across all three upstream projects (source doc):

- TF-A's RB3 Gen 2 port replaces the normal TZ payload with TF-A BL2 and packages BL31, OP-TEE BL32, and U-Boot BL33 in a FIP.
- OP-TEE's Qualcomm configuration defaults to Kodiak, and its Kodiak target enables QFPROM fuse provisioning in secure builds. The fuse-region table includes OEM secure boot, public-key hash, permissions, and anti-rollback regions.

The TF-A documentation confirms the unusual boot shape: TF-A BL2 replaces the TZ firmware binary and a FIP payload replaces the UEFI binary, and the bl2.elf generated for the build is required to be signed as a TZ image with QTI signing involved [https://tf-a.docs.trustedfirmware.org/en/latest/plat/qti/rb3gen2.html] (w 0.87) and [https://trustedfirmware-a.readthedocs.io/en/latest/plat/qti/rb3gen2.html] (w 0.82). The same docs note QTISELIB for Kodiak/SC7280 is required.

U-Boot's own documentation confirms the target: the RB3 Gen 2 is a development board based on the Qualcomm QCM6490 SoC, a derivative of SC7280, and U-Boot can replace Qualcomm's original EDK2 bootloader by flashing it to the uefi_a or uefi_b partition [https://docs.u-boot-project.org/en/v2026.07/board/qualcomm/rb3gen2.html] (w 0.78). Qualcomm sells the board as the Dragonwing RB3 Gen 2 Development Kit for edge AI prototyping [https://www.qualcomm.com/developer/hardware/rb3-gen-2-development-kit] (w 0.66).

## RB3 Gen 2: blocking gaps

The source doc records 4 gaps (source doc):

1. The TF-A port requires a binary `qtiseclib`, says the generated BL2 needs QTI signing involvement, and uses Qualcomm Sectools in secure mode; the exact OEM-versus-QTI authority for every early image must be resolved. The TF-A docs make the QTI signing requirement on bl2.elf explicit, corroborating this [https://tf-a.docs.trustedfirmware.org/en/latest/plat/qti/rb3gen2.html] (w 0.87).
2. The reviewed U-Boot config does not enable OP-TEE, EFI MM communication, eMMC/UFS RPMB, or fTPM.
3. The device uses UFS; no reviewed upstream configuration demonstrates the yubiOS OP-TEE/StandaloneMM secure-variable design on UFS RPMB.
4. The reviewed OP-TEE config defaults `CFG_INSECURE=y`; a production build and fuse flow must deliberately override it.

## Verdicts as recorded

- LX2160A-RDB: preserve as an architectural reference and possible lab target; do not prioritize it over i.MX8MM or an RK3588 alternate (source doc).
- RB3 Gen 2: watch upstream and use for architecture research only; it is not a purchase recommendation for the current Path A milestone (source doc). Re-evaluate when upstream demonstrates OP-TEE secure storage plus owner-controlled signing without ambiguous QTI authority (source doc).
