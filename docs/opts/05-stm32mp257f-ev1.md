# 05 STM32MP257F-EV1: the cleanest firmware shape, the largest U-Boot port

Scope: the STM32MP257F-EV1, whose TF-A BL2 + BL31, OP-TEE BL32, U-Boot BL33 chain best matches the desired firmware stage shape, and why its upstream U-Boot config still misses every yubiOS secure-state integration.

Grounding spine: `yubi-OS/yubiOS docs/OPTS.md`, section "Priority 2, STM32MP257F-EV1", plus the STM32MP257F-EV1 row of the comparison matrix.

## Why it surfaced

The source doc records the appeal (source doc):

- TF-A's STM32MP2 documentation describes a full TF-A BL2/BL31 FIP flow with OP-TEE BL32 and U-Boot BL33. The security-enabled `F` parts support secure boot and hardware cryptography.
- OP-TEE's STM32MP2 configuration contains `stm32mp257f-ev1` and `stm32mp257f-dk` flavors and is maintained upstream.
- The STM32MP257F-EV1 is active, and ST documents the ROM to TF-A to OP-TEE to U-Boot boot chain.

The comparison matrix row confirms the shape: early owner-verification is "ROM + TF-A BL2/BL31" on the secure `F` part, OP-TEE is a board flavor, but none of the three yubiOS secure-state selections (RPMB/EFI MM/fTPM) is present in the reviewed U-Boot config, the principal blocker being the "U-Boot TEE/RPMB/EFI MM/fTPM port and DDR PHY blob" (source doc).

Independent boot-chain documentation matches this shape. On the STM32MP25 family, the first-stage bootloader is TF-A BL2, the secure monitor is OP-TEE (the BL31 role in the TrustZone architecture, loaded by the FSBL), and the second-stage bootloader is U-Boot, packaged in a FIP [https://docs.digi.com/resources/documentation/digidocs/embedded/dey/4.0/ccmp25/yocto-boot-chain_t.html] (w 0.89). ST's wiki documents the FIP build flow where the OpenSTLinux boot flow requires BL32 (OP-TEE OS) and BL33 stages [https://wiki.st.com/stm32mpu/wiki/How_to_configure_TF-A_FIP] (w 0.82), and bootlin's training material describes the same: fsbl is TF-A BL2, ssbl is U-Boot, and the FIP is generated as part of the TF-A build, which requires U-Boot and OP-TEE built beforehand [https://bootlin.com/doc/training/embedded-linux/embedded-linux-stm32mp2-labs.pdf] (weak, w 0.58).

## What stays unproven

The source doc lists the gaps (source doc):

- `stm32mp25_defconfig` does not enable `CONFIG_SUPPORT_EMMC_RPMB`, `CONFIG_TEE`, `CONFIG_OPTEE`, `CONFIG_EFI_MM_COMM_TEE`, or `CONFIG_TPM2_FTPM_TEE`. That is the entire secure-state integration set, absent at once: this is the larger U-Boot port the verdict names.
- The selected board and storage population must be confirmed to expose eMMC RPMB, and U-Boot's STM32 SDMMC path must be confirmed to support it.
- TF-A requires an ST DDR PHY firmware binary; pin and threat-model it.
- Fuse provisioning, closed-state failure, anti-rollback, debug lockdown, and recovery all remain hardware exercises.

## The DDR PHY firmware dependency

The dig results show what that binary is and where it lives:

- ST's application note AN5723 explains that the DDR PHY is trained by an embedded processor in the DDRPHYC PUB loaded with a protocol-specific firmware, and that the STM32CubeMX DDR tool drives the setup [https://www.st.com/resource/en/application_note/an5723-guidelines-for-ddr-configuration-on-stm32mp2-mpus-stmicroelectronics.pdf] (w 0.92).
- ST ships that firmware as a separate repository, `stm32-ddr-phy-binary`, whose STM32MP2 directory carries firmware version A2022.11 [https://github.com/STMicroelectronics/stm32-ddr-phy-binary/] (w 0.67).
- The STM32DDRFW-UTIL tool repository provides a DDR interactive console used to develop and validate DDR configurations for STM32MP2 [https://github.com/STMicroelectronics/STM32DDRFW-UTIL] (w 0.77).
- ST's wiki documents the DDR configuration setup flow that produces the register content the firmware consumes [https://wiki.st.com/stm32mpu/wiki/How_to_setup_the_DDR_configuration] (w 0.79).

So the pin-and-threat-model item has a concrete address: a vendor-published binary blob, version-stamped (A2022.11), needed before the first owner-authenticated stage can even initialize memory. Under gate 3 of the candidate gates this is a vendor-signed or at least vendor-produced executable inside the trust boundary, requiring producer, license, digest, update channel, and signing-authority records (see 09-cross-cutting-conclusions.md).

## Platform context

The STM32MP25 is a heterogeneous part: an Arm Cortex-A35 dual core plus a Cortex-M33 coprocessor [https://wiki.st.com/stm32mpu/wiki/STM32MP25_microprocessor] (w 0.72), with ST's documentation hub for the STM32MP257 covering both [https://www.st.com/en/microcontrollers-microprocessors/stm32mp257/documentation.html] (w 0.92). The OpenSTLinux distribution (STM32MP2Distrib) ships the BSP, including the Linux kernel, U-Boot, TF-A, and OP-TEE, in source form [https://www.st.com/en/embedded-software/stm32mp2distrib.html] (w 0.82), so the source-built story for the 4 main stages is good even though the PHY firmware is binary.

## Verdict as recorded

Strongest alternative firmware architecture, but a larger U-Boot and secure-storage port than i.MX8MM (source doc). The source doc's recommended next work also routes this lane through CI before buying hardware, because STM32MP2 needs U-Boot secure-state configuration work (source doc).
