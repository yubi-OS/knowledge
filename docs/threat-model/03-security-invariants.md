# 03 Security Invariants

Scope: the 10 security invariants the source doc declares the center of the model, plus the evaluation rule attached to them. This is an internal-record subtopic: the invariants are stated verbatim-grade in the source doc, and no searXNG dig was run for it.

Grounding spine: yubi-OS/yubiOS docs/THREAT_MODEL.md (source doc), https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/THREAT_MODEL.md

## The evaluation rule

The source doc states that a vulnerability that violates an invariant should be evaluated at the boundary it defeats, not merely at the file where it appears (source doc). This is the rule that connects this doc to the trust-boundary inventory: an invariant maps to boundaries, and a finding is triaged by which boundary it defeats.

## The 10 invariants

1. Mandatory owner key material is generated by or for the owner, remains owner-controlled, and gates owner actions (source doc).

2. Every boot component is authenticated, measured, or hash-verified before its authority is relied upon; measured-only Path B must never be represented as enforce-before-execution Path A (source doc).

3. The signed UKI binds the kernel, initrd, command line, and dm-verity root needed to authenticate `/usr` (source doc).

4. Writable state cannot silently replace verified `/usr` content or redirect boot into unverified content (source doc).

5. Disk and home unlock require the intended FIDO2 credential, PIN, and physical presence, with recovery material kept as an explicit and separately protected bypass path (source doc).

6. TPM/fTPM evidence complements YubiKey possession; it never silently replaces the owner-held gate for disk unlock (source doc).

7. Production builds accept only approved digest-pinned inputs, and TEST-only authenticators or development artifacts cannot be promoted under production tags (source doc).

8. A/B update rollback and boot-health logic cannot make an unauthenticated artifact authoritative or mark a compromised boot healthy merely because it reached userspace (source doc).

9. Privileged exceptions, especially raw hardware access during first-boot firmware inspection and enrollment, remain narrow, one-shot, and unable to become a general persistence path (source doc).

10. Loss or failure of one authentication mechanism does not force the owner into an undocumented or weaker recovery path (source doc).

## Reading the invariants as a system

The 10 invariants divide into 4 groups by what they protect (all source doc):

- Owner identity and possession (1, 5, 10): keys are owner-generated and owner-controlled, unlock requires possession plus PIN plus presence, and losing one mechanism must not push the owner into a weaker path.

- Boot-chain integrity (2, 3, 4): each boot component is verified before use, the UKI binds the whole early-boot identity, and writable state cannot override verified content.

- Separation of evidence from authority (6): TPM evidence complements but never replaces the YubiKey gate.

- Build, release, and exception hygiene (7, 8, 9): production accepts only pinned approved inputs, update logic cannot authenticate artifacts, and privileged one-time exceptions cannot become persistence paths.

## Why invariants rather than controls

Each invariant is stated so it can be violated in more than one place, which is what makes the boundary-based evaluation rule necessary. Invariant 4, for example, can be defeated by a writable generator, a modified kernel argument, a redirected mount, or a replaced binary consumed before verification; the violation is the same, the file is different. The source doc makes the same point structurally: the attacker-story table later in the model evaluates each surface against these invariants, and the severity calibration raises severity when an issue crosses from untrusted input into release or pre-boot authority (source doc).
