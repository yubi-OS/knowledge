# The Discoverable Partitions Specification and systemd-repart

Abstract: The Discoverable Partitions Specification (DPS) defines a partition grammar for GPT disk images: a set of partition type UUIDs, labels, and attribute flags that encode what a partition contains, where it mounts, which architecture it serves, whether it auto-mounts, and which of several same-purpose partitions is newest. This turns a GPT image into a self-describing artifact that systemd's boot loader, initrd generators, container manager, and repartitioning tool can all interpret without /etc/fstab or a root= kernel command line. systemd-repart builds on that grammar as a declarative, purely additive repartitioner: it runs at first boot (or in the build sandbox) to grow, add, format, and encrypt the partitions an image describes, which is how image-mode OSes stay small at download time and instantiate themselves on the hardware they land on.

## Why a partition grammar exists

Before the DPS, Linux partitions usually declared themselves with one generic "Linux filesystem" type and little else. Lennart Poettering's June 2021 essay "The Wondrous World of Discoverable GPT Disk Images" lays out the problem and the fix: tag GPT partitions with descriptive type UUIDs, partition labels, and attribute flags so the table itself answers seven questions: what kind of data the partition holds (filesystem, swap, or verity data), what it mounts to (/home/, root, ...), which CPU architecture it serves, whether it auto-mounts, whether it mounts read-only, whether its filesystem should grow to fill the partition, and which of several versions of the same data is newest [source: https://0pointer.net/blog/the-wondrous-world-of-discoverable-gpt-disk-images.html (jev 0.06)].

The essay's sharpest point is philosophical: in a traditional install, the source of truth for what the root filesystem is sits in /etc/fstab inside the root filesystem. To know the root you must know the root. The traditional fix copies that information into boot loader configuration, making the primary source mostly irrelevant and the copy authoritative [source: https://0pointer.net/blog/the-wondrous-world-of-discoverable-gpt-disk-images.html (jev 0.06)]. A DPS-compliant image breaks this recursion: the GPT table is the single source of truth, attached to the object it describes. The essay lists the practical payoffs: simpler installers (no /etc/fstab editing step), robustness (partition tables are more stable than files inside filesystems), programmability, alternative entry points (booting the same image in a container, VM, or on bare metal), and readability for humans [source: https://0pointer.net/blog/the-wondrous-world-of-discoverable-gpt-disk-images.html (jev 0.06)].

## The grammar: type UUIDs, labels, flags

The spec today lives as UAPI.2 at uapi-group.org and defines one type UUID per purpose per architecture. Root and /usr/ partitions are architecture-specific (for example root x86-64 is 4f68bce3-e8cd-4db1-96e7-fbcaf984b709, /usr/ x86-64 is 8484680c-9521-48c6-9c11-b0720656f69e), which is what makes multi-arch images possible: ship one root partition per architecture and the right one is picked on each machine [source: https://uapi-group.org/specifications/specs/discoverable_partitions_specification/ (jev 0.71)]. Purpose partitions are architecture-independent: the home partition (933ac7e1-2eb4-4f13-b844-0e14e2aef915) auto-mounts to /home/, the server data partition (3b8f8425-20e0-4f3b-907f-1a25a76f98e8) to /srv/, the temporary data partition (7ec6f557-3bc5-4aca-b293-16ef5df639d1) to /var/tmp/ (deliberately not /tmp/, which stays tmpfs), plus a per-user home partition type managed by systemd-homed, the generic swap UUID (which predates the spec), the ESP (defined by the UEFI specification itself), and the XBOOTLDR partition (bc13c2ff-59e6-4262-a352-b275fd6f7172, defined by the Boot Loader Specification) [source: https://uapi-group.org/specifications/specs/discoverable_partitions_specification/ (jev 0.71)].

Three partition attribute flags complete the grammar: bit 63 "no-auto" (skip auto-discovery), bit 60 "read-only" (mount read-only only), bit 59 "grow-file-system" (grow the filesystem to the partition size if smaller, without effect on read-only partitions) [source: https://uapi-group.org/specifications/specs/discoverable_partitions_specification/ (jev 0.71)]. Version selection is carried in the 36-character GPT partition label: when tools find two or more root or /usr/ partitions of the same type UUID, they pick the one whose label sorts newest under a modified strverscmp(), which is the whole mechanism behind A/B updates on partitions [source: https://0pointer.net/blog/the-wondrous-world-of-discoverable-gpt-disk-images.html (jev 0.06)].

## Verity partitions

The DPS also standardizes how dm-verity data travels with a filesystem: dedicated verity and verity-signature partition types per architecture, plus a linkage convention: the root partition's UUID should be the first 128 bits of the verity root hash and the verity partition's UUID the final 128 bits, so naming the root hash suffices to locate and pair the payload and verity partitions [source: https://uapi-group.org/specifications/specs/discoverable_partitions_specification/ (jev 0.71)]. The 2021 essay notes systemd-nspawn accepts a --root-hash= switch to assemble the dm-verity volume, or a .roothash file next to the image [source: https://0pointer.net/blog/the-wondrous-world-of-discoverable-gpt-disk-images.html (jev 0.06)]. The 2022 essay "Fitting Everything Together" extends the pattern for offline security: an image ships a verity-protected /usr/ partition plus a verity partition plus a partition holding the root hash with a PKCS#7 signature, giving container boots a way into the trust chain without the firmware [source: https://0pointer.net/blog/fitting-everything-together.html (jev 0.12)]. This PKCS#7 signature partition pair appears in the current spec tables, so it is a later revision addition [source: https://uapi-group.org/specifications/specs/discoverable_partitions_specification/ (jev 0.71)] (version-sensitive: signature partitions postdate the 2021 essay, which does not mention them).

## First-boot provisioning with systemd-repart

systemd-repart is a declarative, purely additive repartitioner: it grows existing partitions or adds new ones, and never shrinks, deletes, or moves them. It reads repart.d/*.conf drop-ins shipped inside the image and, when the partition table already matches the configuration, executes no operation, which is why it is safe to run on every boot [source: https://www.freedesktop.org/software/systemd/man/latest/systemd-repart.html (jev 0.94)]. The tool runs in the initrd via systemd-repart.service before partitions are mounted; invoked with no arguments it operates on the block device backing the running root, and in the initrd on the device backing /sysroot/ [source: https://www.freedesktop.org/software/systemd/man/latest/systemd-repart.html (jev 0.94)]. The man page names the A/B case directly: the deployed image carries a single root partition ("A") and on first boot a second partition ("B") is created automatically [source: https://www.freedesktop.org/software/systemd/man/latest/systemd-repart.html (jev 0.94)].

The 2022 essay shows how this composes into an image-mode OS. The shipped image contains only two partitions: an ESP with systemd-boot and one unified kernel image, and a verity-protected /usr/ partition labeled for its version. On first boot, systemd-repart notices the root filesystem does not exist, creates it, formats it, encrypts it, and enrolls a TPM2-bound key; it also creates the empty second /usr/ partition for later A/B updates. Because the OS is hermetic in /usr/ and declaratively describes everything outside it (systemd-tmpfiles, systemd-sysusers, repart.d drop-ins), the initrd then combines the fresh root with the shipped /usr/ and transitions in [source: https://0pointer.net/blog/fitting-everything-together.html (jev 0.12)]. Key material is generated locally on first boot and never pre-provisioned, and the root filesystem sizes itself to the actual storage, so the same image adapts to whatever it was dd'ed onto [source: https://0pointer.net/blog/fitting-everything-together.html (jev 0.12)]. Offline provisioning of the same images is also possible: --image= lets systemd-repart apply the declarative rules inside an image file, combined with --size= to grow it to a target size [source: https://0pointer.net/blog/the-wondrous-world-of-discoverable-gpt-disk-images.html (jev 0.06)]. The 2021 essay also enumerates the offline provisioning siblings that share this --image= pattern: systemd-tmpfiles, systemd-sysusers, systemd-machine-id-setup, and systemd-firstboot [source: https://0pointer.net/blog/the-wondrous-world-of-discoverable-gpt-disk-images.html (jev 0.06)].

## A/B sets, updates, factory reset

In the essay's full model, first boot augments the shipped ESP plus /usr A set with: a second /usr/ partition (version B) labeled _empty (the label systemd-sysupdate uses for partitions carrying no valid payload), its verity and signature partitions also labeled _empty, an encrypted TPM2-locked root, an integrity-protected home partition (encryption left to systemd-homed), and an encrypted TPM2-locked swap. The first update fills the B set and relabels it to the new version; the next update wipes the oldest set. Factory reset deletes the state partitions so repart recreates them with fresh keys [source: https://0pointer.net/blog/fitting-everything-together.html (jev 0.12)]. The man page documents the reset trigger surface precisely (version-sensitive, current behavior): --factory-reset=yes, the systemd.factory_reset=yes kernel command line option, or the FactoryResetRequest EFI variable (vendor UUID 8cf2644b-4b0b-428f-9387-6d876050dc67); marked partitions are deleted and recreated empty [source: https://www.freedesktop.org/software/systemd/man/latest/systemd-repart.html (jev 0.94)]. New partition UUIDs are cryptographically hashed from a common seed, normally the machine ID, so a given machine reproducibly gets the same partition UUIDs [source: https://www.freedesktop.org/software/systemd/man/latest/systemd-repart.html (jev 0.94)].

## How the grammar connects to boot loaders and tools

The DPS is the joint between the image format and every consumer. On bare metal, systemd-gpt-auto-generator (implemented in systemd 211 and newer per the spec, version-sensitive) auto-discovers the root and auxiliary partitions, and automatic root discovery requires a boot loader implementing the Boot Loader Interface to tell the OS where the boot came from; /etc/fstab and root= entries always take precedence when present [source: https://uapi-group.org/specifications/specs/discoverable_partitions_specification/ (jev 0.71)]. In the 2022 boot chain, the unified kernel's usrhash= command line option pins the verity root hash of the /usr/ partition, which under the spec's UUID-derivation convention is also how the initrd finds the right /usr/ partition in the GPT table, tying signed kernels to immutable partitions [source: https://0pointer.net/blog/fitting-everything-together.html (jev 0.12)]. systemd-boot's version sort of kernel files and partition tools' label sort of /usr/ partitions implement the same newest-wins rule at two levels [source: https://0pointer.net/blog/fitting-everything-together.html (jev 0.12)]. Elsewhere: systemd-nspawn boots compliant images with -i foobar.raw -b, systemd-dissect introspects and mounts them, RootImage= runs services off them, journalctl --image= extracts logs [source: https://0pointer.net/blog/the-wondrous-world-of-discoverable-gpt-disk-images.html (jev 0.06)]. The essay's "future work" items, bootctl --image= and coredumpctl --image=, both exist in the current systemd man pages (version-sensitive: present in current releases, future as of the 2021 essay) [source: https://www.freedesktop.org/software/systemd/man/latest/bootctl.html] [source: https://www.freedesktop.org/software/systemd/man/latest/coredumpctl.html]. The 2022 essay adds the installer angle: because repart is purely additive and can copy blocks from a source image, installation can be a dd, or a repart streaming step plus bootctl, erasing the live/installer/installed distinction [source: https://0pointer.net/blog/fitting-everything-together.html (jev 0.12)].
