# Drop-Ins and Overrides in Practice

A systemd drop-in is a `*.conf` fragment placed in a `<unit>.d/` directory that systemd parses after the main unit file, letting you alter or add settings without touching the vendor unit. This doc covers the mechanics of `systemctl edit`, the drop-in search path and precedence rules, how multiple drop-ins merge (lexicographic by filename, then per-directive override or append), the lexicographic-sort trap that bites ordering-sensitive directories like `sysctl.d` and `tmpfiles.d`, `daemon-reload` discipline, and when to mask instead of override. Verification via `systemctl cat` and `systemd-delta` runs through every section.

## What a drop-in is and where systemd looks

For a unit `foo.service`, systemd reads every `*.conf` file from the `foo.service.d/` directory, merges them in alphanumeric order, and parses them after the main unit file itself ([systemd.unit(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html)). Each drop-in file must carry its own section headers (`[Unit]`, `[Service]`, ...); a header-less fragment is ignored with a parse warning, not silently applied.

The drop-in search path is wider than most operators expect:

1. Instance-level: `foo@bar.service.d/` for template instances, followed by the template directory `foo@.service.d/`.
2. Prefix-level: for unit names with dashes, systemd also searches the directories generated by truncating the name at every dash. For `foo-bar-baz.service` it reads `foo-bar-baz.service.d/`, then `foo-bar-.service.d/`, then `foo-.service.d/`. Equally named drop-ins further down the prefix hierarchy override those further up: `foo-bar-.service.d/10-override.conf` overrides `foo-.service.d/10-override.conf` ([systemd.unit(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html)).
3. Location precedence: drop-in directories can live in `/etc/systemd/system`, `/run/systemd/system`, and `/usr/lib/systemd/system`. Files in `/etc/` take precedence over `/run/`, which takes precedence over `/usr/lib/`. Drop-ins under any of these directories take precedence over unit files wherever located. Multiple drop-ins with different names are applied in lexicographic order regardless of which directory they reside in ([systemd.unit(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html)).
4. Top-level per-type drop-ins: `service.d/`, `socket.d/` and so on apply settings to every unit of that type. Files there have lower precedence than name-specific override directories, and a unit-level drop-in applies unless the unit has no drop-ins or masks of its own ([systemd.unit(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html)).

The same `*.conf.d/` pattern applies to the manager's own config: `systemd-system.conf(5)` documents snippets read from `/usr/lib/systemd/*.conf.d/`, `/usr/local/lib/systemd/*.conf.d/`, and `/etc/systemd/*.conf.d/` ([man7.org mirror](https://man7.org/linux/man-pages/man5/systemd-system.conf.5.html), dig weight 0.92; corroborated by the [Debian manpages mirror](https://manpages.debian.org/unstable/systemd/systemd-system.conf.5.en.html), dig weight 0.92).

## systemctl edit mechanics

`systemctl edit foo.service` opens an editor on a temporary file and, on a successful save, writes it as `override.conf` inside `/etc/systemd/system/foo.service.d/`. Key behaviors, all from [systemctl(1)](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html):

- The default target filename is `override.conf`; `--drop-in=NAME` picks another name.
- `--full` edits a full replacement of the main unit file in `/etc/systemd/system/` instead of a drop-in. `--force` creates a unit even if the main file does not exist.
- `--runtime` writes the drop-in under `/run/` so it is lost at reboot. You cannot temporarily edit units already in `/etc/`, because `/etc/` outranks `/run/`.
- On successful exit the configuration is reloaded automatically, equivalent to `systemctl daemon-reload`. For `edit --global` the reload is skipped and the change lands at next login.
- If the editor exits with an empty file, the modification is canceled.
- Version note: `edit` was added in version 218.

`edit` writes only on success and reloads for you, so it is the safe interactive path. Hand-creating `override.conf` with `mkdir -p /etc/systemd/system/foo.service.d/` and a heredoc is fine too, but then the reload is on you (see below).

## How multiple drop-ins merge

All drop-ins are concatenated in lexicographic filename order across all search directories, then parsed as one configuration ([systemd.unit(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html)). What happens per directive depends on the directive's value type ([systemd-system.conf(5)](https://man7.org/linux/man-pages/man5/systemd-system.conf.5.html), dig weight 0.92; framing corroborated by [dev.to](https://dev.to/redrum_yot/understanding-drop-in-overrides-in-systemd-when-parameters-accumulate-vs-override-3noi), dig weight 0.92):

| Directive type | Effect of a later drop-in | Example |
| --- | --- | --- |
| Single-value | Overrides the earlier value | `Type=`, `Nice=`, `PrivateTmp=` |
| List-valued | Appends; entries accumulate | `Environment=`, `ExecStart=` lines in services |
| Dependencies | Append only; cannot be emptied | `After=`, `Wants=`, `Requires=` |
| Reset-to-empty via `=` with no value | Clears the preceding list | `AssertPathExists=` then re-add |

Two consequences from the man page's own example ([systemd.unit(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html)): to remove an entry from a parsed list such as `AssertPathExists=` or `ExecStart=`, a drop-in must first clear the list with an empty assignment and then re-add the wanted entries. Dependencies such as `After=` cannot be reset to empty at all, so drop-ins can only add dependencies; removing one requires `systemctl edit --full` and owning the whole unit file.

## Verifying what the manager will actually use

Two commands answer "what is my effective config and why":

- `systemctl cat foo.service` prints the main unit file followed by every drop-in the manager is reading, annotated with its path ([systemctl(1)](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html)). If the output disagrees with what you expect, a drop-in from an unexpected directory (the prefix-level or top-level `service.d/` search) is in play.
- `systemd-delta` lists every file that overrides another file, and classifies each as `masked`, `equivalent`, `redirected`, `overridden`, `extended` (drop-in `*.conf` files for units, added in version 205), or `unchanged` ([systemd-delta(1)](https://www.freedesktop.org/software/systemd/man/latest/systemd-delta.html)). `systemd-delta --type=extended systemd/system` is the fast audit of all unit drop-ins on a box; `systemd-delta --type=masked` finds leftover masks.

## The lexicographic-sort trap

Ordering-sensitive fragment directories merge by full filename in lexicographic order across all their search directories, and the trap is that "later file wins" is NOT universal:

- `sysctl.d`: all files are sorted lexicographically regardless of directory; when multiple files set the same option, the entry in the lexicographically LATEST file takes precedence. Same-named files are replaced wholesale by a higher-priority directory (`/etc/` over `/run/` and `/usr/`). The man page recommends two-digit prefixes, range 10-40 for vendor files in `/usr/` and 60-90 for local files in `/etc/` and `/run/` ([sysctl.d(5)](https://www.freedesktop.org/software/systemd/man/latest/sysctl.d.html)).
- `tmpfiles.d`: files are also sorted lexicographically across directories, but when multiple files specify the same path, the entry in the lexicographically EARLIEST file wins and other conflicting entries are logged as errors, the opposite direction from `sysctl.d` ([tmpfiles.d(5)](https://www.freedesktop.org/software/systemd/man/latest/tmpfiles.d.html)).
- udev rules: all `.rules` files from `/usr/lib/udev/rules.d`, `/usr/local/lib/udev/rules.d`, `/run/udev/rules.d`, and `/etc/udev/rules.d` are collectively sorted and processed lexicographically; files with identical filenames replace each other, with `/etc/` highest ([udev(7)](https://www.freedesktop.org/software/systemd/man/latest/udev.html)).
- `modprobe.d`: files are sorted lexicographically regardless of directory; a same-named file in a higher-precedence directory is ignored after the first copy loads, and later-ordered files partially replace earlier ones ([modprobe.d(5), man7.org mirror](https://man7.org/linux/man-pages/man5/modprobe.d.5.html)).

**Named failure mode: the 50-something file that silently loses.** A drop-in or fragment named `53-foo.conf` sorts before any `s-*.conf` or `zz-*.conf`, and before a vendor `90-*.conf`. In `sysctl.d` that means the vendor file wins the same option; in `tmpfiles.d` it means the early file wins the same path and the vendor line becomes an error-level conflict. The lexicographic emphasis appears in current third-party walkthroughs precisely because this bites real deployments ([oneuptime](https://oneuptime.com/blog/post/2026-03-02-how-to-override-systemd-service-parameters-with-drop-in-files-on-ubuntu/view), dig weight 0.92). Countermeasures: never rely on "my file happens to sort last", copy the vendor number when overriding the same option, and use the documented vendor/local number bands.

## daemon-reload discipline

The manager holds parsed unit configuration in memory. `systemctl cat` shows the on-disk files, which "might not match the system manager's understanding of these units if any unit files were updated on disk and the `daemon-reload` command was not issued since" ([systemctl(1)](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html)). So:

- After hand-editing or packaging a unit or drop-in, run `systemctl daemon-reload`. It re-reads all unit files and drop-ins and rewires dependencies.
- Runtime settings changed via drop-ins need a service restart to take effect; `daemon-reload` alone does not restart anything.
- `systemctl revert UNIT` (added in version 230) removes all `/etc/` copies and drop-ins for the unit and reloads, undoing exactly what `edit`, `mask`, and `set-property` did ([systemctl(1)](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html)).
- Package scripts that install drop-ins must call `daemon-reload` too; on image-based systems where vendor fragments ship in the initrd, the initrd must be regenerated to pick them up ([sysctl.d(5)](https://www.freedesktop.org/software/systemd/man/latest/sysctl.d.html)).

## Masking vs overriding

Masking is not a stronger drop-in, it is a different mechanism: `systemctl mask UNIT` symlinks the unit's name to `/dev/null` in `/etc/systemd/system/` (or `/run/systemd/system/` with `--runtime`), making activation of every kind, including enablement and manual start, impossible ([systemctl(1)](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html), added in version 238). The command fails if a real unit file already exists at that path, so it mainly works against vendor units under `/usr/lib/systemd/system/`, and it is intentionally stronger than `disable`. Use it to kill a vendor unit outright; use a drop-in to bend it. To neutralize a vendor fragment in the fragment directories (`sysctl.d`, `tmpfiles.d`, udev rules), the documented idiom is a symlink with the same basename pointing to `/dev/null` ([sysctl.d(5)](https://www.freedesktop.org/software/systemd/man/latest/sysctl.d.html), [tmpfiles.d(5)](https://www.freedesktop.org/software/systemd/man/latest/tmpfiles.d.html), [udev(7)](https://www.freedesktop.org/software/systemd/man/latest/udev.html)). `systemd-delta --type=masked` then shows the mask as an override class of its own ([systemd-delta(1)](https://www.freedesktop.org/software/systemd/man/latest/systemd-delta.html)).
