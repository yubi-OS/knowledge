# Boot Analysis and Targets in Practice

systemd boots a machine by building a dependency transaction from `default.target` and exposing each phase of startup as a target unit, so every boot problem is ultimately a target that failed to reach its synchronization point or a job that stalled inside one. This doc covers the operator toolkit for both halves of that problem: reading the boot (targets vs SysV runlevels, `systemd-analyze` timing subcommands, dependency graph tools) and intervening when boot goes wrong (rescue, emergency, and debug shells, runtime masking, break points, and job timeout tuning).

## Targets versus SysV runlevels

Target units (`.target`) have no unit-type-specific configuration at all: there is no `[Target]` section, because targets only group units and act as synchronization points for `Wants=`, `Requires=`, `Before=`, and `After=` dependencies. An empty target unit file is treated as a masked unit, so a custom target must contain at least a `[Unit]` section with a `Description=` [systemd.target(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.target.html). One automatic dependency matters when authoring targets: `Wants=`/`Requires=` configured inside a target are automatically complemented with `After=` on those units, but the reverse is not true, so a service that wants to be ordered after a target must state its own `After=` [systemd.target(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.target.html).

Targets replace SysV runlevels with something more flexible: a named, dependency-linked set of units rather than a single integer. The working mapping an operator needs (jev 0.92, [Red Hat: booting into a target system state](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/10/html/using_systemd_unit_files_to_customize_and_optimize_your_system/booting-into-a-target-system-state)) is runlevel 0 to `poweroff.target`, 1 to `rescue.target`, 3 to `multi-user.target`, 5 to `graphical.target`, and 6 to `reboot.target`. The compatibility is explicit in systemd itself: `rescue.target` documents `systemd.unit=rescue.target` on the kernel command line, with the short alias `1`, as SysV-compatible behavior [systemd.special(7)](https://www.freedesktop.org/software/systemd/man/latest/systemd.special.html). To change the boot target without rebooting, `systemctl isolate NAME.target` switches the running system (isolating stops everything not part of the new target); `systemctl set-default` changes which target boots by default (jev 0.92, Red Hat, same page).

## The chain you are measuring

`default.target` is usually an alias of `graphical.target` or `multi-user.target`, and systemd activates it plus all recursive dependencies. The ordering skeleton is: mount/swap/cryptsetup work converge into `sysinit.target`; `sysinit.target` fans out into `timers.target`, `paths.target`, and `sockets.target` plus `rescue.service`/`rescue.target` alongside; those converge into `basic.target`; and `basic.target` orders the system services that feed `multi-user.target` and then `graphical.target`, with `emergency.service`/`emergency.target` hanging off independently [bootup(7)](https://www.freedesktop.org/software/systemd/man/latest/bootup.html). When a boot appears stuck, the practical question is: which target in this chain did not complete, and which job inside it is still running.

## systemd-analyze: measuring the boot

`systemd-analyze time` prints time spent in the kernel, in the initrd, and in userspace, up to the point where all services were spawned, not necessarily fully initialized. Real-machine output looks like `Startup finished in 2.584s (kernel) + 19.176s (initrd) + 47.847s (userspace) = 1min 9.608s`, followed by a line such as `multi-user.target reached after 47.820s in userspace` [systemd-analyze(1)](https://www.freedesktop.org/software/systemd/man/latest/systemd-analyze.html).

`systemd-analyze blame` lists all running units ordered by initialization time, but read it with its documented caveats: a unit can look slow because it was waiting on another unit, `Type=simple` services never appear (systemd considers them started immediately), and the numbers only cover time in the "activating" state, not queue latency or waiting on hardware [systemd-analyze(1)](https://www.freedesktop.org/software/systemd/man/latest/systemd-analyze.html). Blame answers "what took long", not "what blocked what"; for the latter use `critical-chain` (jev 0.10, [linuxblog.io](https://linuxblog.io/systemd-analyze-debug-optimize-linux-boot/), a tutorial, cited only for this framing).

`systemd-analyze critical-chain [UNIT...]` prints a tree of the time-critical chain toward the default target, or toward the units you name. In the output, the time after `@` is when the unit became active and after `+` how long it took to start: `multi-user.target @47.820s` then `└─pmie.service @35.968s +548ms` and so on down to `system.slice`. The same caveat applies: socket activation and parallel execution can make the tree misleading, and timed-out jobs are not shown [systemd-analyze(1)](https://www.freedesktop.org/software/systemd/man/latest/systemd-analyze.html). A common workflow pairs the two commands: `systemd-analyze blame | grep sshd` for the service's own startup time, then `systemd-analyze critical-chain sshd.service` to see what it waited for (jev 0.96, [oneuptime.com](https://oneuptime.com/blog/post/2026-03-04-systemd-analyze-diagnose-slow-boot-rhel-9/view)). `systemd-analyze plot > bootup.svg` gives the same data as an SVG timeline, based on the most recent start cycle of loaded units, so consult it shortly after boot [systemd-analyze(1)](https://www.freedesktop.org/software/systemd/man/latest/systemd-analyze.html).

`systemd-analyze dump [pattern…]` serializes the complete service manager state; it is long, its format can change without notice and must not be parsed by applications, and it is rate limited for unprivileged users [systemd-analyze(1)](https://www.freedesktop.org/software/systemd/man/latest/systemd-analyze.html). It is the canonical evidence blob for bug reports (jev 0.91, [systemd.io/DEBUGGING/](https://systemd.io/DEBUGGING/)).

`systemd-analyze verify FILE...` loads unit files (plus everything they reference) and reports structural errors: unknown sections and directives, required dependencies that cannot be found, `Documentation=` man pages that do not exist, and `ExecStart=` commands that are missing or not executable. Example output for a bad unit: `[./user.slice:9] Unknown lvalue 'WhatIsThis' in section 'Unit'` followed by a load failure and `Failed to create user.slice/start: Invalid argument` [systemd-analyze(1)](https://www.freedesktop.org/software/systemd/man/latest/systemd-analyze.html). Run it against edited units before they can ruin the next boot. Note that a usable `/dev` plus cgroup and fanotify support are recommended for verify to operate cleanly (jev 0.91, systemd.io/DEBUGGING/).

## The dependency graph

`systemctl list-dependencies [UNIT…]` recursively lists units required and wanted by the named unit, following `Requires=`, `Requisite=`, `Wants=`, `ConsistsOf=`, `BindsTo=`, and `Upholds=`; by default it expands dependencies of target units only, `--all` follows dependencies of all units, and `--reverse` shows what wants a unit instead of what a unit wants [systemctl(1)](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html). For a picture, `systemd-analyze dot [pattern...]` emits a GraphViz-format graph: `systemd-analyze dot | dot -Tsvg >systemd.svg` for everything, or scoped with patterns, e.g. `systemd-analyze dot --to-pattern='*.target' --from-pattern='*.target' | dot -Tsvg >targets.svg` to draw only target-to-target edges. Without `--order` or `--require`, the graph mixes ordering and requirement dependencies [systemd-analyze(1)](https://www.freedesktop.org/software/systemd/man/latest/systemd-analyze.html).

## Debugging a stuck boot: decision tree

First, establish where the boot stopped. Boot with `rhgb` and `quiet` removed from the kernel command line; if you see `Starting name…` and `[ OK ] Started name.` lines, systemd itself is running. If you get no login prompt, try switching virtual terminals with `CTRL+ALT+F__`, because a display server failure can hide tty1 while other VTs work. Let a suspicious boot retry for up to 5 minutes before declaring it stuck: a timing-out service is killed after its timeout and boot often continues, and a failed device for an important mount point usually lands you in emergency mode instead (jev 0.91, [systemd.io/DEBUGGING/](https://systemd.io/DEBUGGING/)).

If you have a shell but the boot is stalled, run `systemctl list-jobs`; jobs listed as running must finish before the waiting ones can start, which pins the blocker. To make systemd verbose, add `systemd.log_level=debug systemd.log_target=kmsg log_buf_len=1M printk.devkmsg=on` and read `journalctl -b` afterwards; for early output when PID 1 itself is suspect, log to a serial console with `systemd.log_level=debug systemd.log_target=console console=ttyS0,38400 console=tty1`, or have journald forward to console with `systemd.journald.forward_to_console=1` when a later critical service is the problem (jev 0.91, systemd.io/DEBUGGING/).

If the failure is in normal services after the basic system came up, boot `systemd.unit=rescue.target` (or just `1`): rescue pulls in the base system including system mounts and spawns a rescue shell, effectively single-user mode with file systems mounted and only the most basic services running; from there, disable the bad service. If rescue fails, go one level lower with `systemd.unit=emergency.target` (or `emergency`): it starts an emergency shell on the main console and pulls in no services or mounts, so usually only PID 1 and the shell are running. The root file system may be mounted read-only, since no special remounting happens for this target, so run `mount -o remount,rw /` before editing files. Classic emergency-shell work is fixing bad `/etc/fstab` lines, then `systemctl daemon-reload` so systemd re-reads it. systemd also drops into `emergency.target` on its own when a file system check on a required file system fails. If even emergency fails, try `init=/bin/sh`; if that fails, boot from other media (jev 0.91, systemd.io/DEBUGGING/ plus [systemd.special(7)](https://www.freedesktop.org/software/systemd/man/latest/systemd.special.html) for the target semantics).

For break points inside the initrd, dracut offers `rd.break` to drop to a shell at the end of initrd, and `rd.break={cmdline|pre-udev|pre-trigger|initqueue|pre-mount|mount|pre-pivot|cleanup}` to break before a specific dracut phase ([dracut.cmdline(7)](https://man7.org/linux/man-pages/man7/dracut.cmdline.7.html)). systemd gained its own equivalent in version 258: `systemd.break=` / `rd.systemd.break=` accept `pre-udev`, `pre-basic`, `pre-mount`, and `pre-switch-root` (comma-separated sets allowed), pausing boot at that point, spawning a shell, and resuming when you exit. `pre-mount` and `pre-switch-root` work only in the initrd; `pre-udev` and `pre-basic` work on the host too. The `rd.` prefix means the option is honored only in the initrd (version-sensitive: added in v258, [systemd-debug-generator(8)](https://www.freedesktop.org/software/systemd/man/latest/systemd-debug-generator.html)).

The same generator handles two more debug levers. `systemd.mask=UNIT` (or `rd.systemd.mask=` in the initrd) masks a unit for this boot only, removing it from the initial transaction without editing any files; repeatable. `systemd.wants=UNIT` adds a start job for an extra unit. `systemd.debug_shell` (since v215) pulls `debug-shell.service` into the boot transaction and spawns a root shell on `/dev/tty9` by default, overridable per boot with `systemd.default_debug_tty=`; from early boot onward, switch to it with `CTRL+ALT+F9` and inspect `systemctl list-jobs`, service status, and logs. It can also be enabled persistently with `systemctl enable debug-shell.service`, or offline with `systemctl --root=/ enable debug-shell.service` from another booted system, but it must be disabled after debugging: an always-available unauthenticated root shell is a security hole (jev 0.91, systemd.io/DEBUGGING/, plus systemd-debug-generator(8)). Since v256 the generator also accepts `systemd.extra-unit.*` credentials to inject extra units (an empty value masks a unit) and `systemd.unit-dropin.*` credentials to add drop-ins to both initrd and final system (version-sensitive, systemd-debug-generator(8)).

## Job timeout tuning

A boot that is "stuck" for exactly 90 seconds per failing service is a timeout, not a hang. `DefaultTimeoutStartSec=`, `DefaultTimeoutStopSec=`, `DefaultTimeoutAbortSec=`, and `DefaultRestartSec=` in `/etc/systemd/system.conf` configure default timeouts for starting, stopping, aborting, and restart delay, overridable per unit via `TimeoutStartSec=` etc. in the unit itself; `DefaultTimeoutStartSec=` also sets the default `TimeoutSec=`. Defaults: 90 s for start and stop in both the system and the user manager, `DefaultTimeoutAbortSec=` unset so units fall back to `TimeoutStopSec=`, and `DefaultRestartSec=` at 100 ms (version-sensitive: these directives exist since v209, [systemd-system.conf(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd-system.conf.html)). To get a machine out of a boot wedged on a service that will never come up, prefer runtime masking for one boot (`systemd.mask=`) over lowering the global timeout; lower timeouts only to make a genuinely broken service fail faster and be skipped.
