# What an OS can safely claim about secure-world time

Scope: the claim boundary for yubiOS secure-world time on RK3399/RK3588: what is claimable before hardware proof, what becomes claimable after proof, and what stays outside the claim (wall clock, reboot rollback, remote freshness).

## The specification's own floor

The GlobalPlatform TEE Internal Core API specification states that trust in System Time and TA Persistent Time is implementation-defined, because implementations may not include fully trustable hardware sources of time (weight 0.92, authoritative backing: https://globalplatform.org/wp-content/uploads/2018/06/GPD_TEE_Internal_Core_API_Specification_v1.1.2.50_PublicReview.pdf). The GlobalPlatform TEE Protection Profile lists monotonic TA instance time among the TEE security functions at the logical boundary of the TOE (weight 0.71, authoritative backing: https://wikileaks.org/sony/docs/05/docs/Global%20Platform/GPD_TEE_ProtectionProfile_v1.0.pdf).

A Stack Overflow answer grounded in the Core API text states the practical minimum guarantee: the system-time value cannot decrease while a trusted application is running, the REE may control at what speed it proceeds, and there is no guarantee across reboots (weak backing, weight 0.07: https://stackoverflow.com/questions/68544061/how-to-get-a-utc-timestamp-in-op-tee-trusted-application-ta-in-datetime-format). A second, near-identical Stack Overflow entry repeats that the security level depends on the secure clocks available on the specific system (weak backing, weight 0.18: https://stackoverflow.com/questions/68544061/how-to-get-a-utc-timestamp-in-op-tee-trusted-application-ta-in-datetime-format).

## Monotonic elapsed time versus wall clock

The counter that backs a TEE-controlled time source on ARM64 is the generic timer physical counter. Arm documents the Generic Timer as a common timer framework for A-profile processing elements with defined programming interfaces (weight 0.81, authoritative backing: https://support.arm.com/documentation/102379/0101/The-processor-timers; PDF version at weight 0.78: https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/Learn%20the%20Architecture/Generic%20Timer.pdf?revision=c710e7a7-9f52-4901-8c9d-91b19f44f9c7 and weight 0.70: https://documentation-service.arm.com/static/6294c39db334256d9ea8ae53). A free-running counter is an elapsed-time source, not a calibrated wall clock: as the maintainer discussion notes, protection level 1000 under Core API v1.1 requires a calibrated time origin such as a secure RTC (weak backing, weight 0.31: https://github.com/OP-TEE/optee_os/issues/5973). This is the specification-level gap between "monotonic-ish elapsed time within a boot" and "wall clock".

## Anti-rollback and persistence are different primitives

Rollback resistance comes from persistent monotonic state, not from a clock. An industry reference defines an anti-rollback clock as a real-time clock periodically verified to have advanced, where trust comes from that verification discipline rather than from the clock hardware alone (weight 0.90, authoritative backing: https://learn.microsoft.com/en-us/playready/features/trusted-clocks). In OP-TEE, rollback protection for persistent state comes from storage choices: the default REE file system versus the RPMB partition of an eMMC device enabled by `CFG_RPMB_FS=y` (weight 0.64, authoritative backing: https://optee.readthedocs.io/en/latest/architecture/secure_storage.html). A domain-specific writeup frames the minimal secure-time loop as event plus monotonic counter plus signed token, providing integrity, freshness, and rollback detection without a full secure log subsystem (weight 0.60, weak-to-moderate backing: https://icnavigator.com/technology/reference-oscillators-timing/secure-rtc-time-stamping/).

A third-party comparison notes that TEE rollback protection generally relies on hardware-enforced monotonic counters and sealed storage to make state reversion physically impossible (weak backing, weight 0.19: https://chainscorelabs.com/differences/execution-environments-and-virtual-machines/sandboxing-and-isolation-boundaries/tee-rollback-protection-vs-blockchain-finality-key-differences).

## The yubiOS claim boundary

Per the yubiOS refs source doc (sectime-rk-secure-time-2026-07-17): until a real RK3399/RK3588 firmware build proves `CFG_SECURE_TIME_SOURCE_CNTPCT=y` in the active OP-TEE platform configuration and OP-TEE boots as BL32 through TF-A `SPD=opteed`, yubiOS should not claim secure-world time at all, only that the design target is TEE-controlled time. After that proof, the safe claim is narrow: TEE-controlled monotonic-ish elapsed time within a boot, resistant to normal-world wall-clock tampering. It is not an absolute wall clock, not a reboot or power-loss anti-rollback counter, and not sufficient freshness for remote attestation or lockout recovery by itself. The dig's sources support each element of that split: the counter is elapsed time (Arm Generic Timer), the calibrated-origin gap keeps it from being wall clock (Core API issue), and rollback and freshness require other primitives (RPMB storage, attestation nonces, covered in doc 08).
