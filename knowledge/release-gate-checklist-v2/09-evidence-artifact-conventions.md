# Evidence artifact conventions for launch gates

Scope: how gate evidence is recorded and kept defensible: artifact paths, review stamps against blockers, version control, and drift correction of planning documents.

## Why conventions matter

Gate evidence that cannot be found, dated, or verified is not evidence. Audit literature makes the point directly: auditing is defined as verification activity, inspection or examination of a process or quality system (w=0.834, high backing) [https://asq.org/quality-resources/auditing], and configuration management exists to guarantee consistency between the system and its configuration information, ensure the integrity and traceability of that information and its changes over time, and facilitate reproducibility (w=0.828, high backing) [https://sebokwiki.org/wiki/Configuration_Management]. A launch gate inventory is a configuration-management problem applied to evidence: every gate's claim must trace to a named artifact at a known location with a known revision.

Compliance practice shows what happens when the conventions are missing: organizations focus on implementing controls while underestimating evidence collection, a gap that becomes apparent when buyers request audit trails, security logs, or documented proof of operational controls (w=0.347, weak backing) [https://www.konfirmity.com/blog/iso-27001-evidence-requirements]. Documented-information regimes require creating and maintaining records as part of normal operation (w=0.242, weak backing) [https://www.wintersmithadvisory.com/iso-27001-documentation-requirements], and change histories created as part of normal operations become audit evidence (w=0.501, weak backing) [https://amdt.com/solutions/ot-change-management-version-control/].

## The artifact conventions

A workable convention set has four rules. First, every gate has named artifact paths in the planning corpus, so evidence lands in a predictable place: an audit report path, a transcript path, a runlog path, an agreement path, each with the date in the filename. Second, protected material is split: the NDA-protected full report lives outside the public repo, and the public summary references it by hash, tying the two cryptographically. Third, each artifact's review state is stamped: which review produced it and against which blocker list. Fourth, tracking items are filed per gate criterion, one issue per incident or finding, linked from the summary artifact. Audit-trail documentation guidance describes the target: a defensible evidence chain with defined record-keeping, known break points, and retention through archive (w=0.266, weak backing) [https://www.fieldguide.io/resource-articles/audit-trail-documentation], and a compliance audit trail as the unbroken chain of evidence that every document and approval followed established procedures (w=0.250, weak backing) [https://www.docsie.io/blog/glossary/compliance-audit-trail/].

## Review stamps and drift correction

Planning documents drift. Revision-drift practice defines the failure precisely: revision drift is the gap between the official document revision in the control system and the version being used to make real-world decisions (w=0.272, weak backing) [https://pathnovo.com/blog/revision-drift-epc-schedule-delay]. Documentation-drift prevention names the countermeasures: detecting when documentation falls out of sync with the actual state, with prevention strategies including change detection and ownership accountability models (w=0.176, weak backing) [https://atlan.com/know/documentation-drift-prevention-strategies/].

The gate-inventory answer is a review stamp on every planning document: a dated marker recording the last time the document was checked against the current blocker list and gate status. Review-stamp practice in engineering document control shows the mechanics: stamps carry the document number, revision, reviewing engineer, date, and review grade (w=0.073, weak backing) [https://www.scribd.com/document/353288059/H347210-5270-50-042-0005-1]. The stamp converts "is this current?" from a question into a lookup, and a stale stamp is itself a finding.

## Version control for evidence

Evidence artifacts need version discipline too. Document version-control practice centers on consistent, descriptive naming so a document's purpose, version, and status are instantly identifiable (w=0.210, weak backing) [https://contractorforeman.com/best-practices-for-document-version-control/]. Policy-as-code systems go further, generating audit trails and compliance reports automatically from the same source that defines the policy (w=0.389, weak backing) [https://policyascode.dev/guides/audit-and-reporting/]. For a gate inventory kept in a repository, the equivalent is: evidence documents in the repo, protected originals outside with hash cross-references, and every status change of a gate recorded as a commit rather than an edit in place, so the history of "when did gate X close" is itself part of the evidence.

## The auditability test

The convention set passes one test: can a reviewer, given only the artifact paths and the tracking items, re-verify every gate's PASS claim without interviewing anyone? If the security audit's claim points to a dated public summary with a hash reference to the full report, if the pricing claim points to verbatim transcripts and a redacted contract, if the reference claim points to a day-by-day runlog and a signed agreement, the answer is yes. That re-verifiability, not the existence of the artifacts, is what makes a gate inventory trustworthy at launch time.
