# Rockchip recovery model (Stage 3)

Scope: hardware-gated recovery options on RK3399 and RK3588 after lockout, cgroup or context drain versus per-GPU reset versus full GPU power-cycle, and what must be proven on the boards before any recovery claim is made.

## What Panfrost reset actually does today

Full GPU reset in Panfrost is a multi-step hardware operation: it soft-stops jobs and polls the hardware. Review discussion on the reset rework series argues that a 60 millisecond wait is extremely short for that sequence, and that premature expiry returns ENODEV and abandons recovery (source: https://www.mail-archive.com/dri-devel@lists.freedesktop.org/msg623631.html, jev weight 0.72). Reset handling is also a state-machine hazard: if a userspace thread calls DRM_IOCTL_PANFROST_PERFCNT_DUMP while the GPU is undergoing a soft reset triggered asynchronously by panfrost_reset_work, the reset state machine could be corrupted, leading to undefined hardware behavior; a reset lock patch addresses this (source: https://www.mail-archive.com/dri-devel@lists.freedesktop.org/msg623642.html, jev weight 0.71).

Recent patches refine when resets happen at all. A status code DRM_GPU_SCHED_STAT_NO_HANG tells the scheduler that a job did not actually time out and no reset was performed, avoiding job leaks (source: https://lists.freedesktop.org/archives/dri-devel/2025-July/514272.html, jev weight 0.70; earlier posting https://lists.freedesktop.org/archives/dri-devel/2025-June/511203.html, jev weight 0.65). A related patch lets Panfrost skip the reset when the TDR fired before the IRQ handler ran, using DRM_GPU_SCHED_STAT_RUNNING, fixing a case where the job leaked because free_job() was never called (source: https://lists.freedesktop.org/archives/dri-devel/2025-May/504885.html, jev weight 0.56). A hard reset fallback for the case where soft reset fails was proposed in an earlier series, with reviewers noting soft reset should ideally never fail (source: https://lkml.rescloud.iu.edu/2311.1/01403.html, jev weight 0.47, weak backing).

## Userspace recovery is separately proven

A GPU reset used to mean the whole GNOME desktop session crashing or freezing with no way back; a 2026 GSoC project built a recovery mechanism so Mutter survives a reset, restoring what can be restored automatically (source: https://blogs.gnome.org/anonymoux47/2026/08/28/gpu-reset-recovery-in-mutter-gsoc-wrap-up/, jev weight 0.70). This matters for the lockout design's recovery criterion: compositor-level reset recovery exists in the ecosystem, but it is compositor work, not a property the lockout mechanism can assume on every board.

## The board split

The design's hardware tests run separately on ROCK 5B (RK3588) and ROCKPro64 (RK3399). The two boards sit on different Mali generations: RK3399 carries a Midgard-class GPU served by Panfrost with Rockchip's proprietary libmali userspace also in circulation (source: https://github.com/hevz/libmali-rk3399, jev weight 0.31, weak backing; source: https://github.com/tsukumijima/libmali-rockchip, jev weight 0.31, weak backing), and RK3588 systems commonly boot with a panthor GPU devicetree overlay that users disable when switching driver stacks, per community troubleshooting threads (source: https://forum.armbian.com/topic/51939-rk3588-setting-up-mali-hardware-acceleration/, jev weight 0.05, weak backing). A vendor-hosted libmali repository for RK3588 Linux exists on GitLab (source: https://gitlab.com/rk3588_linux/linux/libmali, jev weight 0.59). The weak scores on several board sources are themselves evidence for the design's caution: board-level GPU behavior on these SoCs is documented mostly in forums and community guides (source: https://xdaforums.com/t/firmware-and-modifications-for-rockchip-rk35xx-rk3566-rk3588-etc.4716612/, jev weight 0.03, weak backing; source: https://ib.bsb.br/setting-up-gpu-drivers-on-rk3588/, jev weight 0.25, weak backing), so Stage 3 claims must come from direct hardware tests, not from the written record.

## Why Stage 3 is hardware-gated

The open question the design refuses to answer from documentation alone: after a lockout, can RK3399 or RK3588 recover by draining the offending cgroup or context jobs, or is a per-GPU reset required, or does recovery need a full GPU power-cycle or SoC-level reset? The reset machinery described above shows per-GPU soft reset exists and is fragile under concurrency; nothing in the collected evidence proves a drain-only recovery path works on either board. Only after the board tests run does the design pick the recovery mechanism and write production language for it.
