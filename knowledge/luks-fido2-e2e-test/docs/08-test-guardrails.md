# 08 - Guardrails: keeping software authenticators TEST-only

Scope: the separation between test-only software authenticators and production unlock authority, and the certification and CI practices that shape that policy.

## The core distinction

A software FIDO2 authenticator keeps its credential material in host software: a local state file is a stated design property of at least one CTAP2.1 softoken implementation (GitHub fidolizer, https://github.com/19h/fidolizer, weight 0.578), and other software authenticators are explicitly beta-quality implementations of a virtual USB device (GitHub virtual-fido, https://github.com/bulwarkid/virtual-fido, weight 0.747). A production disk-unlock authority, by contrast, is an external hardware security key: FIDO2 supports portable external hardware security keys as a distinct authenticator category, separate from built-in and synced-passkey authenticators (Yubico, https://www.yubico.com/authentication-standards/fido2/, weight 0.639). The guardrail policy follows directly from that asymmetry: a credential that lives in a host state file cannot provide the same assurance as one that lives in a physical token, so softokens are acceptable as test fixtures and unacceptable as production defaults.

## What certification requires of real authenticators

The FIDO Alliance treats interoperability testing as a required step in the certification process, supported through interoperability testing events and on-demand testing (FIDO Alliance, https://fidoalliance.org/certification/interoperability-testing/, weight 0.901). This matters for a guardrail design because it defines what a hardware token has proven that a softoken has not: conformance to the protocol specification under third-party observation (FIDO Alliance, https://fidoalliance.org/certification/interoperability-testing/, weight 0.901). A project policy that treats software authenticators as TEST-only is therefore not paranoia; it is an acknowledgment that only the certified hardware surface has been through interoperability certification.

## CI practice for virtual authenticators

The established CI pattern for web authentication is virtual authenticators: testing passkeys in CI with virtual authenticators through the Chrome DevTools Protocol, Playwright, and Selenium, running WebAuthn headless with no physical key (MojoAuth blog, https://mojoauth.com/blog/test-passkeys-ci-virtual-authenticators, weight 0.603). That pattern operates at the browser WebAuthn layer. Disk unlock testing operates one layer down, at CTAP, where the authenticator must answer hmac-secret derivations; the two layers need different strategies (HelpMeTest blog, https://helpmetest.com/blog/fido2-authenticator-testing/, weight 0.337, weak backing). A guardrail that follows from this layering: the test-only softoken is granted only the surfaces the CI harness needs, and the production image builder is a separate pipeline that never embeds it.

## Why the separation is security-load-bearing

FIDO2's value proposition is phishing-resistant cryptographic authentication (Microsoft Security, https://www.microsoft.com/en-us/security/business/security-101/what-is-fido2, weight 0.885). Substituting a software stand-in in production would convert a hardware-anchored credential into a host-resident secret, which is exactly the property the softoken implementations advertise for their own state (GitHub fidolizer, https://github.com/19h/fidolizer, weight 0.578). Enterprise deployment guidance frames FIDO2 rollout as a lifecycle process covering enrollment, device replacement, and recovery (NhiM FAQ, https://nhimg.org/faq/why-do-enterprise-fido2-rollouts-often-stall-in-production/, weight 0.262, weak backing); a test-only guardrail is the simplest possible lifecycle control, because it removes the softoken from the production lifecycle entirely.

## Concrete policy shape

The defensible policy, grounded in the sources above, has four clauses. First, software authenticators exist only in development and test images; the production image build is a distinct pipeline (MojoAuth blog, https://mojoauth.com/blog/test-passkeys-ci-virtual-authenticators, weight 0.603). Second, every test image carries a marker that a release gate can detect, so a softoken leaking into a release artifact fails the build (FIDO Alliance, https://fidoalliance.org/certification/interoperability-testing/, weight 0.901). Third, release confidence requires at least one hardware-in-the-loop run against a certified-capable external key (Yubico, https://www.yubico.com/authentication-standards/fido2/, weight 0.639; FIDO Alliance, https://fidoalliance.org/certification/interoperability-testing/, weight 0.901). Fourth, a softoken passing all CI legs never upgrades its own authority: CI green is evidence the unlock code works, not evidence the production trust anchor is adequate (GitHub virtual-fido, https://github.com/bulwarkid/virtual-fido, weight 0.747). This corpus documents the policy shape from public sources; each project instantiates it against its own image build and release process.
