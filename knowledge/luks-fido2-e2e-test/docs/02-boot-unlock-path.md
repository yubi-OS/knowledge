# 02 - Boot-time FIDO2 unlock path

Scope: the early-userspace unlock path, from crypttab options through systemd-cryptsetup FIDO2 token handling in the initramfs, and what a boot test observes.

## The crypttab wiring

The unlock side is configured with the fido2-device= option in the fourth column of /etc/crypttab. The systemd 248 announcement describes the mechanism: the option tells systemd-cryptsetup to use the FIDO2 metadata now embedded in the LUKS2 header, to wait for the FIDO2 token to be plugged in at boot, using systemd-udevd, and then to unlock the volume (0pointer.net, https://0pointer.net/blog/unlocking-luks2-volumes-with-tpm2-fido2-pkcs11-security-hardware-on-systemd-248.html, weight 0.897). Waiting via udevd matters for test design: the unlock path must tolerate a token that appears late, which is exactly the situation a CI VM with a hotplugged emulated token reproduces.

The crypttab man page documents the underlying mechanism: the configured key is hashed via the HMAC keyed hash function the FIDO2 device implements, so the volume key never leaves the token as plaintext and the unlock secret is derived inside the authenticator (freedesktop.org crypttab, https://www.freedesktop.org/software/systemd/man/latest/crypttab.html, weight 0.781).

## What the boot process must carry

A boot test that fails only inside the initramfs usually has an initramfs-content bug, not a cryptsetup bug. A practical report of the systemd 248 setup notes that the initramfs must contain the FIDO2 shared library and the crypttab configuration; the reporter added the FIDO2 library to the initramfs binaries list and made sure the crypttab was copied in (Arch Linux forums, https://bbs.archlinux.org/viewtopic.php?id=265134, weight 0.034, weak backing). An independent walkthrough of the YubiKey LUKS flow similarly stresses that the crypttab change alone is insufficient without the matching initramfs regeneration step, and describes solving an unknown fido2-device error before installing the initramfs generator (Guy Rutenberg blog, https://www.guyrutenberg.com/2022/02/17/unlock-luks-volume-with-a-yubikey/, weight 0.809). For distros using initramfs tooling, regenerating the image after enrollment is part of the tested sequence, not a side effect (GoLinuxCloud tutorial, https://www.golinuxcloud.com/systemd-cryptenroll-luks2-tpm2-fido2-linux/, weight 0.228, weak backing).

An alternative boot-time implementation exists outside systemd: fido2luks unlocks LUKS volumes at boot using a FIDO2 token and initramfs-tools, built directly on the hmac-secret extension (GitHub fido2luks, https://github.com/bertogg/fido2luks, weight 0.926). Its existence is useful to a test design as a contrast case: the systemd path is header-metadata driven, the fido2luks path is script driven, and only the first is what a systemd-based image test should exercise.

## The boot-side contract a test asserts

The systemd unlock contract has three observable stages at boot. First, the LUKS2 header is parsed and the FIDO2 token entry is located (0pointer.net, https://0pointer.net/blog/unlocking-luks2-volumes-with-tpm2-fido2-pkcs11-security-hardware-on-systemd-248.html, weight 0.897). Second, the token presence is awaited through udev rather than polled directly, so a missing token should produce a wait-and-timeout behavior rather than an immediate fallback to passphrase prompting in a headless CI run (0pointer.net, https://0pointer.net/blog/unlocking-luks2-volumes-with-tpm2-fido2-pkcs11-security-hardware-on-systemd-248.html, weight 0.897). Third, the derived secret is used as the volume key, which means a successful boot to a mounted root filesystem is the end-to-end assertion, and a serial console showing the mount of the encrypted device is the primary evidence artifact a CI harness collects (freedesktop.org crypttab, https://www.freedesktop.org/software/systemd/man/latest/crypttab.html, weight 0.781).

## Failure taxonomy for the boot leg

From the sources above, the recurring failure classes a boot test should distinguish are: a token the system cannot see because the emulated or passed-through device never registers with the guest udev, an initramfs missing the FIDO2 library so the token entry cannot be processed, and a crypttab option that does not match the enrolled header metadata (Arch Linux forums, https://bbs.archlinux.org/viewtopic.php?id=265134, weight 0.034, weak backing; Guy Rutenberg blog, https://www.guyrutenberg.com/2022/02/17/unlock-luks-volume-with-a-yubikey/, weight 0.809). The first is a harness problem, the second an image problem, the third an enrollment problem, and the test log should be able to tell them apart. The strongest sources here are the upstream documentation and the announcement post; the initramfs-contents details come from community reports and are marked weak.
