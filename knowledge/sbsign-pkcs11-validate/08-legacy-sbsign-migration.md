# Legacy sbsign and the migration to systemd-sbsign

Scope: why documentation converges on systemd-sbsign, what the legacy sbsign engine path cost, and how historical usage is preserved as ADR context instead of being silently dropped.

## The two tools and their overlap

The legacy tool: sbsign, from the sbsigntools project, signs UEFI Secure Boot binaries and pairs with sbverify for verification (sbverify documented at https://man.archlinux.org/man/extra/sbsigntools/sbverify.1.en, jev weight 0.8842). The modern tool: systemd-sbsign, which signs PE binaries for EFI Secure Boot and exposes the key source through `--private-key=` plus `--private-key-source=` as a "type:name" tuple such as "engine:pkcs11" or "provider:pkcs11" (source: https://www.freedesktop.org/software/systemd/man/latest/systemd-sbsign.html, jev weight 0.9575). The overlapping job is signing a PE binary for Secure Boot; the difference is which OpenSSL integration layer each reaches and how the PKCS#11 key is addressed.

## What the legacy engine path cost

The legacy sbsign path with `--engine pkcs11` routes through OpenSSL's engine layer via libp11, and that path carries a fully documented production regression. On Ubuntu 24.04 (noble), sbsign and any tool using the OpenSSL PKCS#11 engine failed when signing files via a PKCS#11 token, tracked as Launchpad bug 2158304 (source: https://bugs.launchpad.net/ubuntu/+source/libp11/+bug/2158304, jev weight 0.8826). The root cause: a regression introduced in OpenSSL commit 2b74e75 (shipped in 3.0.12) and fixed in commit 39ea783, not backported to the 3.0.x series in noble (source: https://lists.ubuntu.com/archives/foundations-bugs/2026-July/550383.html, jev weight 0.8135). The mechanism: PKEY_CRYPTO operations for the engine and instance were routed through the legacy RSA_sign path rather than the EVP_PKEY path, and the fix rerouted them (source: https://www.mail-archive.com/ubuntu-bugs@lists.ubuntu.com/msg6288165.html, jev weight 0.6263). The distribution-level fix shipped as libp11 0.4.12-1.1ubuntu1 with a patch adding an OpenSSL version check in `load_privkey()` and calling `ENGINE_set_default_string(engine, "PKEY_CRYPTO")` (source: https://www.mail-archive.com/ubuntu-bugs@lists.ubuntu.com/msg6298806.html, jev weight 0.5718).

Independent evidence that the legacy path is fragile comes from other token ecosystems: a Nitrokey NetHSM user reported the pkcs11 module crashing inside sbsign (weak backing; source: https://support.nitrokey.com/t/pkcs11-module-crashing-with-sbsign/6852, jev weight 0.3855), and a DigiCert integration guide documents configuring OpenSSL specifically to make PKCS#11 signing work with the engine stack (weak backing; source: https://docs.digicert.com/en/software-trust-manager/client-tools/signing-tools/third-party-signing-tool-integrations/configure-openssl-for-signing-with-pkcs11.html, jev weight 0.4794). None of these failures were reported against systemd-sbsign's provider path, though absence of reports is not proof of absence.

## The convergence

Documentation has converged on the modern tool for UKI workflows: ukify combines kernel, initrd, and the systemd-stub UEFI stub into a single PE binary, which systemd-sbsign then signs (source: https://www.freedesktop.org/software/systemd/man/ukify.html, jev weight 0.8493), and the UKI is a single executable booted directly from UEFI firmware or sourced by bootloaders with little or no configuration (source: https://wiki.archlinux.org/title/Unified_kernel_image, jev weight 0.6344). mkosi's own tool selection can still pick the legacy binary: if set to auto, either systemd-sbsign or sbsign are used if available (source: https://github.com/systemd/mkosi/blob/main/mkosi/resources/man/mkosi.1.md, jev weight 0.7430), which is exactly why docs must pin the modern tool rather than rely on auto-detection.

## The yubiOS consistency rule

yubiOS's rule is explicit: keep build docs on systemd-sbsign; do not reintroduce legacy `sbsign --engine pkcs11` examples except as historical context in ADR-008 (source: https://github.com/yubi-OS/yubiOS/blob/main/refs/sbsign-pkcs11-validate-2026-07-23.md, jev weight 0.5970). The rule has two halves that both matter. The forward half: every signing example in build documentation uses the systemd-sbsign interface, so a reader never re-derives the legacy path and its version sensitivities (the noble regression above is the concrete cost). The preservation half: the legacy form is not erased, it is quarantined in ADR-008 as historical context, which is where the decision record for moving off it lives. The migration pattern is therefore not "delete the old examples" but "move them behind an ADR boundary so the history stays auditable while the active docs stay on one interface".

## What carries over unchanged

One part of the recipe is tool-independent: verification. `osslsigncode verify` against the signed artifact corroborates the PE signature regardless of which tool signed it (source: https://github.com/yubi-OS/yubiOS/blob/main/refs/sbsign-pkcs11-validate-2026-07-23.md, jev weight 0.5970), and sbverify remains the UEFI-native verification tool for either signer's output (source: https://man.archlinux.org/man/extra/sbsigntools/sbverify.1.en, jev weight 0.8842). The migration is about the signing interface only; the trust chain, the certificate, and the verification recipe are shared between both eras.
