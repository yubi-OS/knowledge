# Cross-version token traps: engine, provider, and the noble regression

Scope: the versioning traps that break a PKCS#11 signing chain across OpenSSL 3's engine/provider split, p11-kit's coordinating role, and one fully documented production regression in the sbsign path.

## The engine/provider split is the primary trap

OpenSSL carries two parallel mechanisms for reaching external tokens. Engines have a long history of providing new algorithms, but they can also interface external crypto tokens such as PKCS#11, or key managers (weak backing; source: https://blog.hansenpartnership.com/converting-engines-to-openssl-3-providers/, jev weight 0.2001). OpenSSL 3's provider layer is the successor: the pkcs11 provider allows applications linked to OpenSSL to use keys and cryptographic operations from a hardware or software token via their PKCS#11 driver and the use of pkcs11 URIs (weak backing; source: https://www.mankier.com/7/provider-pkcs11, jev weight 0.4118). The standalone provider project states it targets PKCS#11 version 3.2 but is backwards compatible to versions 3.1, 3.0 and 2.40 (weak backing; source: https://github.com/openssl-projects/pkcs11-provider, jev weight 0.2928). A module that predates 3.2 still works through the provider, but the version matrix is something to check, not assume.

systemd-sbsign sits on top of this split and exposes it directly: `--private-key-source=engine:pkcs11` versus `--private-key-source=provider:pkcs11` selects which layer receives the URI (source: https://man.archlinux.org/man/systemd-sbsign.1.en, jev weight 0.8022). A signing flow that works under the engine form can fail under the provider form and vice versa, because the two layers resolve the URI and negotiate mechanisms differently. This is why the yubiOS docs pin one form and forbid drifting between them (source: https://github.com/yubi-OS/yubiOS/blob/main/refs/sbsign-pkcs11-validate-2026-07-23.md, jev weight 0.5970).

## The documented regression: Ubuntu noble, sbsign, libp11

The best-evidenced cross-version trap in this dig is a real production failure. Users on Ubuntu 24.04 (noble) who attempted to sign files via a PKCS#11 token through sbsign, and any tool using the OpenSSL PKCS#11 engine, hit a failure tracked as Launchpad bug 2158304 (source: https://bugs.launchpad.net/ubuntu/+source/libp11/+bug/2158304, jev weight 0.8826). The root cause analysis: a regression introduced in OpenSSL commit 2b74e75 (shipped in 3.0.12) and fixed in OpenSSL commit 39ea783, which was not backported to the 3.0.x series in noble; libp11 0.4.13 in plucky carried the fix forward (source: https://lists.ubuntu.com/archives/foundations-bugs/2026-July/550383.html, jev weight 0.8135).

The failure mode is precise: the problem was that PKEY_CRYPTO operations for the engine plus instance were being routed through the legacy RSA_sign path rather than the EVP_PKEY path; the fix reroutes all PKEY_CRYPTO operations for the engine and instance through the EVP_PKEY path (source: https://www.mail-archive.com/ubuntu-bugs@lists.ubuntu.com/msg6288165.html, jev weight 0.6263). The shipped workaround is instructive as a pattern: because the 0.4.12 version did not contain an existing `if` condition that the fix extends, the backported patch adds an OpenSSL version check in `load_privkey()` and calls `ENGINE_set_default_string(engine, "PKEY_CRYPTO")` (source: https://www.mail-archive.com/ubuntu-bugs@lists.ubuntu.com/msg6288038.html, jev weight 0.6042). The noble package that carries it is libp11 0.4.12-1.1ubuntu1, whose changelog entry is `d/p/pkcs11-engine-openssl3-load-privkey-segfault-workaround.patch` (source: https://www.mail-archive.com/ubuntu-bugs@lists.ubuntu.com/msg6298806.html, jev weight 0.5718).

Generalizable lesson: an OpenSSL point-release can break the engine path for PKCS#11 signing without any change in the token, the module, or the signing tool. When a previously green signing job suddenly fails, the OpenSSL package version is a first-class suspect, and the engine path has more legacy-route sensitivity than the provider path.

## libp11 and p11-kit: the layers in between

libp11 is the PKCS#11 wrapper library that sbsign's engine path goes through (source: https://github.com/OpenSC/libp11, jev weight 0.8076). Above it, p11-kit coordinates the use of PKCS#11 by different components or libraries living in the same process, providing module loading and enumeration plus a standard proxy module (source: https://github.com/p11-glue/p11-kit, jev weight 0.6812). OpenSC's own wiki documents how `pkcs11-tool` and OpenSSL combine against a module (source: https://github.com/OpenSC/OpenSC/wiki/Using-pkcs11-tool-and-OpenSSL, jev weight 0.7605). A cross-version trap at this layer: the same PKCS#11 URI can resolve differently depending on whether the application reaches the module directly or through the p11-kit proxy, because the proxy re-exports the token set of every registered module.

## What the traps look like in practice

Crash-class failures at module load are real and cross-project: a Nitrokey NetHSM user reported the pkcs11 module crashing inside sbsign (weak backing; source: https://support.nitrokey.com/t/pkcs11-module-crashing-with-sbsign/6852, jev weight 0.3855), which shows that a module binary itself can be the unstable element independent of OpenSSL version. When triaging a signing failure, the ordering that matches the evidence base above: confirm the module registers with p11-kit (doc 02), confirm the URI resolves via a read-only listing such as storeutl (doc 03), then compare the OpenSSL version against the module and the engine/provider path in use. The noble regression is the worked example of why the version comparison is not optional.
