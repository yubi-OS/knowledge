# yubiOS Boot Chain and UKIs

**Corpus:** knowledge/yubios · **Doc:** 03-boot-chain-and-ukis.md · **Authored:** 2026-09-29

yubiOS's boot chain answers one question before any user code runs: is this kernel and this root filesystem exactly what the project built and signed, or has something been swapped, patched, or tampered with along the way? It protects that answer with a layered integrity model. At the top, a Unified Kernel Image (UKI) bundles kernel, initrd, kernel command line, and identity data into one PE binary signed at build time with the owner's YubiKey, so firmware Secure Boot covers the whole bundle, not a bare kernel plus mutable bootloader config ([docs/ADR.md](https://github.com/yubi-OS/yubiOS/blob/main/docs/ADR.md), ADR-002). Inside the UKI, the command line pins the root's cryptographic digest, so the kernel cannot be tricked into mounting a modified userspace tree. At mount time, dm-verity on /usr and composefs' fs-verity digest catalog verify every block and every file against that digest. The whole chain rests on the YubiKey 5 series as the sole trust anchor: user-generated keys, no OEM trust chain, no TPM chip ([docs/ADR.md](https://github.com/yubi-OS/yubiOS/blob/main/docs/ADR.md), ADR-001).

## Layer 1: UKI signing via YubiKey PIV slot 9c

Secure Boot signing needs an asymmetric key with a certificate that firmware can enroll in its `db`. yubiOS uses YubiKey PIV slot 9c (Digital Signature) through PKCS#11 over CCID, explicitly not FIDO2 over hidraw: neither `sbsign` nor `systemd-sbsign` natively wraps a signing key through FIDO2 HMAC-secret, while PIV/PKCS#11 is directly supported by every signing tool ([docs/ADR.md](https://github.com/yubi-OS/yubiOS/blob/main/docs/ADR.md), ADR-002). The consequence is operational: users need `pcscd` running for PIV operations, enabled with `ykman config usb --enable FIDO --enable CCID` (ADR-002).

The signing tool is `systemd-sbsign`, not legacy `sbsigntools`. It was added in systemd v257 (Dec 2024), ships inside the systemd tree, co-develops with `ukify` and the UKI pipeline, and generates and verifies PCR 11 signatures (`--pcr-private-key` / `--pcr-public-key`) alongside the Secure Boot signature in one step ([docs/ADR.md](https://github.com/yubi-OS/yubiOS/blob/main/docs/ADR.md), ADR-008; upstream docs at https://www.freedesktop.org/software/systemd/man/latest/systemd-sbsign.html). It requires systemd >= 257; the yubiOS base is pinned to systemd v261 per ADR-015/ADR-016, with [PINNED.md](https://github.com/yubi-OS/yubiOS/blob/main/PINNED.md) as the digest and package-floor source of truth. The repo keeps a documented validation shape: `systemd-sbsign sign --private-key "pkcs11:manufacturer=piv_II;id=%9c;type=private" --private-key-source engine:pkcs11 --certificate /etc/yubico/sb-cert.pem`, corroborated by `osslsigncode verify`; a physical YubiKey remains required for final production signing validation ([refs/sbsign-pkcs11-validate-2026-07-23.md](https://github.com/yubi-OS/yubiOS/blob/main/refs/sbsign-pkcs11-validate-2026-07-23.md)).

The build configuration mirrors this. `mkosi.conf` sets `Format=disk` with `SplitArtifacts=uki,partitions`, `SecureBoot=yes`, `SignExpectedPcr=no`, and a kernel command line of `root=dissect mount.usr=dissect rw audit=0` ([mkosi.conf](https://github.com/yubi-OS/yubiOS/blob/main/mkosi.conf)). The `SecureBootKey` is a PKCS#11 URI; the signing path runs through mkosi's `--secure-boot-key-source provider:pkcs11 --secure-boot-sign-tool systemd-sbsign`, and mkosi upstream v27 confirms native support for `SecureBootKeySource=engine:pkcs11` / `provider:pkcs11` via `systemd-sbsign` ([refs/sbsign-pkcs11-validate-2026-07-23.md](https://github.com/yubi-OS/yubiOS/blob/main/refs/sbsign-pkcs11-validate-2026-07-23.md)).

## Kernel+rootfs split: the UKI is a first-class artifact

yubiOS treats the kernel as a separately published artifact. Under ADR-032 (kernel+rootfs split as a first-class principle) and OMN-51, `ci_mkosi-installer.yml` builds the signed UKI anchored to a SoftHSM token standing in for PIV slot 9c, and `Containerfile.uki` packages it as a tiny OCI artifact containing `/usr/lib/yubiOS/uki/yubios.efi`, the signing cert, and a `MANIFEST.txt`. The `yubios-uki` bake target publishes it as `0mniteck/yubios:uki-<sha>-<arch>` under ADR-022's per-artifact tag scheme ([Containerfile.uki](https://github.com/yubi-OS/yubiOS/blob/main/Containerfile.uki)). Phase 2 of the split (install-time handler wiring the UKI into bootc's BLS entries) is deferred: bootc 1.16.3 has no BLSConfig drop-in intake for project-authored `.conf` files ([Containerfile.uki](https://github.com/yubi-OS/yubiOS/blob/main/Containerfile.uki)).

## SoftHSM in CI: emulating PIV slot 9c

CI has no physical YubiKey, so a SoftHSM token labeled `yubiOS-ci` emulates PIV slot 9c. The sealed-UKI workflow's canonical sequence: import a PKCS#8 key with `softhsm2-util --import /tmp/sb.p8 --token yubiOS-ci --label sb-key --id 0102 --pin 1234`, set `PKCS11_PROVIDER_MODULE=/usr/lib64/libsofthsm2.so`, then sign with `/usr/lib/systemd/systemd-sbsign sign --private-key-source=provider:pkcs11 --private-key='pkcs11:token=yubiOS-ci;object=sb-key;type=private?pin-value=1234' --certificate=/output/pki/sb.crt` ([.github/workflows/ci_test_sealed-uki-vm.yml](https://github.com/yubi-OS/yubiOS/blob/main/.github/workflows/ci_test_sealed-uki-vm.yml)). Note the backend spelling: the workflow uses `provider:pkcs11`, not `engine:pkcs11`; `systemd-sbsign` is not a separate dnf package on rawhide, it ships inside the main systemd package at `/usr/lib/systemd/systemd-sbsign` (workflow comments, V26 revision). The debug playbook records the hard-won constraints: never cross-mount SoftHSM token dirs between host and container (cross-version BDB token files are unreadable, giving `Input/output error`), and pin `pkcs11-provider >= 1.2.0` because SoftHSM 2.7.0's hashed-ECDSA mechanisms are single-part only, which breaks pkcs11-provider's streamed signing; kryoptic is the fallback token ([playbooks/sealed-uki-vm-debug.md](https://github.com/yubi-OS/yubiOS/blob/main/playbooks/sealed-uki-vm-debug.md)).

## The sealed-UKI Secure Boot VM test lane

`ci_test_sealed-uki-vm.yml` (parent issue OMN-53, spec in [refs/sealed-uki-vm-test-2026-07-30.md](https://github.com/yubi-OS/yubiOS/blob/main/refs/sealed-uki-vm-test-2026-07-30.md)) is the e2e proof that the chain actually enforces, not just builds. It runs three jobs on fresh GitHub-hosted runners, arch-matrixed amd64/arm64:

- **build-and-verify-uki** builds the UKI via `bootc container ukify` (a bootc 1.16.6+ capability, probed and verified by `ci_test_bootc-filesystem.yml` run #11 at `7eba4856e7`), signs via `systemd-sbsign` with the SoftHSM PKCS#11 backend, then verifies with `osslsigncode` (sbverify dropped per ADR-008), asserts UKI structure (`.cmdline` + `.linux` + `.initrd`), and asserts the composefs fs-verity digest is sealed in the `.cmdline` section ([.github/workflows/ci_test_sealed-uki-vm.yml](https://github.com/yubi-OS/yubiOS/blob/main/.github/workflows/ci_test_sealed-uki-vm.yml)). A documented nuance: bootc's ukify path embeds a `composefs=<sha512>` fs-verity digest karg (with optional `?` prefix meaning allow-missing-fsverity), not a dm-verity `roothash=`; the `roothash=` expectation belongs to the separate mkosi dm-verity lane (workflow comments, V81).
- **boot-secure-vm** boots the signed UKI in QEMU with Secure Boot firmware. On amd64 that is `OVMF_CODE_4M.secboot.fd` with the CI cert enrolled as PK/KEK/db via `virt-fw-vars`, asserting `systemd-stub` reports Secure Boot enabled on the serial console. On arm64 it is `AAVMF`: the workflow deliberately uses `AAVMF_CODE.secboot.fd`, because Debian's `AAVMF_CODE.fd` is a symlink to the no-secboot build with Secure Boot compiled out ([.github/workflows/ci_test_sealed-uki-vm.yml](https://github.com/yubi-OS/yubiOS/blob/main/.github/workflows/ci_test_sealed-uki-vm.yml)). The arm64 leg is a **differential proof**: positive leg boots the signed UKI with our cert in `db` and must reach `Booting Linux`; negative leg boots the identical UKI with a foreign self-signed cert enrolled and must NOT reach `Booting Linux`. This is strictly stronger than string-matching, because the x86 kernel string `secureboot: Secure boot enabled` can never appear on arm64, so an assertion built on it would pass vacuously (workflow comments, V79).
- **negative-tamper-tests** (amd64 only): Negative 1 flips one byte in the signed UKI and asserts the signature verify rejects it (implemented). Negative 2, tampering the `composefs=<sha512>` BLS entry so dm-verity refuses the mount, is deferred to a separate e2e lane per user decision. Negative 3 boots the signed UKI under a foreign `db` and asserts firmware refuses it (implemented) (workflow comments).

What the lane deliberately does not prove: the yubiOS-side install wiring (BLS entries still point at the composefs-blessed kernel, not the signed UKI, pending OMN-150 Phase 2), real YubiKey PIV 9c in CI, and ARM64 Secure Boot on RK3588 hardware (tracked under OMN-141 / B-REAL-FIDO2) ([refs/sealed-uki-vm-test-2026-07-30.md](https://github.com/yubi-OS/yubiOS/blob/main/refs/sealed-uki-vm-test-2026-07-30.md)).

## dm-verity on /usr and the composefs catalog

The load-bearing invariant: **/usr is dm-verity-verified at every boot**. dm-verity computes a Merkle tree over /usr's blocks; the root hash rides in the UKI command line, so tampering is detected before any userspace runs. /etc, /var, and /home are mutable and protected by other means (fs-verity, IMA) ([skills/dm-verity-and-integrity/SKILL.md](https://github.com/yubi-OS/yubiOS/blob/main/skills/dm-verity-and-integrity/SKILL.md)). ADR-007 specifies the mkosi path: composefs over a dm-verity-checked EROFS partition, `Verity=signed` in mkosi.conf, `Type=root` + `Verity=data` plus a matching `Type=root-verity` in systemd-repart's `50-yubiOS-root.conf`, and dracut modules `composefs dm-verity` in `51-yubiOS-composefs.conf` ([docs/ADR.md](https://github.com/yubi-OS/yubiOS/blob/main/docs/ADR.md), ADR-007).

The bootc path composes differently: native bootc composefs stores content in an fs-verity-capable ext4/Btrfs sysroot with a metadata-only EROFS image under `/composefs/images/<digest>` and objects under `/composefs/objects`. Sealing there is two-factor: strict fs-verity alone is not sealing; the composefs digest must also be authenticated by the signed UKI command line. `composefs=?...` (allow-missing-verity) encodes an explicitly unsealed reference, and CI rejects it ([refs/bootc-composefs-sealed-flow-2026-07-22.md](https://github.com/yubi-OS/yubiOS/blob/main/refs/bootc-composefs-sealed-flow-2026-07-22.md)).

## Measured boot posture

The spec scopes PCR measurement handoff with golden-value assertions against `tpm2_pcrread sha256:0,1,2,3,4,7,11`: PCR0 initial state, PCR4 UKI cmdline plus initrd, PCR7 Secure Boot policy, PCR11 initrd measurements; AMD64 CI uses a swtpm-backed fTPM, and ARM64 applies the `ftpm-optee-tpm` skill ([refs/sealed-uki-vm-test-2026-07-30.md](https://github.com/yubi-OS/yubiOS/blob/main/refs/sealed-uki-vm-test-2026-07-30.md)). On the systemd side, v261 supplies `systemd-tpm2-swtpm.service` for CI TPM emulation and `ConditionSecurity=measured-os` so enrollment and first-boot validation units refuse to run on an unmeasured boot; bcvk attaches the vTPM host-side through QEMU `swtpm` with `-tpmdev emulator` and arch-aware `tpm-tis`/`tpm-crb` devices, since DirectBoot cannot rely on an in-guest service for `/dev/tpm0` ([docs/ADR.md](https://github.com/yubi-OS/yubiOS/blob/main/docs/ADR.md), ADR-016). yubiOS itself keeps YubiKey FIDO2 for secrets; the TPM is a measurement substrate, not a secret store (ADR-016). `SignExpectedPcr=no` in mkosi.conf means expected-PCR prediction is off; the posture is measure-and-attest rather than precompute-and-seal against fixed PCR values ([mkosi.conf](https://github.com/yubi-OS/yubiOS/blob/main/mkosi.conf)).

## Kernel version floors for composefs

composefs depends on specific kernel features at specific floors, and yubiOS picks the lowest-supported kernel that carries the full feature set needed ([skills/composefs-kernel-floors/SKILL.md](https://github.com/yubi-OS/yubiOS/blob/main/skills/composefs-kernel-floors/SKILL.md)):

| Floor | Feature | Why it matters |
|---|---|---|
| >= 6.5 | Data-only OverlayFS | composefs's primary backing fs. Without 6.5, composefs falls back to a writable upper layer and the mounted /usr is mutable, breaking the invariant. |
| >= 6.6 | `verity=require` | Mount-time enforcement that the composefs catalog is trusted. Without 6.6 the catalog is informational only: the kernel mounts an unsigned layer. |
| >= 6.12 | File-backed EROFS | The alternate composefs backing fs, denser than Squashfs, used for high-density sysext images. Block-device EROFS works on older kernels but is not how composefs composes layers. |

The convention in force (2026-08, per the skill): production yubiOS targets kernel >= 6.12, LTS >= 6.6, experimental >= 6.5. A kernel older than 6.5 cannot use composefs at all and must fall back to the pre-composefs dm-verity-only path that ADR-007 explicitly discourages ([skills/composefs-kernel-floors/SKILL.md](https://github.com/yubi-OS/yubiOS/blob/main/skills/composefs-kernel-floors/SKILL.md)).
