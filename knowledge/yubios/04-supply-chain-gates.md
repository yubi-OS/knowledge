# Supply Chain Gates

yubiOS's build pipeline is attacked the same way every container-based OS is attacked: a mutable tag changes under a build, an unapproved base image enters the trust chain, an unsigned artifact gets published, and no one can later prove which inputs produced the bytes that boot. The defense is layered so that each gate catches what the previous one cannot. Layer 1 pins every input by content address. Layer 2 vets every build input with an OPA/Rego policy before any layer executes. Layer 3 makes the build itself deterministic and proves it with two-build comparison. Layer 4 attaches verifiable attestations and signatures to every published artifact, with a SLSA v1.0 Build L3 target and a Rekor v2 transparency-log posture defined in a dated integration spec. Sources: [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md), [yubiOS.rego](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/yubiOS.rego), [refs/reproducible-builds-2026-07-22.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/refs/reproducible-builds-2026-07-22.md), [refs/slsa-l3-sbom-cosign-integration-spec-2026-08-04.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/refs/slsa-l3-sbom-cosign-integration-spec-2026-08-04.md).

## Layer 1: Digest-pinned inputs

The base image is `quay.io/fedora/fedora-bootc`, pinned by SHA256 digest under ADR-015. Mutable tags (`:latest`, `:45`) are explicitly forbidden without a digest suffix: a digest is content-addressed and immutable, which is the precondition for both reproducibility and policy compliance. The current digest lives in [PINNED.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/PINNED.md), the single source of truth. ADR text explicitly warns that historical digests embedded in ADRs are not current pins (amendments dated 2026-07-07 and 2026-07-11). The bump policy requires that every new digest still ships the required floors, including the systemd target, pam-u2f >= 1.3.1, and OpenSSL 3.5+. Source: [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md) (ADR-015).

Pinning does not stop at the base image. ADR-030 requires that GitHub Actions are pinned to full commit SHAs, container bases to OCI digests, source checkouts to immutable commit refs, and downloaded tools to a reviewed version plus checksum. A workflow must fail rather than silently fall back to a moving tag, branch, unsigned download, faked firmware blob, or unverified alternate source. Source: [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md) (ADR-030, item 6).

## Layer 2: Docker Build Policies (yubiOS.rego)

[yubiOS.rego](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/yubiOS.rego) is the OPA/Rego policy evaluated by Docker Buildx's Build Policies feature, invoked as `docker buildx build --policy reset=true,strict=true,filename=yubiOS.rego`. It is default-deny (`default allow := false`) and vets every build input before any layer executes: violations fail the build immediately, so nothing is pulled or built.

The policy enforces three rules. Rule 1 passes pure local builds that never pull a `FROM`. Rule 2 requires that every external image reference comes from an approved registry AND is canonical (`input.image.isCanonical`, i.e. digest-pinned; mutable tags are rejected with a remediation message that names the `FROM ...@sha256:<hash>` form). The approved registry list is: `quay.io/fedora/` (official Fedora bootc images), `dhi.io/` (Docker Hardened Images used as the pinned build tooling), `ghcr.io/actions/`, and `ghcr.io/hadolint/`. `docker.io/docker/*` is deliberately NOT blanket-approved. Rule 2.5 grants exactly one narrow carve-out: `docker.io/docker/buildkit-syft-scanner:stable-1`, pulled internally by BuildKit during the SBOM attestation pass, never landing in a runtime image. Any future BuildKit-internal helper needs its own explicit exception, per the narrow-by-default doctrine. Rule 3, requiring provenance on all base images (`input.image.hasProvenance`), exists in the policy but is commented out until `quay.io/fedora/fedora-bootc` ships provenance upstream. Source: [yubiOS.rego](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/yubiOS.rego).

The policy runtime is not incidental. ADR-014 selects rootless Docker Buildx as the sole container build runtime and removes Podman from the build dependency chain, precisely because Build Policies are a Buildx feature with no Buildah equivalent, and because one runtime means one audit target. Buildx also emits SLSA provenance and SBOM attestations natively via `--attest type=provenance,mode=max` and `--attest type=sbom`. Source: [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md) (ADR-014).

## Layer 3: The reproducible build substrate

ADR-030 defines the build environment as one indivisible pattern: a digest-pinned Docker Hardened Image (DHI) job container (privileged outer boundary, the Docker-in-Docker line), a checksum-pinned Docker CLI plus rootless dockerd running as an unprivileged `docker-rootless` user on a user-owned socket, an explicitly selected Buildx builder named `hardened` whose BuildKit daemon image is pinned independently of the client, and [yubiOS-bake.hcl](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/yubiOS-bake.hcl) as the only invocation path (bake owns contexts, platforms, tag families, deterministic exporter settings, and the shared policy attachment). Every Bake target must inherit the common `_policy` and `_reproducible` targets, declare its attestation boundary, and carry a policy-negative test before it counts as complete. Sources: [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md) (ADR-030), [yubiOS.rego](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/yubiOS.rego).

Pinning is necessary but not sufficient, and ADR-030 says so: package repository state, timestamps, compression, and generated metadata can still vary. The executable contract is in [refs/reproducible-builds-2026-07-22.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/refs/reproducible-builds-2026-07-22.md). The canonical build identity is the selected yubiOS commit plus its committer timestamp; `scripts/lib/reproducible-build.sh` derives that pair once and exports the same values to local builds and GitHub Actions, so a caller cannot silently assign a different `SOURCE_DATE_EPOCH` to the same revision. Bake passes `SOURCE_DATE_EPOCH` and `BUILDKIT_MULTI_PLATFORM`, fixes the OCI `created` label, clamps layer mtimes with `rewrite-timestamp`, and fixes compression and exporter settings. The proof is `scripts/verify-reproducible-images.sh`: it builds the real target twice with separate pinned builders, no cache, and no default attestations, then compares the complete unpacked OCI-layout Merkle content (transport wrappers like `docker image save` are rejected as equality oracles). Generated DNF cache, history, logs, and the regenerable `ldconfig` auxiliary cache are removed; Python bytecode uses single-worker checked-hash compilation; Rust debug paths are remapped. The mkosi installer adds an architecture-scoped deterministic seed, no incremental cache, Dracut reproducible mode, a fixed zstd worker count, normalized payload metadata, and sorted SHA-256 records. The firmware lane feeds the commit epoch into EDK2, U-Boot, and OP-TEE, gives TF-A an explicit timestamp and build string, and uses commit- and platform-scoped deterministic stack-cookie lists. Blocking two-build gates run on ARM64 (the primary architecture) for the production and TEST-only dev OCI subjects, the installer's canonical unsigned root filesystem contents and metadata, initrd, and package manifest, and firmware's StandaloneMM plus per-board unsigned components, with JSON evidence retained 30 days.

The contract is honest about boundaries: bytes that intentionally vary, such as the installer's fresh SoftHSM RSA key and certificate, the root-resident signed systemd-boot binary, signed UKI, ESP, Btrfs block serialization, the QEMU TF-A `CREATE_KEYS=1` envelope, and the RK3588 external-TPL-dependent final image, are recorded but excluded from the equality claim. Source: [refs/reproducible-builds-2026-07-22.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/refs/reproducible-builds-2026-07-22.md).

## Layer 4: Attestations, signatures, and verification

Every published OCI artifact carries BuildKit-native provenance and SBOM attestations, extracted and checked in CI via `docker buildx imagetools inspect`. The image is signed with cosign v3.1.2, installed from a SHA512-verified release download, using `cosign sign --key cosign/yubios-omni157.key --signing-config cosign/signing-config.json` and OIDC `id-token: write` declared on the job. A dedicated `verify-attest` job runs [tests/verify-oci-attestations.sh](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/tests/verify-oci-attestations.sh), which always verifies against the immutable digest, never a mutable tag, and checks four things: the local-key signature against `cosign/yubios-omni157.pub`, the cosign-attached SPDX SBOM attestation (`--type spdxjson`), the cosign-attached SLSA v1.0 provenance attestation (`--type slsaprovenance1`, requiring the SLSA `buildDefinition` to be present), and the original BuildKit attestation children on the OCI index. Sources: [.github/workflows/yubiOS-ci.yml](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/.github/workflows/yubiOS-ci.yml), [tests/verify-oci-attestations.sh](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/tests/verify-oci-attestations.sh).

Verification also runs at consume time. The boot-time GPU launch gate in ADR-030's successor rules requires that a bootc image's digest matches a pinned reference AND its SLSA provenance verifies against the expected builder-id before any libvirt-class launcher may attach a PCI GPU to a yubiOS guest, enforced software-only, proven end to end by a `YUBIOS_ATTESTED=1` CI leg. Source: [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md) (GPU trust-boundary rules 1-7).

## SLSA v1.0 Build L3 target

The integration spec under OMN-157 ("yubiOS Production Proof & Release Gates", filed 2026-08-01 from PR #156 / commit `3e74579c8e50`) sets the target: SLSA v1.0 Build L3, SPDX 2.3 JSON SBOMs, cosign-signed attestations, and Rekor v2 entries, across `yubiOS-ci.yml`, `ci_mkosi-installer.yml`, and `ci_dev_image.yml`, plus a new `ci_attestation-verify.yml` verifier gate downstream consumers can re-run independently. Two framing facts are load-bearing. First, SLSA v1.0's Build track runs L1 to L3 only; there is no Build L4, and source-track requirements (two-person review, retention, versioned history) are a separate track, not a level. Second, L3's distinguishing requirement is a hardened, isolated builder the tenant project cannot tamper with; on GitHub Actions the canonical path is the `slsa-framework/slsa-github-generator` reusable workflows (v2.1.0 in the spec), which build on isolated GitHub-hosted runners. Source: [refs/slsa-l3-sbom-cosign-integration-spec-2026-08-04.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/refs/slsa-l3-sbom-cosign-integration-spec-2026-08-04.md).

## Rekor v2 posture

The project's transparency-log posture targets Sigstore Rekor v2: a tile-backed, hash-only log with sharded inclusion proofs, per-tile checkpoints signed by a witness quorum (no single global root, so one witness compromise invalidates at most one tile), and TUF SigningConfig-driven endpoint discovery. The yubiOS integration path is publishing artifact attestations to a Rekor v2 tile and verifying with `cosign verify-attestation --rekor-tiles`; the spec's cross-cutting gap G-X-3 requires refreshing the TUF metadata cache on every CI run to avoid rotation-related failures. Source: [skills/docker-build-policy/../sigstore-rekor-v2/SKILL.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/skills/), [refs/slsa-l3-sbom-cosign-integration-spec-2026-08-04.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/refs/slsa-l3-sbom-cosign-integration-spec-2026-08-04.md).

## Open items

- Keyless OIDC cosign signing and Rekor v2 transparency-log entries are a post-launch follow-up. The current implementation is key mode: `cosign/signing-config.json` intentionally contains no `rekorTlogUrls`, so verification uses `--insecure-ignore-tlog` with `--key`. Source: [tests/verify-oci-attestations.sh](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/tests/verify-oci-attestations.sh).
- The L3 isolation gap is open: the release workflows build on rootless dockerd in the runner, not the isolated `slsa-github-generator` runners the OMN-157 spec requires (the spec's gap rollup counts this as the single biggest behavioral change; the spec is the Specify-phase output with Plan and Task phases deferred to follow-up tickets). Sources: [refs/slsa-l3-sbom-cosign-integration-spec-2026-08-04.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/refs/slsa-l3-sbom-cosign-integration-spec-2026-08-04.md), [.github/workflows/yubiOS-ci.yml](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/.github/workflows/yubiOS-ci.yml).
- Rule 3 (`input.image.hasProvenance`) in [yubiOS.rego](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/yubiOS.rego) stays commented out until `quay.io/fedora/fedora-bootc` ships provenance.
