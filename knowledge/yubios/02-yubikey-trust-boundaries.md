# YubiKey Trust Boundaries: One Owner-Held Root of Trust, Five Boundaries

yubiOS replaces the TPM with the owner's YubiKey at every trust boundary that matters to a machine owner. A TPM is soldered to the board, provisioned by whoever built the machine, and invisible to most people who own one [README.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/README.md), [MISSION.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/MISSION.md). A YubiKey is a $25 to $70 device the owner physically holds, generated keys on, and can pull out of the USB port [MISSION.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/MISSION.md). This doc enumerates the five boundaries the YubiKey anchors in yubiOS: Secure Boot UKI signing via PIV slot 9c, LUKS2 full-disk unlock via FIDO2 hmac-secret, SSH authentication via FIDO2 resident keys, login and sudo via pam-u2f, and per-user home directories via systemd-homed. Its thesis, stated in every project document: No TPM. No OEM. No trust anchors you don't control [MISSION.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/MISSION.md).

## The thesis in one ADR

ADR-001 is titled "YubiKey as TPM replacement" and is Accepted status [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md). Its rationale is structural, not marketing: hardware-bound key material that travels with the user rather than the board; open specifications (FIDO2/CTAP2, PIV/PKCS#11, OATH) instead of a vendor NDA; touch required by default so nothing decrypts silently; keys generated by the user, so no OEM or manufacturer trust chain [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md). MISSION.md generalizes it: hardware roots of trust have historically sat behind enterprise contracts and OEM partnerships, and yubiOS bets that a YubiKey is a better root of trust than a TPM most people will never own or control [docs/MISSION.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/MISSION.md).

The README's trust-chain block is the whole architecture in five lines: PIV slot 9c via CCID for UKI signing, FIDO2 hmac-secret via hidraw for LUKS2 root and homed unlock, FIDO2 ed25519-sk via hidraw for SSH resident keys, FIDO2 U2F via hidraw for pam-u2f, OATH via hidraw for application 2FA [README.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/README.md).

## Boundary 1: Secure Boot, PIV slot 9c via CCID

UKI signing needs an asymmetric key whose certificate can be enrolled in the UEFI Secure Boot `db`. yubiOS uses PIV slot 9c (PIV Digital Signature) accessed over CCID through PKCS#11, and ADR-002 explicitly rejects the FIDO2/hidraw path for this boundary [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md). The signing tool is `systemd-sbsign` with a `pkcs11:` key URI, which needs systemd v257 or newer; the yubiOS base image is pinned to systemd v261 per ADR-015 and ADR-016 [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md). Users need `pcscd` running and both FIDO2 and CCID USB interfaces enabled on the key (`ykman config usb --enable FIDO --enable CCID`) [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md).

Why not FIDO2 for signing: FIDO2 hmac-secret can wrap a signing key, but neither sbsigntools nor systemd-sbsign supports that path natively, while PIV/PKCS#11 is directly supported in every signing tool [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md). A fully hidraw signing path is tracked as future work in TODO.md [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md). In practice the repo ships both patterns: the CI lane signs UKIs with a direct PKCS#11 URI against slot 9c (`SecureBootKey=pkcs11:token=yubiOS-ci;object=sb-key;type=private`, SoftHSM standing in for the key on CI) [refs/sealed-uki-vm-test-2026-07-30.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/refs/sealed-uki-vm-test-2026-07-30.md), while the on-device script `sign-uki-fido2.sh` demonstrates the wrapped-key variant: the Secure Boot private key is stored age-encrypted on disk and decrypted through a YubiKey touch at signing time, then signed with systemd-sbsign and the plaintext key is shredded [usr/lib/yubiOS/sign-uki-fido2.sh](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/usr/lib/yubiOS/sign-uki-fido2.sh). The sealed-UKI test lane defines what this boundary must prove: a tampered UKI is refused by Secure Boot, a flipped composefs digest is refused by dm-verity, and boot without the owner-enrolled ROTPK fails [refs/sealed-uki-vm-test-2026-07-30.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/refs/sealed-uki-vm-test-2026-07-30.md).

Slot discipline comes from the yubikey-operations skill: 9c is the signing root, 9a is the user-authentication root, and slots 82-95 hold generation history when 9c is rotated [skills/yubikey-operations/SKILL.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/skills/yubikey-operations/SKILL.md).

## Boundary 2: LUKS2 disk unlock, FIDO2 hmac-secret, no TPM slot

ADR-003: disk encryption is LUKS2 with `systemd-cryptenroll --fido2-device=auto`, and no TPM slot is enrolled [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md). The FIDO2 credential with the hmac-secret extension lives in the LUKS2 token header; the volume unlocks on any machine with the YubiKey, where a TPM-bound disk would be board-locked; touch is required at every boot so decryption is never silent [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md). The yubiOS PIN policy is `--fido2-with-client-pin=yes`, so every boot needs FIDO2 PIN plus touch [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md).

The deepest reason is operational, and it is its own ADR. ADR-011 records that TPM2 PCR-hash policies break on every kernel, initrd, or boot-config change, forcing re-enrollment or a distribution-maintained signed-PCR-policy infrastructure. FIDO2 hmac-secret derives a deterministic key from credential ID, salt, and PIN, independent of which OS is running, so OS updates require zero re-enrollment [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md). The recorded trade-off: FIDO2 does not verify which OS is booting before releasing the key; physical possession of the YubiKey is the protection instead [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md).

Recovery is mandatory, not optional: a `systemd-cryptenroll --recovery-key` must be enrolled alongside FIDO2, printed, and stored offline, because it is the only escape hatch if the YubiKey is lost [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md). Boot-time unlock requires the dracut `fido2` module, shipped in `usr/lib/dracut.conf.d/50-yubiOS-fido2.conf` [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md). Upstream reference: the systemd-cryptenroll manual [systemd-cryptenroll(1)](https://www.freedesktop.org/software/systemd/man/latest/systemd-cryptenroll.html). CI proves this boundary three ways: a real YubiKey on bare metal with `bcvk native-to-disk`, and two hardware-free lanes using software authenticators that are TEST-only and never ship in production images [refs/luks-fido2-e2e-test-2026-07-23.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/refs/luks-fido2-e2e-test-2026-07-23.md).

## Boundary 3: SSH, ed25519-sk resident keys

ADR-004: SSH uses `ed25519-sk` with `-O resident`, so the private key never leaves the YubiKey; only a credential ID and public-key stub sit on disk [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md). Resident keys are stored in the YubiKey's internal FIDO2 storage, `ssh-keygen -K` can regenerate the stub on a new machine from the YubiKey alone, and `-O verify-required` forces the FIDO2 PIN on every use [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md). Version floors: OpenSSH 8.2 or newer (the release that introduced FIDO2 keys), libfido2 1.10 or newer, and YubiKey firmware 5.2.3 or newer for ed25519-sk [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md), [OpenSSH 8.2 release notes](https://www.openssh.com/txt/release-8.2). The operations skill adds the naming convention `id_yubico_<algo>_<resident?>` so anyone reading `~/.ssh` can tell a key is YubiKey-backed and whether it demands touch [skills/yubikey-operations/SKILL.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/skills/yubikey-operations/SKILL.md).

## Boundary 4: Login and sudo, pam-u2f

ADR-005 pins pam-u2f at 1.3.1 or newer because of CVE-2025-23013, a partial authentication bypass in earlier versions disclosed in Yubico advisory YSA-2025-01 [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md), [YSA-2025-01](https://www.yubico.com/support/security-advisories/ysa-2025-01/). The PAM line is `auth required pam_u2f.so`, deliberately not `sufficient`, so YubiKey touch is always needed; enrolled keys are centralized in a root-owned `/etc/yubico/u2f_keys` for auditability [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md). The enrollment script creates that file with mode 600 and appends a credential via `pamu2fcfg -u <user> -N`, deferring the PIN to authentication time [usr/lib/yubiOS/enroll-pam.sh](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/usr/lib/yubiOS/enroll-pam.sh). The documented recovery path if the key is lost: boot with the `rd.break` kernel argument, mount the rootfs, comment out the pam_u2f line in `/etc/pam.d/sudo` [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md).

## Boundary 5: systemd-homed, per-user LUKS2 volumes

ADR-009 moves user data out from under system-wide FDE. Each home directory is its own LUKS2 volume unlocked by that user's own YubiKey FIDO2 credential, so one user's data is cryptographically inaccessible while the system runs but that user is not logged in [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md). systemd-homed flushes LUKS2 keys before suspend and re-authenticates the YubiKey on resume, so the key never sits in RAM during sleep [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md). Homes are portable: the LUKS2 volume migrates between machines with `homectl adopt`, and v258 added `homectl add-signing-key` and `homectl list-signing-keys` for the same purpose [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md). The operational pattern is `homectl create <user> --storage=luks --fs-type=btrfs --recovery-key --fido2-device=auto --fido2-with-client-pin=yes --fido2-with-user-presence=yes`, with btrfs required for online resize [skills/systemd-homed/SKILL.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/skills/systemd-homed/SKILL.md), [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md).

## What the YubiKey is deliberately not

yubiOS does not claim the YubiKey is a TPM. The operations skill draws the split explicitly: the YubiKey is user-held, removable, owner-controlled identity (SSH, Git signing, disk unlock, PAM, home unlock); the fTPM is platform-bound integrity attestation (PCR measurement, IMA, TPM2 quotes, measured boot), pairing with the YubiKey and never substituting for it [skills/yubikey-operations/SKILL.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/skills/yubikey-operations/SKILL.md). Where a TPM or the yubiOS-owned ARM64 fTPM exists, it adds an optional layer, such as PCR 11 phase-word sealing of the disk key against post-boot extraction, but the no-TPM configuration rests on the key being derived per-boot from the YubiKey with PIN and touch rather than stored at rest [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md). The honest gap ADR-011 records stands: possession is not measurement, and yubiOS chooses it anyway to avoid OEM and distribution trust dependencies [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md).

## One key is not a root of trust

Because the YubiKey is the sole root of trust, losing it is the failure mode the whole design must survive. ADR-001's trade-offs are explicit: a lost YubiKey means lockout without the recovery key, FIDO2 credentials are device-bound and cannot be backed up cryptographically, and a backup YubiKey should be enrolled [docs/ADR.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/docs/ADR.md). The operations skill goes further with a 2-of-3 quorum pattern (daily driver, backup in a safe, recovery key in a second location), composed at the application layer because YubiKeys have no native quorum, and a backup/restore discipline that exports the slot 9c attestation certificate before any re-enrollment [skills/yubikey-operations/SKILL.md](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/skills/yubikey-operations/SKILL.md).
