# CI and Test Infrastructure

yubiOS CI is built to prove one thing: a bootc-built, Secure-Boot-sealed, YubiKey-unlockable OS image actually boots and behaves on real ARM64 and x86_64 hardware. The proof is split by cost: cheap static lint runs on GitHub-hosted runners, full boot e2e runs in ephemeral bcvk VMs, a dedicated lane proves the PKCS#11-signed UKI boot chain under OVMF Secure Boot, and a vGPU lane proves that adding a virtual GPU changes nothing else. Coordination is deliberately dumb: one group-routing orchestrator fires independent `workflow_dispatch` events, two audit workflows police the dispatch surface, and a shared library pins every build to a reproducible epoch and seed. The `playbooks/` directory is the operator layer: runbooks written from verified failure timelines, not theory.

## Orchestrator: ci.yml group routing

`.github/workflows/ci.yml` is the top-level dispatcher ([source](https://github.com/yubi-OS/yubiOS/blob/main/.github/workflows/ci.yml)). It exposes a single `group:` choice input (none, firmware, tests, vm-tests, fetches, ci-builders, forks, audits, research, all), plus `reason` (an audit-log entry), `target_ref`, and a `Docker_push` boolean that propagates only to the four builder workflows (ci_firmware-rk, yubiOS-ci, ci_dev_image, ci_mkosi-installer); every other workflow ignores it. When dispatched with a group, it fires one independent `workflow_dispatch` per workflow in that group and exits: no state machine, no `needs:`, no callback. A 2026-07-29 redesign (PR #145) removed all path-scoped `on: push` triggers, made all 22 sibling workflows dispatch-only, and deleted the legacy `Dev_Docker_push`, `Firmware_Docker_push`, `Installer_Docker_push`, `ci_fork_run`, `ci_test_run`, and `vm_image` pass-through inputs plus the internal `ci_*` callback contract (same file, header comment; [docs/CI_MAP.md](https://github.com/yubi-OS/yubiOS/blob/main/docs/CI_MAP.md)).

The mapping lives in the `case` statement, and the header comment lags it: the comment's `tests` group lists 3 workflows, but the code dispatches 8 (`ci_test_rootless-docker.yml`, `ci_test_bootc-filesystem.yml`, `ci_test_pq_tls_verify.yml`, `ci_test-bootc-lifecycle.yml`, `ci_test-sysext-portable.yml`, `ci_test-fedora-bootc-arm64-pull.yml`, `ci_test-ftpm-tpm0.yml`, `diag_sign-matrix.yml`), and the code's `vm-tests` group contains 3 lanes while both the comment and the CI_MAP table list 2 (verified against the file 2026-09-29). The full dispatch surface is 39 workflow files in `.github/workflows/` (GitHub Contents API listing, verified 2026-09-29). `docs/CI_MAP.md` is regenerated on merge and remains the declared source of truth for group membership, but drift between it, the `ci.yml` comment, and the `case` code is real: `ci_test-ftpm-tpm0.yml`, `ci_test-fedora-bootc-arm64-pull.yml`, and `ci_test-vgpu-vm.yml` are documented as being in no group at all, so `group=all` silently misses them ([playbooks/dispatch-chain-verification.md](https://github.com/yubi-OS/yubiOS/blob/main/playbooks/dispatch-chain-verification.md), Gap 9).

## The asymmetric dispatch schema problem

Every sub-workflow owns a different dispatch schema, and the orchestrator does not check it. `yubiOS-ci.yml`, the production image builder, still carries the legacy internal `ci_*` inputs (`ci_callback`, `ci_chain_ref`, `ci_reason`, four push flags, `ci_fork_run`, `ci_test_run`, `ci_vm_image`) in its `workflow_dispatch` body even after the orchestrator stopped sending them ([source](https://github.com/yubi-OS/yubiOS/blob/main/.github/workflows/yubiOS-ci.yml)). `ci_test-vm.yml` takes `image` (the OCI ref to boot), `hw_device` (a DESTRUCTIVE spare block device for the physical-YubiKey test `tests/vm/test-luks-fido2.sh`, wiped on use), `hw_image`, `firmware_image`, `ftpm_linux_payload`, and an `allow_real_u2f` flag required on rock1 because a physical YubiKey sits on that host: a passless regression must not be silently masked by the in-guest software authenticator winning an enumeration race, so the `assert_passless_only` guard from PR #144 refuses to run passless tests when a real key is present unless the flag is explicitly set ([source](https://github.com/yubi-OS/yubiOS/blob/main/.github/workflows/ci_test-vm.yml), input descriptions). Forwarding `allow_real_u2f` to a workflow that does not declare it returns HTTP 422 ([playbooks/hw-device-and-allow-real-u2f.md](https://github.com/yubi-OS/yubiOS/blob/main/playbooks/hw-device-and-allow-real-u2f.md)).

Two audit workflows police the surface: `ci_input-shape.yml` runs `scripts/validate-input-shape.py` on pull requests touching `.github/workflows/**` plus a weekly Monday 09:00 UTC drift scan, uploads a JSON report with 30-day retention, and takes a `fail_on` choice of ERROR/WARN/NEVER (verified in the workflow file 2026-09-29). Its siblings `ci_dispatch-reachability.yml`, `ci_token-audit.yml`, `ci_fork-drift-detect.yml`, and `ci_package-floor.yml` exist in the same listing.

## Self-hosted ARM64 runner fleet

Org `yubi-OS` has two self-hosted ARM64 runners, both online (org-level runners API, verified 2026-09-29; also recorded in [refs/chromium-runner-highmem-2026-09-09.md](https://github.com/yubi-OS/yubiOS/blob/main/refs/chromium-runner-highmem-2026-09-09.md)):

| Runner | Labels | Role |
|---|---|---|
| `rock1` | self-hosted, Linux, ARM64, KVM | SBC doubling as CI runner and serial/audio lab host; the only runner for the DESTRUCTIVE `hw_device` hardware leg |
| `ubuntu` | self-hosted, Linux, ARM64, HIGH-MEM | Jenny's HIGH-MEM attach from 2026-09-09: 12 cores, 62 GiB RAM observed, no passwordless sudo, restricted to the Chromium arm64 main-branch workflow |

The workflows encode rock1's permanence directly: `ci_test-vm.yml` reclaims root-owned files before checkout, frees disk after, and caches the built bcvk binary under `/opt` because "rock1 is self-hosted and persistent" with "a small root disk" (same file, step comments, verified 2026-09-29). The KVM gate skips boot legs loudly with a warning, not a failure, if `/dev/kvm` is absent, and the comment notes that if this fires on rock1 it means KVM is not enabled in its kernel or BIOS. Self-hosted runner version enforcement is an upstream pressure on this fleet: GitHub resumed minimum-version enforcement during 2026, with enforcement dates extending into September 2026 (GitHub Changelog, 2026-06-12, weight 0.94). GitHub's own position that self-hosted runners, unlike hosted ones, carry no isolation guarantees (GitHub Docs, weight 0.92) is the background for the org's privilege audit: [refs/adjacent-problems-runner-privilege-2026-09-13.md](https://github.com/yubi-OS/yubiOS/blob/main/refs/adjacent-problems-runner-privilege-2026-09-13.md) maps the three trust postures (HIGH-MEM runner without sudo, dual-duty rock1, hosted fallback for full Chromium builds) and names rejection criteria for each. All GitHub Actions are pinned to full 40-character SHAs org-wide (same ref).

## The three VM test lanes

Three bcvk-based VM lanes share the same preflight (host deps, zstd-QEMU, bcvk build, KVM gate, AppArmor) and the same rc contract: exit 0 means pass, 77 means loud SKIP, anything else fails ([ci_test-vgpu-vm.yml](https://github.com/yubi-OS/yubiOS/blob/main/.github/workflows/ci_test-vgpu-vm.yml), header).

- **`ci_test-vm.yml`**, the standard e2e: boots the yubiOS image via `bcvk ephemeral run --swtpm --swu2f` and runs in-guest assertions for the fTPM chain, LUKS2 FIDO2 unlock, and FIDO2 enrollment. `pam-u2f` and `swtpm` legs always run; the LUKS2/homed FIDO2 legs SKIP unless a CTAP2 hmac-secret authenticator is present, and the hardware YubiKey leg never runs on push, only on an explicit destructive dispatch ([source](https://github.com/yubi-OS/yubiOS/blob/main/.github/workflows/ci_test-vm.yml)).
- **`ci_test-vgpu-vm.yml`**, derived from the first: `tests/vm/test-vgpu-virtio-ci.sh` gates virtio-gpu-pci on the host and asserts the negative VFIO surface in-guest (no `/dev/vfio`, nothing bound to vfio-pci), while `tests/vm/test-vfio-user-host-ci.sh` exercises QEMU's vfio-user-pci client against a libvfio-user server over an owner-only AF_UNIX socket with no kernel VFIO modules. It then re-runs every `ci_test-vm.yml` leg with `YUBIOS_VGPU=1`, because per the vGPU trust-boundary rule no trust-boundary component may consume GPU state. Real vfio-pci passthrough, IOMMU isolation, and vendor mediated vGPU are not testable here: no runner in the org has an IOMMU plus a real GPU (same header).
- **`ci_test_sealed-uki-vm.yml`**, the sealed-boot lane: builds a signed UKI from a yubiOS OCI image, signs it via `systemd-sbsign` with a SoftHSM PKCS#11 backend (`provider:pkcs11`, never `engine:pkcs11`, per ADR-008), boots it under OVMF Secure Boot asserting `systemd-stub SecureBoot=yes` via serial console, and runs negative tamper tests. Three jobs (`build-and-verify-uki`, `boot-secure-vm`, `negative-tamper-tests`), 6 assertions ([source](https://github.com/yubi-OS/yubiOS/blob/main/.github/workflows/ci_test_sealed-uki-vm.yml)).

This shape matches the upstream bootc testing pattern of validating a converted disk image by actually booting it in a VM ([Fedora bootc docs, weight 0.80](https://docs.fedoraproject.org/en-US/bootc/getting-started/); [bootc-image-builder VM boot testing, weight 0.62](https://deepwiki.com/osbuild/bootc-image-builder/4.4.3-vm-and-boot-testing)), but yubiOS goes further by pinning the QEMU/UKI signing chain and adding negative tamper tests. The sealed-UKI lane went green at V83 (run 30652859000, commit `1d0666d77c0b`, arm64 `boot_timeout` raised 900 to 1200 s) after roughly 15 debug runs over 2 days; the full failure taxonomy lives in [playbooks/sealed-uki-vm-debug.md](https://github.com/yubi-OS/yubiOS/blob/main/playbooks/sealed-uki-vm-debug.md), including the SoftHSM single-part ECDSA limitation (upstream SoftHSMv2#842, fix: pin `pkcs11-provider >= 1.2.0` or switch to kryoptic).

## Reproducible builds

`scripts/lib/reproducible-build.sh` is the single shared reproducible environment for GitHub Actions and the local CI-parity entrypoint ([source](https://raw.githubusercontent.com/yubi-OS/yubiOS/main/scripts/lib/reproducible-build.sh)). `SOURCE_DATE_EPOCH` is always the selected source commit's committer timestamp, and a caller-supplied epoch that mismatches the revision is a hard error, never a silent override. `YUBIOS_MKOSI_SEED` is derived deterministically as a version-5-style UUID from sha256 over a fixed namespace plus the git SHA, architecture, and `minimal` profile, so filesystem and partition identities stay stable per output without colliding across distinct outputs. The library also pins `PYTHONHASHSEED=0`, `ZERO_AR_DATE=1`, `TZ=UTC`, `LC_ALL=C`, kernel build identity variables (`KBUILD_BUILD_USER=yubios`, `KBUILD_BUILD_HOST=reproducible`), TF-A build timestamp and string, seeds deterministic EDK2 stack cookies from the same revision material, and sets `umask 022`. `reproducible_git` restricts git trust to the caller-supplied canonical repository path so a mounted checkout cannot be spoofed. Per [docs/CI_MAP.md](https://github.com/yubi-OS/yubiOS/blob/main/docs/CI_MAP.md), the ARM64 production and dev jobs build their real subject twice with isolated no-cache builders and compare canonical OCI layouts, the firmware lane rebuilds StandaloneMM and every board in a second clean ARM64 job and compares intended unsigned components (recording the QEMU signing envelope and RK3588 TPL as explicitly outside byte equality), and the installer lane proves ARM64 reproducibility with a SoftHSM PKCS#11 mock.

## Playbooks: the operational layer

`playbooks/` holds operator runbooks, one per recurring failure mode, revised in place with no date suffix ([playbooks/README.md](https://github.com/yubi-OS/yubiOS/blob/main/playbooks/README.md)). Hard rules: never cite a run ID, SHA, or PR not fetched that session; every playbook names at least one commit, run, or PR under "Verified working"; agents draft, Jenny merges; a failure mode qualifies once it has fired twice; permanent patterns are cross-registered in `docs/BLOCKERS.md` under Permanent CI-Evidence Patterns. Match on failure mode, not workflow name.

The CI-specific set: `playbooks/dispatch-chain-verification.md` codifies "outer is not inner": `ci.yml` succeeding means only its single dispatch job ran, so every inner run's own conclusion must be read; the PR #150 cycle produced four fabricated run IDs in one session, and the playbook's rule 4 is "never fabricate: unqueried means say I have not verified this yet." `total_count: 0` on a completed run is a YAML parse failure, not an empty run list; logs 404 after roughly 15 to 30 minutes, so diagnose from the file diff; duplicate dispatches land 10 to 20 seconds apart and are cancelled (HTTP 202); merging is always verified read-only because Jenny merges. `playbooks/drop-in-override-naming.md` is the lex-sort rule: systemd drop-ins sort by full filename, so `53-yubiOS-no-static-vfio.conf` (`5` = 0x35) sorted before upstream's `static-nodes-permissions.conf` (`s` = 0x73) and upstream re-created `/dev/vfio` every boot for 4 days (OMN-149); the fix renamed it `vfio-yubiOS-no-static-vfio.conf` (commits `59f4332`, `f92c6010`). `playbooks/hw-device-and-allow-real-u2f.md` and `playbooks/fido2-vm-e2e-recipe.md` cover the two-flag opt-in and the FIDO2 VM lane recipe.
