# CI and Test Infrastructure

yubiOS CI has one job: prove that a bootc-built, Secure-Boot-sealed, YubiKey-unlockable image actually boots and behaves on real ARM64 and x86_64 hardware. The proof is divided across lanes by cost: cheap static lint and rootless-docker checks run on GitHub-hosted runners, full boot e2e runs in ephemeral bcvk VMs, the sealed-UKI lane proves the PKCS#11-signed boot chain under OVMF, and the vGPU lane proves that adding a virtual GPU is behaviorally a no-op for everything else. Coordination is deliberately dumb: a single group-routing orchestrator fires independent `workflow_dispatch` events, and two audit workflows mechanically verify that the dispatch surface stays consistent.

## Orchestrator: ci.yml group routing

`.github/workflows/ci.yml` is the top-level dispatcher. It exposes one `group:` choice input (none, firmware, tests, vm-tests, fetches, ci-builders, forks, audits, research, all) plus `reason` (an audit-log entry), `target_ref`, and `Docker_push` (https://github.com/yubi-OS/yubiOS/blob/main/.github/workflows/ci.yml). When dispatched with a group, it fires one independent `workflow_dispatch` per workflow in that group and exits: no state machine, no `needs:`, no callback. A 2026-07-29 redesign removed all path-scoped `on: push` triggers, made all sibling workflows dispatch-only, and deleted the legacy `ci_*` pass-through inputs and the callback contract (same file, header comment). The group→workflow mapping lives in the `case` statement; note the header comment's taxonomy lags it: the `tests` group now dispatches 8 workflows including `ci_test-bootc-lifecycle.yml`, `ci_test-sysext-portable.yml`, `ci_test-fedora-bootc-arm64-pull.yml`, `ci_test-ftpm-tpm0.yml`, and `diag_sign-matrix.yml`, while the comment still lists 3. `docs/CI_MAP.md` holds the authoritative group membership, regenerated 2026-07-29 for PR #145.

The dispatch surface is 39 workflow files (Contents API listing of `.github/workflows/`, verified 2026-09-29): builders (`yubiOS-ci.yml`, `ci_dev_image.yml`, `ci_mkosi-installer.yml`, `ci_build-test-fixtures.yml`), 8 fork-guard workflows (`ci_fork_mkosi.yml` through `ci_fork_edk2.yml`), 8 test workflows including the 3 VM lanes, 3 fetch workflows that commit manifests to `main`, 5 audits, and 4 research workflows.

## Builders and the asymmetric dispatch schema problem

`yubiOS-ci.yml` is the production image builder: shellcheck and hadolint arch-neutral, then a native amd64/arm64 matrix (explicitly "native split, NOT QEMU"), mkosi, build, `merge-manifest`, `verify-attest`, and a `ci-callback` job. It still carries the legacy internal `ci_*` inputs (`ci_callback`, `ci_chain_ref`, `ci_reason`, `ci_Docker_push`, `ci_fork_run`, `ci_test_run`, `ci_vm_image`, and three more push flags) in its `workflow_dispatch` schema (https://github.com/yubi-OS/yubiOS/blob/main/.github/workflows/yubiOS-ci.yml).

That is the asymmetry: every sub-workflow owns a different dispatch schema. `ci_test-vm.yml` takes `image` (the OCI ref to boot), `hw_device` (a DESTRUCTIVE spare block device for the physical-YubiKey test `tests/vm/test-luks-fido2.sh`, wiped on use), `hw_image`, and an `allow_real_u2f` flag required on rock1 because a real YubiKey sits on the host; a passless regression must not be silently masked by the in-guest software authenticator winning an enumeration race (https://github.com/yubi-OS/yubiOS/blob/main/.github/workflows/ci_test-vm.yml, input descriptions). The orchestrator sends only `{ref, Docker_push}` to builders and `{ref, {}}` to everything else, so schema drift is invisible until a manual dispatch fails.

Two audit workflows police this: `ci_input-shape.yml` (runs `scripts/validate-input-shape.py`, PR-triggered on `.github/workflows/**` plus weekly Monday 09:00 UTC cron, uploads a JSON report with 30-day retention) and `ci_dispatch-reachability.yml` (`scripts/assert-dispatch-reachable.py` checks every workflow named by ci.yml groups is actually dispatchable). Both take a `fail_on` choice of ERROR/WARN/NEVER. The doctrine behind them is recorded in `refs/validate-input-shape-doctrine-2026-08-04.md` and `refs/workflow-dispatch-reachability-spec-2026-08-04.md`; the token-scope counterpart is `ci_token-audit.yml` (schema informed by `refs/workflow-token-scope-audit-script-2026-08-04.md`, refs listing verified 2026-09-29).

## Self-hosted ARM64 runner fleet

Org `yubi-OS` has two self-hosted ARM64 runners (verified live via GitHub API, https://github.com/yubi-OS/yubiOS/blob/main/refs/chromium-runner-highmem-2026-09-09.md): `rock1`, labels `self-hosted, Linux, ARM64, KVM`, and `ubuntu`, Jenny's HIGH-MEM attach from 2026-09-09 (12 cores, 64 GB-class RAM, no passwordless sudo, currently restricted to the Chromium main-branch workflow). `ubuntu` is a bare-metal Snapdragon X Elite (X1E80100) laptop running the runner as `github-actions-runner.service` (systemd, active and running at verification: live `systemctl` probe via the ubuntu shell bridge, 2026-09-29); rock1 is the SBC that doubles as CI runner and serial/audio lab host (https://github.com/yubi-OS/yubiOS/blob/main/refs/adjacent-problems-runner-privilege-2026-09-13.md, and the 2026-09-24 system inventory showing `Runner.Listener` RUNNING on rock1). Rock1's runner is a migrated copy that came back alongside ubuntu's (workspace system inventory, `documents/github-yubios-KS9n5GAT/2026-09-24_System_Inventory.txt`).

The workflows encode rock1's permanence: `ci_test-vm.yml` and `ci_test-vgpu-vm.yml` reclaim root-owned files before checkout, free disk after, and cache the built bcvk binary under `/opt` because "rock1 is self-hosted and persistent" with "a small root disk" (same file, step comments). The arm64 matrix leg targets `[self-hosted, Linux, ARM64, KVM]` because hosted ARM64 GPU runners lack nested virt, and a `/dev/kvm` gate skips the boot leg loudly (warning, not failure) if KVM is absent. The privilege story of this fleet is deliberately documented rather than assumed: `refs/adjacent-problems-runner-privilege-2026-09-13.md` maps the three trust postures (HIGH-MEM runner without sudo, dual-duty rock1, hosted fallback) and names the GitHub large-runner fallback for full Chromium builds.

## VM test lanes

Three VM lanes, all bcvk-based, all sharing the same preflight (host deps, zstd-QEMU, bcvk build, KVM gate, AppArmor) and the same rc contract: 0 means pass, 77 means loud SKIP, anything else fails (https://github.com/yubi-OS/yubiOS/blob/main/.github/workflows/ci_test-vgpu-vm.yml, header).

`ci_test-vm.yml` is the standard e2e: boots the image, runs the fTPM chain, LUKS2 FIDO2 unlock, FIDO2 enrollment, and (on explicit dispatch only) the hardware YubiKey leg against `hw_device`. `ci_test-vgpu-vm.yml` is derived from it and adds a virtual GPU in scope: `tests/vm/test-vgpu-virtio-ci.sh` gates virtio-gpu-pci and asserts the negative VFIO surface (no `/dev/vfio`, nothing bound to vfio-pci), `tests/vm/test-vfio-user-host-ci.sh` exercises QEMU's vfio-user-pci client against a libvfio-user server over an owner-only AF_UNIX socket with no kernel VFIO modules. It then re-runs every `ci_test-vm.yml` leg with `YUBIOS_VGPU=1`, because per `refs/vgpu-vfio-user-trust-boundary-2026-07-25.md` rule 5 no trust-boundary component may consume GPU state. Real vfio-pci passthrough, IOMMU isolation, and vendor mediated vGPU are not testable: no runner in the org has an IOMMU plus a real GPU (same header).

`ci_test_sealed-uki-vm.yml` (52 KB, the largest workflow) proves the sealed-boot chain: a SoftHSM slot emulating PIV 9c signs a UKI via `provider:pkcs11` (OpenSSL 3.x, per ADR-008/OMN-116; never `engine:pkcs11`), the UKI boots under OVMF Secure Boot, and negative tamper tests run. Three jobs: `build-and-verify-uki`, `boot-secure-vm`, `negative-tamper-tests`. It went green at V83 (run 30652859000, commit `1d0666d77c0b`) after PR #154 opened the lane and PR #155 filled the stub; the arm64 leg runs on GitHub-hosted `ubuntu-24.04-arm` under TCG with `boot_timeout` 1200 s (https://github.com/yubi-OS/yubiOS/blob/main/.github/workflows/ci_test_sealed-uki-vm.yml, matrix; https://github.com/yubi-OS/yubiOS/blob/main/playbooks/sealed-uki-vm-debug.md).

## Reproducible builds

`scripts/lib/reproducible-build.sh` is the single shared environment (https://raw.githubusercontent.com/yubi-OS/yubiOS/main/scripts/lib/reproducible-build.sh). `SOURCE_DATE_EPOCH` is always the selected source commit's committer timestamp; a caller-supplied epoch that mismatches the revision is a hard error, not a silent override. `YUBIOS_MKOSI_SEED` is derived deterministically as a version-5-style UUID from sha256 over "yubiOS", the git SHA, the architecture, and the profile, so filesystem and partition identities stay stable per output without colliding across distinct outputs. The library also pins `PYTHONHASHSEED=0`, `ZERO_AR_DATE=1`, `TZ=UTC`, kernel and TF-A build timestamps, and `umask 022`. Both `yubiOS-ci.yml` and `ci_mkosi-installer.yml` call it (the installer passes `--source-date-epoch` and `--seed` to mkosi), run `normalize_reproducible_tree` and `write_reproducible_checksums` over each artifact tree, upload reproducibility evidence artifacts (e.g. `reproducibility-production-arm64-<sha>`), and `scripts/verify-reproducible-images.sh production` gates the production build (workflow files cited above, grep-verified).

## Playbooks: the operational layer

`playbooks/` holds operator runbooks, one per recurring failure mode, revised in place with no date suffix (https://github.com/yubi-OS/yubiOS/blob/main/playbooks/README.md). Hard rules: never cite a run ID, SHA, or PR not fetched that session; every playbook names at least one commit/run/PR under "Verified working"; agents draft, Jenny merges; a failure mode qualifies once it has fired twice, and permanent patterns are cross-registered in `docs/BLOCKERS.md` under Permanent CI-Evidence Patterns. Match on failure mode, not workflow name.

The CI-specific ones: `playbooks/dispatch-chain-verification.md` codifies "outer ≠ inner": `ci.yml` succeeding means only its single dispatch job ran, so every inner run's own conclusion must be read, run IDs must never be fabricated (the PR #150 cycle produced four fabricated ones), `total_count: 0` on a completed run is a YAML parse failure, logs 404 after roughly 15 to 30 minutes, duplicate dispatches land 10 to 20 seconds apart and get cancelled, and merging is always verified read-only because Jenny merges. `playbooks/drop-in-override-naming.md` is the lex-sort rule: drop-ins sort by full filename, so `53-yubiOS-no-static-vfio.conf` sorted before upstream's `static-nodes-permissions.conf` and upstream re-created `/dev/vfio` every boot for 4 days (OMN-149); the fix renamed it `vfio-yubiOS-no-static-vfio.conf` (commits `59f4332`, `f92c6010`), proven by `ci_test-vgpu-vm.yml`'s arm64 `test-vgpu-virtio-ci.sh` assertion. `playbooks/sealed-uki-vm-debug.md` is a row-by-row decision tree for that lane, from unquoted colons in step names through SoftHSM's single-part ECDSA limitation (upstream SoftHSMv2#842, fix: pin `pkcs11-provider ≥ 1.2.0` or switch to kryoptic) to the currently expected OVMF enrollment gap. `hw-device-and-allow-real-u2f.md`, `fido2-vm-e2e-recipe.md`, `github-token-vs-secrets.md`, and `digest-bump-recovery.md` cover the dispatch-input and token-writing failure modes.
