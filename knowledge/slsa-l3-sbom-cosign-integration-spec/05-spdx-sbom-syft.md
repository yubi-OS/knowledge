# SPDX SBOM generation with Syft and cosign attest

Scope: generating SPDX-format SBOMs with Syft from container images and filesystems, the output format surface, attaching the SBOM to an artifact as a cosign attestation, policy enforcement against SBOM attestations, and the coverage caveats that decide whether an SBOM is trustworthy.

## What Syft is

Syft is a CLI tool and Go library for generating a Software Bill of Materials from container images and filesystems; it is positioned as exceptional for vulnerability detection when used with a scanner like Grype. Source: https://github.com/anchore/syft (weight 0.72, primary).

The CLI surface is compact: syft takes a SOURCE (container image or filesystem) plus flags, and the reference documentation (generated against Syft version 1.54.0) shows examples like syft scan alpine:latest for a package summary and -o json for full cataloging details, with -o cyclonedx among the output modes. Source: https://oss.anchore.com/docs/reference/syft/cli/ (weight 0.87, primary vendor doc).

## Output formats, SPDX in particular

A tutorial listing the format surface shows the -o values include cyclonedx-json, cyclonedx-xml, spdx-json, spdx-tag-value, syft-json, syft-table, syft-text, and github-json, with the input being a remote image, a local image dictionary, or a local compressed image dictionary. Source: https://reestwick.github.io/sbomgen/tutorials/containers/creating-syft-sbom/creating-syft-sbom.html (weight 0.26, weak backing, tutorial). Anchore's own overview confirms SBOM generation in a variety of ecosystems and formats such as SPDX, CycloneDX, and Syft Lossless. Source: https://anchore.com/sbom/how-to-generate-an-sbom-with-free-open-source-tools/ (weight 0.65).

For the SPDX 2.3 JSON target, spdx-json is the format selector; verify the emitted spdxVersion field parses as SPDX-2.3 in the SBOM consumer rather than assuming it from the format flag.

## Attaching the SBOM as a cosign attestation

The attachment path is cosign attest. Chainguard's guide walks generating an SBOM and associating it with a specific OCI container using an attestation generated by Cosign. Source: https://edu.chainguard.dev/open-source/sigstore/cosign/how-to-sign-an-sbom-with-cosign/ (weight 0.86, primary vendor doc).

The cosign attest reference shows the general shape: cosign attest --predicate --type --key with a local key pair file, or with a key stored in Azure Key Vault (azurekms://[VAULT_NAME][VAULT_URI]/[KEY]). Source: https://github.com/sigstore/cosign/blob/main/doc/cosign_attest.md (weight 0.90, primary). Anchore's own guide covers generating cryptographically signed SBOM attestations using in-toto and Sigstore to create, verify, and attach attestations to container images. Source: https://oss.anchore.com/docs/guides/sbom/attestation/ (weight 0.69).

Cosign signs attestations using DSSE envelopes, commonly in the in-toto attestation format. Source: https://blog.glen-thomas.com/software%20engineering/security/2026/01/20/signing-container-images-with-cosign.html (weight 0.19, weak backing, blog).

## Enforcement: policy controllers can require the SBOM

The Sigstore policy-controller sample policies include one asserting that all images must have a signed SPDX SBOM (spdxjson) attestation. Source: https://docs.sigstore.dev/policy-controller/sample-policies/ (weight 0.90, primary). This is the consumption-side counterpart: emitting an spdxjson attestation is only useful if some gate can require it, and the policy-controller is that gate in the Sigstore ecosystem.

## Coverage caveats

The SBOM scan is only as complete as the SBOM itself: if Syft misses a package, for example a statically compiled binary, a vulnerability scanner like Grype will not find vulnerabilities for it. For maximum coverage, generate the SBOM with Syft's --catalogers all flag. Source: https://secure-pipelines.com/ci-cd-security/lab-sbom-pipeline-generate-attest-verify-syft-cosign/ (weight 0.62).

The same weakly backed blog that describes the DSSE wrapping lists what makes an SBOM valuable: generate it consistently, store it alongside the exact digest you shipped, sign it so people can trust its origin, and make it discoverable by automation. Source: https://blog.glen-thomas.com/software%20engineering/security/2026/01/20/signing-container-images-with-cosign.html (weight 0.19, weak backing). The four-point discipline is a useful checklist; its backing is weak, so treat it as review guidance.

## Verification checklist

1. Generate with syft scan <ref> --output spdx-json (0.87 primary CLI reference).
2. Confirm spdxVersion in the output matches the intended SPDX version.
3. Attach with cosign attest --type spdxjson --predicate <file> against the artifact digest, not a mutable tag (0.90 primary).
4. Enforce downstream with a policy that requires the signed spdxjson attestation (0.90 primary).
5. Audit coverage: run --catalogers all where statically linked binaries matter (0.62).
