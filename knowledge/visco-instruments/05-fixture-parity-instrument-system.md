# 05 The fixture-parity instrument system

Scope: `tools/visco-instruments/` as the system of record: `verify_visco.py`, `generate_fixtures.py`, `CONTRACTS.md`, JSON fixtures, and the fixture-parity-tested JS port (`jev-visco-math.js`) that is never re-derived.

## The shape of the system

The instrument math lives in a Python package that is the single system of record: `tools/visco-instruments/` contains `verify_visco.py` (the selftest and verification entry), `generate_fixtures.py` (the fixture generator), `CONTRACTS.md` (the written contract between lanes), and `fixtures/visco-fixtures.json` (the recorded outputs). The JavaScript implementation on the worker, `jev-visco-math.js`, is a separate worker part that is fixture-parity-tested against those recordings and is never re-derived from scratch [source: internal build record, https://raw.githubusercontent.com/yubi-OS/yubiOS/main/refs/visco-instruments-2026-10-02.md].

The verification numbers make the split concrete: the Python side passes a 15/15 selftest and reproduces the 102.86 hysteresis anchor exactly; the JavaScript port passed 9/9 parity checks on its first run [source: internal build record, https://raw.githubusercontent.com/yubi-OS/yubiOS/main/refs/visco-instruments-2026-10-02.md].

## Golden master and characterization testing

The fixture design is the golden master (characterization test) pattern. A characterization test describes the actual behavior of an existing piece of software and thereby protects existing behavior [source: https://en.wikipedia.org/wiki/Characterization_test, jev weight 0.1758, weak backing]. Approval testing (also called golden master testing) compares actual output against a known-good snapshot, the approved file or golden master, generated once, reviewed once, and then treated as the baseline [source: https://helpmetest.com/blog/approval-testing-golden-master/, jev weight 0.3874, weak backing]. The pattern captures legacy or current behavior as a baseline so that refactoring proceeds without fear: if the output changes, the test fails [source: https://stackpractices.com/patterns/golden-master-testing-pattern/, jev weight 0.5702]. One guide frames approval testing as a way to put code under a test harness quickly by generating the golden master output and comparing subsequent outputs against it [source: http://octopusinvitro.gitlab.io/blog/code-and-tech/approval-testing, jev weight 0.2425, weak backing].

In `tools/visco-instruments/` the golden master is literal and machine-readable: `generate_fixtures.py` produces `fixtures/visco-fixtures.json`, and both the Python verifier and the JS port assert against the same file. The recorded anchor values, such as the 102.86 hysteresis figure from the round-3 calibration case [source: internal replay record, https://raw.githubusercontent.com/yubi-OS/knowledge/main/knowledge/linear-viscoelasticity/08-creep-recovery-replay.md], live in that fixture file rather than in either implementation.

## Cross-language conformance as a pattern

The parity requirement is an instance of cross-language conformance testing: shared, machine-readable test vectors against which every implementation must produce identical output. The pattern is used by protocol ecosystems; one conformance suite ships machine-readable JSON test vectors shared across TypeScript and Python implementations, proven cross-language compatible [source: https://s402-protocol.org/guide/conformance, jev weight 0.477, weak backing], and another publishes a cross-language conformance test suite whose explicit purpose is to verify that all implementations produce identical output for the same inputs [source: https://github.com/cyphera-labs/cyphera-conformance, jev weight 0.5416]. A shared-fixture approach was proposed in the same spirit for a three-implementation codebase (backend, SDK, frontend), with language-agnostic fixtures so that any future drift between implementations is caught [source: https://github.com/aadityat23/finverify-llm/issues/17, jev weight 0.1623, weak backing].

The visco system applies this with one deliberate asymmetry: there is exactly one source of record (Python) and one consumer port (JS). A drift can be introduced only on the JS side or a fixture regeneration on the Python side; the fixtures are the arbiter in both directions.

## The port that is never re-derived

The build record's sharpest rule is that `jev-visco-math.js` is fixture-parity-tested and never re-derived [source: internal build record, https://raw.githubusercontent.com/yubi-OS/yubiOS/main/refs/visco-instruments-2026-10-02.md]. This matters because the failure mode of a second implementation is not a crash but silent numeric drift: two independently written NNLS solvers or tau-grid generators can produce close-but-different numbers, and a corpus gate keyed on those numbers would then depend on which implementation ran. The multi-language SDK ecosystem handles the same risk by releasing parallel implementations of one specification together, so that cross-language equivalence is a release property rather than an afterthought [source: https://blog.modelcontextprotocol.io/posts/sdk-betas-2026-07-28/, jev weight 0.9036]. Porting assistants that map library-specific behaviors between Python and TypeScript acknowledge that the port itself is error-prone and needs its own verification [source: https://github.com/glassBead-tc/python-to-typescript-assistant, jev weight 0.5898].

## CONTRACTS.md as the shared artifact

`CONTRACTS.md` in the tool directory is the written contract the lanes built against. The build ran as parallel lanes (Python, JS port, routes and wiring) with an advisor reconciling 5 contract ambiguities found at integration [source: internal build record, https://raw.githubusercontent.com/yubi-OS/yubiOS/main/refs/visco-instruments-2026-10-02.md]; the contract document is what makes parallel implementation and later re-derivation-proofing possible, because the fixtures encode the contract's consequences as concrete numbers. When a caller wants to verify the instrument math, the answer is not "read the JS": it is run `verify_visco.py`, regenerate fixtures, and diff.
