# 05 Closest prior-art chains and the coverage matrix

Scope: the three closest prior-art chains to the attested cutover synthesis, what each covers and leaves open, and the NVIDIA and Keylime anchors behind the comparisons.

## Chain 1: Confidential Containers plus NVIDIA confidential computing

The closest production-grade chain fuses launch measurement and GPU readiness under one policy surface. NVIDIA's GPU Operator documentation for Confidential Containers describes the operating pieces: the NVIDIA Confidential Computing Manager for Kubernetes manages the confidential computing mode of the NVIDIA GPU on the node, and the NVIDIA Sandbox Device Plugin discovers and advertises passthrough GPUs to kubelet (weight 0.94, https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/25.3.1/gpu-operator-confidential-containers.html). Underneath that sits Hopper-class hardware security: the H100 introduced the confidential computing capability on NVIDIA's Hopper architecture (weight 0.84, https://developer.nvidia.com/blog/confidential-computing-on-h100-gpus-for-secure-and-trustworthy-ai/).

A secondary industry matrix, dated September 24, 2026, reports that NVIDIA's Confidential Containers reference architecture lists H100 and H200 for single GPU passthrough with protected PCIe configurations, and that the answer to "confidential GPU attestation" depends on the complete platform rather than the GPU name alone (weight 0.33, https://gpusmith.com/articles/en/confidential-gpu-attestation-deployment-matrix, weak backing).

What this chain covers and does not cover, per the dig: it gates GPU use through TEE-attested workloads and device-plugin machinery, anchored to confidential-guest identity. It does not tie a bootc OCI image digest to the gate, and it operates at Kubernetes admission rather than at the libvirt launch boundary.

## Chain 2: Keylime measured boot

Keylime is a CNCF project providing highly scalable remote boot attestation and runtime integrity measurement, monitoring remote nodes with a hardware-based cryptographic root of trust (weight 0.74, https://keylime.dev/). Its measured-boot documentation explains the substrate: TPM 2.0 assigns specific meanings to the lower-numbered PCRs (0 through 9), extended during the events of a measured boot log, and the verifier compares those PCRs against an allowlist (weight 0.86, https://keylime.readthedocs.io/en/v7.14.2/user_guide/use_measured_boot.html). SUSE's deployment guide describes the operational flow: validate the PCRs extended during measured boot, analyze the event log, make assertions on PCR values, monitor open or executed files, and deliver encrypted payloads to verified nodes via secure payloads (weight 0.87, https://documentation.suse.com/smart/security/html/SLE-Micro-security/ch03.html).

The chain is real but has rough edges: an open issue documents systems failing measured-boot attestation when the policy was generated by create_mb_refstate from the system's own measured boot log (weight 0.60, https://github.com/keylime/keylime/issues/1617).

What this chain covers and does not cover: C1-style provenance and C2-style measurement are squarely its domain, with QEMU-class guests as launch surfaces. Nothing in the kept results shows Keylime gating a device attachment; its release surface is secrets and payloads, not GPUs.

## Chain 3: TEE-bound confidential systems (Kata, AKS)

Azure's AKS confidential containers preview shows the third chain's shape: a security policy must be generated (via the confcom CLI extension) and the deployment requires a workload identity plus a federated identity credential (weight 0.92, https://learn.microsoft.com/en-us/azure/aks/deploy-confidential-containers-default-policy). The CoCo project frames the goal as protecting containers while running, using confidential computing and hardware-backed isolation (weight 0.81, https://confidentialcontainers.org/). NVIDIA's troubleshooting page for its Confidential Containers architecture covers installation and workload-deployment failure modes (weight 0.80, https://docs.nvidia.com/datacenter/cloud-native/confidential-containers/latest/troubleshooting.html). A secondary layer breakdown notes that CoCo integrates many components across different trust boundaries, so failures must be attributed layer by layer (weight 0.16, https://deepwiki.com/confidential-containers/confidential-containers/6-troubleshooting, weak backing).

These systems all require a TEE to hold the trust anchor. The synthesis's distinguishing property, attested cutover with no TEE, is exactly what this chain cannot express without redesign.

## The coverage picture

Reading the three chains together with the component docs (01, 02, 03):

| Capability | Where the dig shows it |
|---|---|
| Digest-pinned bootable images | bootc / RHEL image mode / Fedora Phase 2 (doc 01) |
| Image provenance verification | Docker provenance docs, registry-level (doc 01) |
| Launch measurement replay | Keylime PCRs 0 to 9, SUSE event-log analysis (this doc) |
| Attestation-policy resource release | CoCo KBS resource policies (doc 03) |
| GPU passthrough / mediation | vfio-user, mdev lineage (doc 02) |
| GPU binding as an attestation-gated claim | not found in any kept result |
| TEE-free cutover sequencing | not found in any kept result |

The bottom two rows are the synthesis's claimed gap, and the dig is consistent with the source topic's verdict: the combination is absent from the reviewed landscape, while every individual row is independently established.
