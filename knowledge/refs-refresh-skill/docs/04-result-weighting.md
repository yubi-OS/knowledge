# Result quality weighting: scoring every result as it lands

Scope: weighting every search result with a yes/no decision model so primary sources separate from aggregators before anything enters the research database.

## The seat

Every result a dig returns is a candidate citation. The weighting seat asks one question per result: is this a high-quality authoritative source worth citing? True means primary or official source. False means aggregator, forum, marketing page, dead link, or off-topic. The answer is a probability, stored with the result, and the stored weight travels with every claim that cites the result downstream.

This is the highest-value seat for the decision model in the whole pipeline. The validated run observed the weighting seat separating upstream primary sources at 0.90 to 0.96 from aggregators at 0.01 to 0.16 (internal evidence, 2026-09-29). A threshold at 0.5 then converts a continuous judgment into a hard gate: above 0.5 backs a claim as authoritative, below 0.5 the claim can still be made but must be labeled as weakly backed.

## Why judge this per result instead of per doc

Scoring results individually costs more requests than scoring whole result sets, and the pipeline pays it anyway. The reason is auditability. A per-result weight recorded next to the query that found it, the raw answer object, and the request timestamp makes every downstream claim traceable to a specific decision made at a specific time. Batch-level judgment can produce the same prose but not the same audit trail, and the research database exists precisely to be that audit trail.

The batching is still real: 5 results per request, one question per result inside the batch. The validated run weighted 144 dig results with 31 requests at roughly $0.006 (internal evidence, 2026-09-29).

## The literature agrees the judge can do this job

The approach has direct research backing. SourceCheckup is an automated agent-based pipeline that evaluates the relevance and supportiveness of sources in LLM responses (https://www.nature.com/articles/s41467-025-58551-6, weight 0.93), which is the same judgment shape: per-source, automated, supportiveness-focused. Work on LLM-driven usefulness judgment argues that traditional relevance labels alone fail to capture whether a search system actually helps the user, and proposes LLM judgment as the evaluation mechanism (https://arxiv.org/abs/2504.14401, weight 0.92).

Benchmarking work provides the calibration caution: a study benchmarking LLM-based relevance judgment methods built a practical methodology for evaluating diverse LLM-based relevance assessment methods and released judgments generated by both an open-source model (Llama3.2b) and a commercial model (gpt-4o) (https://dl.acm.org/doi/10.1145/3726302.3730305, weight 0.85). The lesson for the weighting seat is that judge choice is a measured decision, not a default.

The same pattern is appearing in production search systems. OpenSearch 3.5 introduced LLM as a Judge, using large language models to automatically evaluate search result relevance at scale (https://opensearch.org/blog/introducing-llm-as-a-judge-scaling-search-relevance-evaluation-with-ai/, weight 0.62), with a tutorial framing it as automating what manual annotators do inconsistently (https://docs.opensearch.org/latest/tutorials/llm-as-a-judge-tutorial/, weight 0.64). An e-commerce engineering writeup describes running relevance assessment at scale with the judge and caring about result position, not just relevance (https://blog.allegro.tech/2026/08/automating-search-relevance-llm-as-a-judge.html, weight 0.70).

Adjacent evidence bounds the judge's reliability. A two-stage LLM pipeline for automated citation quality scoring in academic manuscripts exists and was evaluated as a method (https://www.nature.com/articles/s41598-026-60947-3, weight 0.63). A comparison of LLM and expert assessments of journal quality found the LLM leans on general indicators of visibility, topical centrality, and perceived disciplinary impact, even without explicit citation data (https://link.springer.com/article/10.1007/s11192-026-05644-8, weight 0.61). Translation: the judge approximates reputation, which is exactly what "is this authoritative" asks for, but it can be fooled by a familiar-looking domain with thin content.

Search-engine comparison work also warns about the upstream supply: LLM-based search engines filter and re-rank citations with reasoning capabilities, potentially improving citation reliability relative to traditional search engines where users run sub-queries themselves (https://arxiv.org/html/2512.09483v1, weight 0.66). The weighting seat is the pipeline's own version of that re-rank.

## The failure the seat prevents

Without the gate, an aggregator result with a scraped summary enters the research database indistinguishable from the upstream release note it paraphrased. Every downstream document then cites the paraphrase. The weight split makes that failure visible at collection time instead of review time: the validated run's per-document average quality spread from 0.23 to 0.70 (internal evidence, 2026-09-29), and a low average on a doc is a signal to redo the dig with different queries rather than author from thin material.

## Summary

1. Weight every result at collection time with a typed yes/no judgment, 5 per request.
2. Threshold at 0.5: authoritative backing above, weak-backing label below.
3. The judge approximates reputation through visibility and centrality signals (https://link.springer.com/article/10.1007/s11192-026-05644-8, weight 0.61), so keep the audit trail per result.
4. A low per-doc average weight is a dig-redo signal, not an authoring constraint to write around.
