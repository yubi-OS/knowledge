# 06 - Verification timeline state

Scope: current state of the PQ verification timeline: slsa-verifier and cosign verify algorithm coverage, and why verification lags signing.

## What slsa-verifier does today

slsa-verifier is the canonical tool for verifying SLSA provenance generated by CI/CD builders. Its documentation states the mechanism directly: slsa-verifier "verifies the provenance by verifying the cryptographic signatures on provenance to make sure it was created by the expected builder" (https://github.com/slsa-framework/slsa-verifier, weight 0.90). That mechanism is algorithm-dependent: whatever signature algorithm the provenance was signed with, the verifier must support it natively, in a small statically linked binary, for the verification to succeed anywhere.

The dig for this subtopic found no source documenting post-quantum signature algorithm support in slsa-verifier. The tool's own documentation describes classical signature verification, and the PQ-focused sources surfaced (a survey of library support, an NSA resource hub) do not list it as a PQ adopter. This absence of evidence is itself the finding: the verification timeline has no documented PQ-aware slsa-verifier, which matches the gap the source readiness record flags. The claim is stated here as a dig outcome, not as a fact about the repository's current head, and should be re-verified against the repository before any commitment is based on it.

## What cosign verify supports

The verification side of Sigstore is documented more explicitly. Cosign verification docs cover verifying signed artifacts, blobs, and container images, described as the point where "the full potential of Sigstore to secure the software supply chain is achieved" (https://docs.sigstore.dev/cosign/verifying/verify/, weight 0.62). The verifying overview documents the tooling, security model, threat model, Sigstore bundle format, and API stability and deprecation policy (https://docs.sigstore.dev/cosign/verifying/, weight 0.75). The cosign repository adds the key structural fact: cosign can do completely offline verification by verifying a bundle distributed as an annotation on the image manifest, and can store and retrieve signatures in any format from any algorithm (https://github.com/sigstore/cosign, weight 0.70).

A secondary explainer describes the bundle mechanism in operational terms: a Sigstore bundle packages verification material so a client can validate log evidence without a live Rekor query, and cosign can save an image with its signatures locally and verify that representation (https://oneuptime.com/blog/post/2026-08-11-verify-cosign-air-gapped-sigstore-bundles/view, weight 0.36, weak backing). The bundle format is therefore the artifact a PQ migration would need to extend: whatever algorithm the signature uses, the verifier consumes the bundle offline.

## Why verification lags signing

Verification is structurally last for three reasons visible in the sources:

1. There is nothing to verify until signing ships. The signature timeline (doc 05) has no mainstream ML-DSA signing flow yet, so verifier support has no demand signal to implement against.
2. Verification is the widest deployment surface. Signing happens once in a CI system; verification happens on every consumer machine, including minimal and embedded environments, so the verifier's algorithm table is a compatibility contract that is expensive to widen. A survey examining the state of post-quantum algorithm support in widely used open-source cryptographic libraries, focused on NIST PQC finalists, documents how uneven library support still is, and verifiers sit on top of those libraries (https://arxiv.org/html/2508.16078v1, weight 0.89).
3. Verification carries policy weight. Government guidance treats verification tooling as part of the adoption surface: the NSA's PQC Resource Hub provides explainers, technical guidance, and white papers aimed at implementers of quantum-resistant algorithms (https://www.nsa.gov/cybersecurity/post-quantum-cryptography-resource-hub/, weight 0.89), and a verifier that cannot check PQ signatures cannot accept PQ-signed provenance regardless of library support elsewhere.

## Consequence for sequencing

The verification timeline is the binding constraint of the three. Transport has shipped defaults (doc 04), signing has a roadmap and draft hardware standards (doc 05), but verification has neither a documented PQ-capable verifier nor a standardized signing flow to verify against. An OS project that wants PQ-integrity for its artifacts must plan to be a follower on this timeline: track the slsa-verifier and cosign verify algorithm coverage as the gate, and treat any internal PQ signing pilot as unshippable until the mainstream verifiers can consume it. The source readiness record's conclusion that timeline 3 is furthest behind is consistent with this dig.
