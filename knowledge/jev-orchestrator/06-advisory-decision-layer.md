# 06 - The advisory decision layer: probabilities never authorize

Scope: the advisory decision layer: typed decision models (intent category, actionable yes/no, risk score, proposed action) that inform the pipeline but never authorize dispatch themselves.

## Two decision layers with different jobs

The controller runs two kinds of decisions, and keeping them separate is the architecture's central safety move. The advisory layer is a typed decision model: it returns calibrated outputs such as an intent category, a yes/no actionability judgment, a risk score, and a proposed action. The authority layer is the deterministic gate. In the deployed controller, Understand and Decide run via a typesafe decision model (DefAPI typesafe/jev-1.13, relayed through the worker's `/api/decide`) and are explicitly advisory only: a probability never authorizes dispatch (source: system of record).

Decision-model products are converging on this shape. Cloudflare's Clef open-source decision models are built to answer typed questions (single-choice labels, yes/no with a probability, or scores) rather than emit free text, precisely so downstream code can consume them deterministically (source: https://blog.cloudflare.com/clef-decision-models/, weight 0.91). AWS's agentic AI pattern library describes workflow-for-routing in the same terms: a lightweight classifier steers each input to the right path, and the routing decision is a separate, testable artifact rather than something the reasoning model improvises (source: https://docs.aws.amazon.com/prescriptive-guidance/latest/agentic-ai-patterns/workflow-for-routing.html, weight 0.81). Microsoft's Agent Framework models workflow structure as typed edges between steps, so the control flow is explicit and checkable rather than implied by model output (source: https://learn.microsoft.com/en-us/agent-framework/concepts/workflows/edges, weight 0.94).

## What "advisory only" buys

When the model layer is advisory, its errors have bounded blast radius. A misclassification routes the task to the wrong review tier; a bad proposed action still has to pass the gate on its own terms; an overconfident probability changes nothing about dispatch authority. The Jev design states this as a rule: nothing in the understand or decide output can dispatch, and the gate evaluates every action as if it came from an untrusted proposer (source: system of record). This is also how the first live task used the layer: understand classified the digest task as communication work below the review floor, which correctly put it on the no-approval path, and the gate still independently split its two actions by policy (source: system of record).

The inverse design, letting model confidence feed authorization, fails in a specific way: the gate's guarantee would degrade from "deterministic code evaluated this action" to "a model was probably right," and the audit trail could no longer distinguish a policy decision from a model opinion. Structured output tooling makes model outputs reliable as data, which is exactly why they can be treated as proposals: reliable data from an untrusted source is safe to gate, never safe to trust (source: https://baeseokjae.github.io/posts/llm-structured-output-guide-2026/, weight 0.26, weak backing).

## Where typed decisions belong in the pipeline

Three placements are proven. Classification at ingest: intent category plus risk score decide queueing and the review floor, cheap and high volume (source: https://docs.aws.amazon.com/prescriptive-guidance/latest/agentic-ai-patterns/workflow-for-routing.html, weight 0.81). Actionability gating before proposal: a yes/no decision on whether the request is even actionable prevents wasted proposals (source: https://blog.cloudflare.com/clef-decision-models/, weight 0.91). Verification assistance after dispatch: a decision model can help judge whether an observed result matches the intended effect, as long as its verdict records as evidence rather than as terminal truth (source: https://learn.microsoft.com/en-us/agent-framework/concepts/workflows/edges, weight 0.94). A talk on how Jev differs from LLM structured outputs covers the same separation from the practitioner side: decision models answer bounded questions with probabilities; the surrounding system decides what those probabilities are allowed to cause (source: https://www.youtube.com/watch?v=BMUGlE8dWs8, weight 0.53).

## Adoption rules

Four rules for adding an advisory layer to an orchestration pipeline. First, type every question: one label, one number, one yes/no, never a paragraph, so the answer is machine-consumable and diffable. Second, keep the schema versioned alongside the policy so an audit can reconstruct what both looked like at decision time. Third, never pass model confidence into the gate's inputs; the gate sees the action shape only. Fourth, record the full raw answer object (probabilities, confidence, legend) in the audit trail, because advisory decisions are evidence too: in the deployed system every decision record stores its raw answer object with usage tokens and a timestamp (source: system of record). The advisory layer then does what it should: concentrates model judgment where it is genuinely useful, while the deterministic layer keeps every authorization reproducible.
