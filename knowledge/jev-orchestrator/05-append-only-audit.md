# 05 - Append-only central state and the pause switch that cannot undo

Scope: append-only central state and audit: event-chained tables, why mutable state is forbidden, and the pause/kill switch that cannot undo effects already executed.

## Append-only as the core data model

The deployed controller keeps every fact it ever knew in an append-only store: tasks, actions, and events live in D1 tables (`jev_tasks`, `jev_actions`, `jev_events`), with `jev_events` structured as an append-only chain, and approvals and learnings alongside them (source: system of record). Nothing is updated in place when the meaning changes; a new event is appended that describes the transition. The first live run produced a 25-event append-only chain for a single two-action task, which is what an audit trail looks like when it is generated by the pipeline itself rather than reconstructed after the fact (source: system of record).

Tamper-evident append-only logging is an established pattern outside agents too: hash-linked event records make any deletion or edit detectable, which is why the audit-log reference implementations chain entries by hash rather than storing rows in a mutable table (source: https://github.com/pametan/audit-log, weight 0.61). Durable execution frameworks reach the same structure for a different reason: a durable orchestrator must be able to replay history to recover state, and replay only works over an immutable record of what happened (source: https://learn.microsoft.com/en-us/azure/durable-task/common/what-is-durable-task, weight 0.96). The Jev design gets both properties at once: the chain is the audit log and it is the replayable state.

## Why mutable state is forbidden

A mutable state table creates three failure modes that an append-only chain eliminates. First, silent overwrite: an update that replaces "pending approval" with "approved" destroys the information that an approval was pending, which an auditor or a debugging human might need. Second, unattributable transitions: with in-place updates, who changed what and when lives only in application code; with an event chain, every transition is a row with an author and a reason. Third, replay inconsistency: frameworks that recover by replaying require the history to be complete and immutable, and a mutable row cannot guarantee either (source: https://learn.microsoft.com/en-us/azure/durable-task/common/what-is-durable-task, weight 0.96). Workflow engine comparisons list durable event-sourced state as the dividing line between engines that can survive process crashes mid-task and engines that cannot (source: https://labhub.hopto.org/blog/culture/2026-05-25-durable-workflow-temporal-inngest-trigger, weight 0.39, weak backing).

## The pause/kill switch and its hard limit

The controller exposes a pause switch that halts dispatch of pending actions. Its power is deliberately bounded: pausing and killing prevent future effects, they cannot reverse effects that already executed (source: system of record). This is an honest boundary, and designing around it is mandatory. The first live run demonstrated the semantics: after the pause was engaged, the controller correctly skipped both dispatches with a `pause_active` verdict, and the check happened again at dispatch time, not only at task level (source: system of record).

The asymmetry has a design consequence: anything that should be undoable needs its own compensation path in the action vocabulary, because the switch will not provide one. A kill switch that pretended to undo completed HTTP POSTs would be a lie in the data model. Agent control literature makes the same point about irreversible external actions: the safety mechanism has to fire before the side effect, since no runtime control can reach backwards after it (source: https://www.agentnative.dev/patterns/human-in-the-loop-approval-flow-pattern-for-ai-agents, weight 0.44, weak backing).

## What the audit chain must carry

For the chain to be worth anything, each event needs: the task and action it belongs to, the transition it records, the actor or subsystem responsible, the policy version in force, and a timestamp. The deployed schema carries the full data payload into `state_change` audit events when a write is filtered down to known columns, so filtered persistence never loses audit fidelity (source: system of record). That detail came from a real bug: the persistence layer initially forwarded unknown keys into a SQL UPDATE and failed closed with a column error, which the fix resolved by separating what is persisted from what is audited (source: system of record). The general rule: store the complete event, project the narrow row, and never let a storage constraint shrink the evidence.
