# 01 - Pipeline stages: the controller flow that makes an agent trustworthy

Scope: the seven-stage operations controller flow (ingest, understand, decide, gate, execute, verify, terminal) and why stage ordering, not model intelligence, is what makes an autonomous agent trustworthy.

## The shape of the controller

A Jev operations controller is a fixed pipeline, not a free-form agent loop. Work arrives as a task, is ingested into central state, is understood (classified for intent and risk), is turned into a concrete proposed action, is forced through a deterministic policy gate, is executed, is independently verified, and then lands in exactly one terminal state. The live implementation exposes this as 21 routes under `https://steady-orbit.systems-a.workers.dev/api/jev/*` with an ops console at `/jev/` (source: system of record, the live worker surface itself).

Mainstream agent frameworks confirm the same skeleton. OpenAI's Agents SDK documents orchestration as agents handing work to specialized agents with defined handoffs and validation at each step (source: https://openai.github.io/openai-agents-python/multi_agent/, weight 0.95). IBM's orchestration guide presents the same decomposition: a controller coordinates planning, tool use, and verification so no single model call both decides and acts unchecked (source: https://www.ibm.com/think/tutorials/llm-agent-orchestration-with-langchain-and-granite, weight 0.87). NVIDIA's agent tutorial separates tool selection, tool execution, and observation of results into distinct phases precisely so each can fail and be inspected on its own (source: https://developer.nvidia.com/blog/building-your-first-llm-agent-application/, weight 0.75).

## Why the ordering matters

The load-bearing property is not the number of stages, it is which stage can authorize what. In the Jev design, Understand and Decide are advisory: they produce a classification and a proposed action, but nothing they output can dispatch anything. Authorization is the gate's job and the gate is deterministic, code not probability. The community pattern literature reaches the same conclusion from the other direction: the plan-approve-execute-verify reference architecture explicitly places a human or policy approval step between planning and execution so the planner's output is never self-executing (source: https://robert-n-myhre.github.io/architecture-portfolio/reference-architectures/plan-approve-execute-verify, weight 0.45, weak backing). The plan-execute-verify overview makes the same argument: separation of planning from execution is what allows verification to catch a bad plan before it has effects (source: https://schwannden.github.io/ai-agent-study/plan-execute-verify/01-overview/, weight 0.36, weak backing).

A second ordering property is that the gate sits immediately before dispatch, not merely once per task. In the deployed controller, each action is re-checked against current policy right before it is sent, which generalizes the diagram's "check pause again at dispatch" requirement (source: system of record). This closes the window where policy changed or a pause switch was engaged after the original approval but before the HTTP call. The human-in-the-loop approval pattern documentation calls out exactly this class of gap as the reason approval flows need re-validation at the moment of effect (source: https://www.agentnative.dev/patterns/human-in-the-loop-approval-flow-pattern-for-ai-agents, weight 0.49, weak backing).

## Stages as failure isolation

Each stage also has its own failure mode and its own recovery. Ingest fails on malformed input and produces no side effects. Understand can misclassify, and the cost is a wrong routing suggestion that the gate will still evaluate on its own terms. The gate can deny, and denial is terminal for that action without touching the world. Execution can partially fail, which is why verify judges each action independently rather than the task as a blob. Microsoft's Copilot Analyst documentation describes the same per-stage accountability: when a multi-step analysis runs, each step is surfaced and checkable rather than the result appearing as one opaque blob (source: https://support.microsoft.com/en-us/microsoft-365-copilot/get-started-with-analyst-in-microsoft-365-copilot, weight 0.51).

## What this buys the operator

The controller flow converts "an AI did something" into "a classified task produced a proposed action, that action passed policy version N, was approved under binding H, executed with response R, and verified to outcome V, all recorded in an append-only chain." That sentence is auditable end to end. Human-in-the-loop control implementations emphasize that the auditability comes from the pipeline structure itself, not from logging bolted on afterwards (source: https://dev.to/pinnasys/how-to-implement-human-in-the-loop-controls-for-ai-agents-58ol, weight 0.44, weak backing). The Jev deployment's first live run produced a 25-event append-only chain for one task with two actions, demonstrating that the stage structure generates evidence as a byproduct of running (source: system of record).

The takeaway: stage ordering is the security model. Move authorization earlier and approvals go stale; move it later and effects happen before checks; merge it into the model and no deterministic guarantee exists at all.
