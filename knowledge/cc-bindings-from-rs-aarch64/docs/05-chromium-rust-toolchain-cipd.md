# 05. Chromium's rust toolchain packaging: where the binary lives and which platforms it ships for

Scope: how Chromium builds and distributes its Rust toolchain, which CIPD platform variants exist, why Linux_arm64 does not, and why cc_bindings_from_rs rides inside the toolchain tarball.

## Why Chromium builds its own toolchain

Chromium's tools/rust documentation states the constraint that shapes everything downstream: "Like with Clang, Chromium uses bleeding edge Rust tooling. We track the upstream projects' latest development as closely as possible. However, Chromium cannot use official Rust builds for various reasons which require us to match the Rust LLVM backend version with the Clang we use" (source: https://chromium.googlesource.com/chromium/src/+/main/tools/rust/, w=0.83). Each Rust package is built from an official Rust nightly source release and a corresponding LLVM revision, so a new Rust package must be built whenever either Rust or Clang is updated, and Chromium's Clang build process deliberately leaves behind artifacts needed for the Rust build (source: https://chromium.googlesource.com/chromium/src/tools/+/4607797c74146b9287c2837f6567a7f7af08ed01/rust/, w=0.68).

The cadence is documented in toolchain_support.md: the toolchain (clang, lld, libc++, and a small assortment of helper binaries) is updated every 2 to 4 weeks, and is used to build Chromium for 7+ platforms targeting 4+ CPUs including arm and arm64 (source: https://github.com/chromium/chromium/blob/main/docs/toolchain_support.md, w=0.44, weak). Note the carefully scoped meaning of that "4+ CPUs" figure: it covers target architectures, not host architectures of the toolchain packages.

## What the package contains

The rust toolchain package is not just rustc and cargo. The tools/rust README documents that Chromium ships two copies of the Rust standard library: a prebuilt version used only for host tools such as build scripts and proc macros, and a version built from source as part of the normal Chromium build for target artifacts; both match the toolchain revision's stdlib (source: https://github.com/chromium/chromium/tree/main/tools/rust, w=0.73). The crubit host tool rides along in the same package: Chromium's docs state that `//third_party/rust-toolchain` includes cpp_api_from_rust (source: https://chromium.googlesource.com/chromium/src/+/HEAD/docs/rust/cpp_api_from_rust.md, w=0.91), and the toolchain build script's install step iterates `CRUBIT_BINS = ['cc_bindings_from_rs']` and copies each binary into `RUST_TOOLCHAIN_OUT_DIR` (source: https://chromium.googlesource.com/chromium/src/+/refs/heads/lkgr-android-internal/tools/rust/build_crubit.py, w=0.83).

The distribution mechanism is CIPD, Chromium's package service. The CIPD documentation describes package ownership under chromium/ and the troubleshooting flow when a CIPD-maintained file goes missing during gclient sync (source: https://chromium.googlesource.com/chromium/src/+/refs/heads/main/docs/cipd_and_3pp.md, w=0.73). A related tracker issue shows the toolchain's GCS- and CIPD-managed layout under `lib/rustlib/src/rust/library` being actively reorganized (source: https://issues.chromium.org/issues/470138209, w=0.53).

## The platform variant list

The internal survey behind this corpus read the DEPS file at Chromium pin 153.0.8010.36 (commit 507c6ee3e2f3b2ca0e660547e5b9ea4820c67f4c), lines 1073 to 1114, where the rust-toolchain CIPD package is declared, and found exactly four platform variants shipped: Linux_x64, Mac, Mac_arm64, Win (source: internal record, yubiOS refs/ cc-bindings-from-rs-aarch64-2026-09-26, unweighted). There is no Linux_arm64 variant at that pin, and the survey verified the same absence on main as of 2026-09-25 (internal record, same doc). The GitHub mirror of DEPS is publicly fetchable for re-verification (source: https://github.com/chromium/chromium/blob/main/DEPS, w=0.62), but this corpus's dig did not capture the variant block text, so the four-variant list rests on the internal record.

The asymmetry has a known shape: upstream arm64 Chromium work targets arm64 as a cross-compilation target built on x64 hosts. The official ARM Linux build documentation describes building for ARM using the clang binary in the tree with specific gn args, with sysroots installed by script and a testing infrastructure described as "somewhat limited" with two builders on the FYI waterfall and try bots (source: https://chromium.googlesource.com/chromium/src/+/main/docs/linux/chromium_arm.md, w=0.84). Nothing in that flow needs an aarch64 host toolchain, because the toolchain binaries always execute on an x64 host. The internal survey drew exactly this conclusion: upstream never reaches the native-aarch64-toolchain state because upstream never syncs a native aarch64 toolchain at all (internal record, yubiOS refs/ cc-bindings-from-rs-aarch64-2026-09-26, unweighted).

## Why a native aarch64 sync hits the gap

When a builder on a linux-aarch64 host syncs the DEPS-managed tree, gclient pulls the CIPD package matching the host platform. With no Linux_arm64 variant, the host either gets nothing or the builder improvises, as the internal survey's build did, by deploying a toolchain whose rustc and cargo are aarch64 but whose packaged crubit binaries remain x86_64 ELF files. The x86_64 `bin/cc_bindings_from_rs` then fails with an exec format error the moment the build graph reaches the bindings step (internal record, yubiOS refs/ cc-bindings-from-rs-aarch64-2026-09-26, unweighted).

## What ships the variants

The toolchain packages are produced by the tools/rust pipeline: the Rust build there also builds LLVM for rustc and Clang for bindgen and crubit (source: https://chromium.googlesource.com/chromium/src/tools/rust/, w=0.61), and the crubit packaging step is part of that pipeline via build_crubit.py (source: https://chromium.googlesource.com/chromium/src/+/refs/heads/lkgr-android-internal/tools/rust/build_crubit.py, w=0.83). Doc 06 covers what that script does per host architecture, which is the sanctioned lever for producing the missing variant.
