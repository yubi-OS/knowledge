# 09. Route (a): the native build recipe, install layout, and risk register

Scope: the concrete plan for producing an aarch64 cc_bindings_from_rs natively on the build host, installing it into the Chromium toolchain layout, and the mechanical risks with their mitigations.

## The recipe

The internal survey behind this corpus produced a 7-step route (a) plan for building cc_bindings_from_rs natively on a 12-core, 62 GB aarch64 build host (source: internal record, yubiOS refs/ cc-bindings-from-rs-aarch64-2026-09-26, unweighted; this doc restates it with public corroboration where the dig provides it):

1. Pin the crubit revision. Read `CRUBIT_REVISION` (or equivalent) from `tools/rust/update_rust.py` at Chromium pin 507c6ee3, and read `tools/rust/build_crubit.py` at the same commit to check its `CRUBIT_BINS` list. The script's bin list changed over time; a recent branch snapshot shows `CRUBIT_BINS = ['cc_bindings_from_rs']` (source: https://chromium.googlesource.com/chromium/src/+/refs/heads/lkgr-android-internal/tools/rust/build_crubit.py, w=0.83), so if the pin's list already includes the target, build_crubit.py itself is the build driver; otherwise invoke the crubit cargo rules directly (internal record).
2. Fetch crubit source at the pinned revision from chromium.googlesource.com's external mirror of github.com/google/crubit, into a directory outside the DEPS-managed tree to keep the synced tree clean (internal record; mirror existence corroborated by source: https://chromium.googlesource.com/external/github.com/google/crubit/+/refs/heads/upstream/main/, w=0.57).
3. Build as the non-root user, with the toolchain's own aarch64 cargo and rustc, using `cargo build --release --locked --bin cc_bindings_from_rs` and Linux RUSTFLAGS `-Clink-args=-Wl,-z,origin -Clink-args=-Wl,-rpath,$ORIGIN/../lib` so the binary locates `librustc_driver-*.so` inside the toolchain (internal record; the rpath mechanism's necessity is corroborated by rust-lang issue 140299, where building without rpath breaks tools that need librustc_driver, source: https://github.com/rust-lang/rust/issues/140299, w=0.49, weak).
4. Install per the build_crubit.py convention: the aarch64 `cc_bindings_from_rs` ELF into `third_party/rust-toolchain/bin/`, replacing the x86_64 binary which is preserved as `cc_bindings_from_rs.x64` for the audit trail, plus `BUILD.gn`, `crubit.gni`, `LICENSE` and `support/` into `third_party/rust-toolchain/lib/crubit/` (internal record; the install-into-toolchain-out-dir behavior is corroborated by the script snapshot, source: https://chromium.googlesource.com/chromium/src/+/refs/heads/lkgr-android-internal/tools/rust/build_crubit.py, w=0.83).
5. Verify with `file third_party/rust-toolchain/bin/cc_bindings_from_rs | grep aarch64`, then rebuild the previously failing target (the rs_core.h generation action) and re-dispatch the arm64 Chromium build workflow; expect the graph to clear the failing step and reach the next unknown (internal record).
6. Check `buildtools/linux64-format/clang-format` in the same pass, since the bindings pipeline references it; swap in an aarch64 clang-format if it fails to exec (internal record).
7. Persist: record the fix in the host state and in the arm64 Linux CI doc, and make re-installation idempotent, because the binary is a host-tool artifact that future re-syncs of `third_party/rust-toolchain` will clobber; the build workflow or a bootstrap script should re-install it on every sync (internal record).

## What the toolchain-side evidence adds

The upstream integration work confirms the coupling points the recipe touches. Chromium's tools/rust history contains "[crubit] Link cc_bindings_from_rs with Chromium's toolchain", the exact link-level fix the recipe reproduces by building against the toolchain rustc (source: https://chromium.googlesource.com/chromium/src/tools/rust/, w=0.59). The same directory documents "Local development. Rolling Crubit tools. Building and testing Crubit locally", with the Rust build including LLVM for rustc and Clang for bindgen and crubit (source: https://chromium.googlesource.com/chromium/src/tools/rust/, w=0.61).

The known failure modes of building cc_bindings_from_rs against a Chromium toolchain are documented in the tracker. Issue 460482110, "Errors when building cc_bindings_from_rs using Chromium's Rust toolchain", records that prebuilt toolchain sysroots may lack crates the build expects: "You'll have to directly add them to the sysroot or the list of --extern flags if you want to build with stable or beta. Crubit itself also makes use of unstable internal rustc APIs, so you'll need to set RUSTC_BOOTSTRAP in order to allow the use of nightly features with a stable/beta toolchain" (source: https://issues.chromium.org/issues/460482110/resources, w=0.86). That issue is the strongest public corroboration that the recipe's core risk, rustc-version coupling, is real and already encountered upstream.

## The risk register

1. rustc-dev bindings drift. crubit at the pinned revision may not compile against the toolchain's rustc if its rustc-dev bindings have drifted. Mitigation: build with the exact toolchain rustc, from the same directory that supplies librustc_driver (internal record). The version-gate failure mode has a concrete public example: issue 506182737 describes Chromium's rustc reporting a version that makes crubit's `rustversion` gates select the wrong code branch, needing `#[rustversion::before(...)]` instead of `#[rustversion::since(...)]` for week-old toolchains (source: https://issues.chromium.org/issues/506182737, w=0.45, weak).
2. --locked resolution on aarch64. The vendored lockfile may lack aarch64 platform-specific resolution and fail under `--locked`; regenerate the lockfile if so (internal record). The rustc-dev prerequisite itself is documented by crubit: x.py-installed rustc must include the rustc-dev component (source: https://crubit.rs/overview/cargo_build.html, w=0.84).
3. RUSTC_BOOTSTRAP and sysroot crates. If the build runs against a stable or beta-flavored toolchain, the --extern/sysroot adjustments from issue 460482110 apply (source: https://issues.chromium.org/issues/460482110/resources, w=0.86).
4. clang-format. The x86_64 `buildtools/linux64-format/clang-format` may need replacement on aarch64 (internal record). This is the same pattern the theoparis pipeline documents for other prebuilt binaries, such as node.js shipped for the wrong architecture (source: https://github.com/theoparis/chromium-linux-arm64, w=0.48, weak).
5. Clobbering on re-sync. Any `gclient sync` that refreshes `third_party/rust-toolchain` restores the x86_64 binary; the fix must be idempotently re-applied (internal record).

None of these risks are structural: each has a bounded, mechanical mitigation, and the prerequisite layer, a working native aarch64 rustc and cargo with the rustc-dev component, was verified in place before the plan was written (internal record). The survey's overall judgment holds: the first aarch64 cc_bindings_from_rs host-tool build is a mechanical problem, not an architectural one.
