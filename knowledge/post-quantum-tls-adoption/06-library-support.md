# 06. TLS library support: OpenSSL 3.5, Go, and the FIPS-mode question

Scope: what OpenSSL and Go ship by default for X25519MLKEM768, the GODEBUG and configuration toggles, known bugs, and what FIPS mode allows.

## OpenSSL 3.5

OpenSSL 3.5.0 is a feature release whose release notes record a significant default change: the default TLS supported groups list has been changed to include and prefer hybrid PQC KEM groups (source: https://github.com/openssl/openssl/discussions/27299, weight 0.79). Per the source corpus (yubiOS refs/post-quantum-tls-adoption-2026-07-23.md), OpenSSL 3.5 (released 2025) ships ML-KEM natively in both the default and FIPS providers, prefers hybrid groups in the default TLS supported groups, and sends X25519MLKEM768 plus X25519 as default key shares; it also carries the SecP256r1MLKEM768 and SecP384r1MLKEM1024 hybrids (release notes: https://github.com/openssl/openssl/releases/tag/openssl-3.5.0, cited by the source corpus; not separately dug this pass). The 3.5 series is still an active patch line, with 3.5.8 shipping security fixes (source: https://openssl-library.org/news/openssl-3.5-notes/, weight 0.92), and a 3.6 series now also exists (source: https://github.com/openssl/openssl/releases, weight 0.93).

Practitioner guidance treats the TLS handshake as the low-hanging fruit of the migration and recommends compiling NGINX against OpenSSL 3.5 and running it as a reverse proxy with the hybrid X25519-ML-KEM-768 key exchange (source: https://www.cryptomathic.com/blog/quantum-ready-cryptography-with-openssl-3.5-on-rhel-9.6, weight 0.75). That is the concrete recipe for the origin-leg gap described elsewhere in this corpus.

## Go

Go 1.24 made the switch: the post-quantum X25519MLKEM768 key exchange mechanism is supported and enabled by default when Config.CurvePreferences is nil, and the GODEBUG setting tlsmlkem=0 reverts the default (source: https://go.dev/doc/go1.24, weight 0.74). The design issue behind it proposed removing X25519Kyber768Draft00, adding X25519MLKEM768 and SecP256r1MLKEM768, enabling both by default, and sending X25519MLKEM768 plus X25519 key shares by default (source: https://github.com/golang/go/issues/69985, weight 0.83).

The default has had rough edges. A bug report documents a case where the ML-KEM support needed GODEBUG=tlsmlkem=1 to be enabled, contrary to the documented Go 1.24 behavior, and notes the setting exists partly for dealing with buggy TLS servers that do not handle large records correctly (source: https://github.com/golang/go/issues/76677, weight 0.94). Go's GODEBUG surface for TLS includes tlsmlkem and tlssecpmlkem among its crypto/tls entries (source: https://silo.pigsty.io/blog/design/tls-parameter-pinning/, weight 0.60, marginal backing); the tlssecpmlkem toggle is the switch for the NIST-curve hybrids that later versions add. The crypto/tls package reference is the canonical configuration surface via tls.Config (source: https://pkg.go.dev/crypto/tls, weight 0.94).

Later Go versions per the source corpus: 1.25 added no new default group but confirmed X25519MLKEM768 is allowed in FIPS 140-3 mode, and 1.26 adds SecP256r1MLKEM768 and SecP384r1MLKEM1024 as additional default hybrids, toggleable via Config.CurvePreferences or GODEBUG=tlssecpmlkem=0, plus new crypto/mlkem and crypto/hpke packages (cited from go.dev/doc/go1.25 and go.dev/doc/go1.26 in the source corpus; these two release-note URLs were not independently retrieved in this dig, so treat the version-specific details as source-corpus attested rather than dig-weighted).

## Other stacks

The source corpus records BoringSSL, the TLS stack Chrome uses, as supporting X25519MLKEM768, and GnuTLS 3.8.5+ as partial support (yubiOS refs source doc; not separately dug). For library selection the load-bearing line is: OpenSSL 3.5+ and Go 1.24+ have the hybrid on by default, so most modern toolchains negotiate PQ without any operator action, and the residual risk lives in old versions, FIPS policy toggles, and custom CurvePreferences that pin the group list.
## The default-on era and its failure modes

The significance of these library defaults is that adoption stopped being a per-application decision. When OpenSSL 3.5 prefers hybrid PQC groups in its default supported groups list (source: https://github.com/openssl/openssl/discussions/27299, weight 0.79) and Go 1.24 enables X25519MLKEM768 unless CurvePreferences is set (source: https://go.dev/doc/go1.24, weight 0.74), most newly built or upgraded TLS endpoints negotiate the hybrid without anyone deciding to. The residual failure modes are therefore specific and enumerable: old library versions still in production, custom group preference lists pinned by hand, enterprise policy that disables the feature, and buggy peers that mishandle large records, the exact failure class the tlsmlkem toggle exists to route around (source: https://github.com/golang/go/issues/76677, weight 0.94).

An audit checklist falls out of this. Pin or verify the library floor, OpenSSL 3.5 or later, Go 1.24 or later; inspect any code that sets CurvePreferences or supported_groups explicitly; confirm FIPS-mode policy permits the hybrid where FIPS compliance is claimed; and keep the GODEBUG toggles documented in your runbook as the emergency revert path (sources: https://go.dev/doc/go1.24, weight 0.74; https://silo.pigsty.io/blog/design/tls-parameter-pinning/, weight 0.60, marginal backing).
