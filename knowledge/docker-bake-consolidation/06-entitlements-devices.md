# Entitlements and devices: what bake will not pretend to grant

Scope: privileged entitlements (two-step declaration and grant), bake filesystem entitlements, `RUN --device` with labs syntax and CDI registration, and the argument for keeping `/dev/kvm` lanes outside bake.

Buildx and BuildKit operate with restricted permissions by default to protect users from unintended side effects. Privileged operations are gated by entitlements, and granting them is a two-step process: first the build (target) declares the entitlements it requires, then the user grants them at invocation with `--allow` or confirms interactively ([Bake file reference, w 0.96](https://docs.docker.com/build/bake/reference/); [docker buildx build, w 0.60](https://docs.docker.com/reference/cli/docker/buildx/build/)). The two core BuildKit entitlements are `network.host` (for `RUN --network=host`) and `security.insecure` (for `RUN --security=insecure`, privileged containers outside the default sandbox) ([Bake file reference, w 0.96](https://docs.docker.com/build/bake/reference/)). In a bake file, `target.entitlements` declares what a target needs ([Bake file reference, w 0.96](https://docs.docker.com/build/bake/reference/); [bake-reference.md, w 0.96](https://github.com/docker/buildx/blob/master/docs/bake-reference.md)). The declaration-grant split is deliberate design: "this is to ensure that the user is aware of the possibly insecure permissions they are granting to the build process" ([Bake file reference, w 0.96](https://docs.docker.com/build/bake/reference/)). The same two-step rule applies to network mode: setting `network = "host"` on a target also requires granting the `network.host` entitlement with `--allow=network.host` or interactive confirmation ([Bake file reference, w 0.96](https://docs.docker.com/build/bake/reference/)).

Bake extends the entitlement model with filesystem grants: `--allow fs=<path|*>` for read and write outside the working directory, plus `fs.read=` and `fs.write=` variants, and `--allow=buildx.local.delete` for local outputs with `mode=delete` ([docker buildx bake, w 0.96](https://docs.docker.com/reference/cli/docker/buildx/bake/); [buildx_bake.md, w 0.94](https://github.com/docker/buildx/blob/master/docs/reference/buildx_bake.md)).

## Devices are a different animal

`RUN --device` mounts a device into a build step through the Container Device Interface (CDI). The Dockerfile instruction is lab-only: it ships in the `labs` channel of the Dockerfile frontend, available since Dockerfile frontend v1.14.0-labs, and is not yet in stable syntax. The build requests a device by vendor name and the device must exist in a registered CDI specification file such as `/etc/cdi/foo.yaml`; a build that requests an unregistered device fails with "device ... is requested by the build but not allowed" ([Container Device Interface (CDI), w 0.13, weak backing](https://docs.docker.com/build/building/cdi/); [cdi.md source, w 0.28, weak backing](https://docs.docker.com/build/building/cdi.md); [Dockerfile reference, w 0.74](https://docs.docker.com/reference/dockerfile/)). Note the official CDI page scored below the 0.5 threshold in this corpus's source-quality pass, so treat its specifics as weakly backed here and verify against your Buildx version.

The yubiOS reading of this is the meaningful design decision: device entitlements require explicit daemon and invocation grants, plus labs syntax and a CDI-registered device ([yubiOS source doc, refs/docker-bake-consolidation-2026-07-17.md]). A generic bake target therefore cannot safely schedule `/dev/kvm` for firmware testing, because access depends on the host daemon's registration state, not on anything the bake file can declare. The self-hosted KVM VM lane remains a host workflow responsibility in GitHub Actions ([yubiOS source doc, refs/docker-bake-consolidation-2026-07-17.md]).

## The boundary in one sentence

Bake models what a build invocation needs; the environment must still grant it. Consolidation into one bake file is safe precisely because everything the file declares (entitlements, outputs, policies) is enforceable at invocation time, while things that depend on host state (KVM devices, QEMU evidence capture, SoftHSM, user namespaces) stay in the workflow layer where the host is visible ([yubiOS source doc, refs/docker-bake-consolidation-2026-07-17.md]).

For CI wiring, the buildx build reference documents the `--allow` grant mechanics on the plain build path ([docker buildx build, w 0.60](https://docs.docker.com/reference/cli/docker/buildx/build/); [buildx_build.md, w 0.83](https://github.com/docker/buildx/blob/master/docs/reference/buildx_build.md)), and the bake reference documents the same flag plus the filesystem extensions ([docker buildx bake, w 0.96](https://docs.docker.com/reference/cli/docker/buildx/bake/)). Community discussion of entitlement ergonomics (for example, persistent `fs.read` grants) shows the model is still evolving, and that discussion thread carries weak backing as a source ([buildx discussion, w 0.24, weak backing](https://github.com/docker/buildx/discussions/2869)).
