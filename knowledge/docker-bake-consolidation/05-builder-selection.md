# Builder selection: create --use versus bake --builder

Scope: how a buildx builder becomes "current" in the Docker configuration, how the bake `--builder` flag overrides it, and why containerized CI jobs create a user-scoped named builder before invoking bake.

`docker buildx create` makes a new builder instance, and its `--use` flag "automatically switches the current builder to the newly created one", equivalent to running `docker buildx use $(docker buildx create ...)` ([docker buildx create, w 0.65](https://docs.docker.com/reference/cli/docker/buildx/create/); [buildx_create docs, w 0.82, via buildx repo](https://github.com/docker/buildx)). The "current builder" is a property of the invoking Docker CLI's configuration context, not of the bake file: whichever builder was last selected with `--use` (or `docker buildx use`) is the one a plain `docker buildx bake` invocation picks up ([docker buildx create, w 0.65](https://docs.docker.com/reference/cli/docker/buildx/create/)).

Bake keeps an escape hatch: the `--builder` flag on `docker buildx bake` "overrides the configured builder instance" for that invocation ([docker buildx bake, w 0.96](https://docs.docker.com/reference/cli/docker/buildx/bake/); [buildx_bake.md, w 0.94](https://github.com/docker/buildx/blob/master/docs/reference/buildx_bake.md)). So there are two layers: the persisted selection (written by `create --use`) and the per-invocation override (`--builder`).

## Why containerized CI cares

The yubiOS consolidation exploits this layering deliberately ([yubiOS source doc, refs/docker-bake-consolidation-2026-07-17.md]). Containerized jobs create a user-scoped builder named `hardened` with `buildx create --use`, in the same Docker configuration that later invokes bake. That matters because:

1. A GitHub Actions container job has its own Docker configuration scope. A builder created with a global or host-level selection may not be visible where the bake call runs. Creating the builder and selecting it inside the same job's configuration removes the ambiguity.
2. The `--builder` override exists for cases where the configured selection is not what the job wants, for example when a workflow step changed the selection or when targeting a specific named builder across steps.
3. Keeping creation and invocation in one Docker configuration means the "current builder" is deterministic at bake time without threading `--builder` through every call.

The buildx architecture documentation describes how builder instances relate to Docker contexts and drivers (docker, docker-container, kubernetes, remote), which is the model behind user-scoped selections ([Docker GitHub Builder architecture, w 0.52](https://docs.docker.com/build/ci/github-actions/github-builder/architecture/); [docker buildx create, w 0.65](https://docs.docker.com/reference/cli/docker/buildx/create/)). The `create` reference lists exactly those four available drivers and pairs `--use` with `--bootstrap` (boot the builder after creation), which is the sequence CI jobs want: create a `docker-container` driver builder, bootstrap it, and select it in one step ([docker buildx create, w 0.65](https://docs.docker.com/reference/cli/docker/buildx/create/)).

There is also a determinism argument for the user-scoped pattern. A builder created without a `--name` gets a generated name, and the "current" selection is global to the CLI configuration, so two jobs on the same runner can clobber each other's selection. A named, user-scoped builder (`hardened`) plus an explicit selection inside the job makes the state local to the job's Docker configuration directory, which is what makes the bake invocation deterministic regardless of what ran before it on the machine ([docker buildx create, w 0.65](https://docs.docker.com/reference/cli/docker/buildx/create/); [yubiOS source doc, refs/docker-bake-consolidation-2026-07-17.md]).

## Interaction with the rest of the bake file

Builder selection is invisible in the bake file itself by design. The HCL file describes what to build (targets, platforms, outputs, policies), while the environment decides where to build it. The one place they meet is when entitlements or device access require a specific daemon capability: the yubiOS KVM lane stays a host-workflow responsibility precisely because the builder's daemon, not the bake definition, is what must hold `/dev/kvm` access ([yubiOS source doc, refs/docker-bake-consolidation-2026-07-17.md]; see the entitlements doc in this corpus).

For teams consolidating workflows, the practical checklist is: create the builder once per job with `--driver docker-container` (the driver documented for hardened, multi-platform CI builds) plus `--bootstrap`, select it with `--use` in the same Docker configuration, then invoke bake without extra flags; use `--builder` only to override deliberately ([docker buildx create, w 0.65](https://docs.docker.com/reference/cli/docker/buildx/create/); [docker buildx bake, w 0.96](https://docs.docker.com/reference/cli/docker/buildx/bake/)). The docker/bake-action GitHub Action wraps this pattern for hosted runners ([docker/bake-action, w 0.82](https://github.com/docker/bake-action)).
