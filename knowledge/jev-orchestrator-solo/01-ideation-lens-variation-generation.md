# Ideation lenses and variation generation in the jev-orchestrator-solo framing log

Scope: how the 7 design variations for the Jev v2 gated-approval orchestrator were generated by applying named ideation lenses (simplification, constraint removal, inversion, audience shift, combination) to the Jev v2 control diagram.

## The framing log's variation set

The primary input for this corpus is the ideate-solo framing log dated 2026-09-30 (source doc, extracted from yubi-OS/yubiOS refs/). It records 7 variations generated against one problem statement: how to turn the Jev v2 control architecture (ingest, understand, decide, gate, execute, verify, continue/terminal, with a fail-closed policy gate and a human review loop) into a concrete skill plus API surface on the steady-orbit worker. Each variation carries one lens label, which is the key structural fact of the log: the generator did not free-associate, it rotated through named lenses.

The lenses applied map cleanly onto established ideation technique families:

- V1, Simplification: strip the diagram to a thin controller (state machine, gate, review) and use plain HTTP fetch as the tool layer.
- V2, Constraint removal: port everything, including tenants, the improve-loop, and provider adapters.
- V3, Inversion: gate-as-library, embedding the control flow locally in the skill with no central service.
- V4 and V7, Audience shift: make n8n workflows the caller (V4) or make Sauna sessions the caller (V7).
- V5, Combination: extend the existing outcomes ledger, treating jev as a verdict type on the append-only pattern already on the worker.
- V6, Inversion again but riskier: an LLM-scored policy gate feeding jev probabilities into the gate.

## Why named lenses instead of open brainstorming

Structured ideation techniques exist to counteract unguided generation: a well-chosen technique provides rules or constraints that redirect thinking and create the conditions for divergent thinking, generating many distinct ideas before any evaluation takes place (https://dovetail.com/design-thinking/ideation-techniques/, jev weight 0.32, weak backing). The framing log's behavior matches this pattern: 7 variations were generated and logged with their lenses before any scoring happened.

The lens set itself is a recognizable slice of the canonical prompt families. The SCAMPER technique uses 7 prompts (Substitute, Combine, Adapt, Modify, Put to another use, Eliminate, Reverse/Rearrange), each representing a different lens through which participants examine an existing design (https://www.6sigma.us/lean-tools/scamper-technique/, jev weight 0.46, weak backing; same structure described at https://www.figma.com/resource-library/lateral-thinking-explained/, jev weight 0.58, authoritative backing). Read against SCAMPER: V5 is Combine, V1 is Eliminate taken to an architecture level, V3 and V6 are Reverse (inverting who holds the gate), and V4/V7 are a substitute-the-user move. The framing log did not cite SCAMPER, but its lens vocabulary is the same move: apply a fixed transformation verb to a fixed artifact (the Jev v2 diagram) to force a distinct variant.

Constraint removal is also documented as a deliberate prompt: "what would you build if you had no technical constraints, no budget constraints, no political constraints?" then work backward to what is feasible (https://mcpservers.org/agent-skills/anthropic/product-brainstorming, jev weight 0.29, weak backing). V2 is exactly this prompt applied and then exactly this prompt's fate: it scored 10, the lowest total, because removing the constraints (tenants, adapters, auto-activation) also removed testability and added switching cost.

## What the log shows about generation discipline

Three discipline signals in the log are worth recording:

1. One problem statement, held fixed. All 7 variations answer the same question, so scores are comparable. Ideation literature treats a stable problem frame as the precondition for meaningful divergence (https://ixdf.org/literature/article/introduction-to-the-essential-ideation-techniques-which-are-the-heart-of-design-thinking, jev weight 0.71, authoritative backing, on ideation as the heart of the design process).
2. Lenses are assigned, not inferred after the fact. Each row of the generation log names its lens, which makes the later failure analysis attributable (V2 fails because constraint removal overscopes; V6 fails because the inversion violates an invariant of the source diagram).
3. The count is small and deliberate: 7 variations, not 30. For a solo run (ideate-solo, no dialogue), a bounded variation set keeps the scoring step tractable while still spanning simplification, expansion, inversion, and audience lenses.

The one lens absent from the log is Substitute at the technology level (no variation proposes a different database or runtime); all 7 variations accept the steady-orbit worker as fixed. That is consistent with the problem statement scoping the solution space to "a concrete skill plus API surface on the steady-orbit worker" from the start.
