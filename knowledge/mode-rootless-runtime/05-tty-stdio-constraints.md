# 05: TTY and stdio constraints: what each mode does to output

Scope: what TTY presence or absence does to rootless tooling: prompts that hang batch jobs, progress bars and colors, NO_COLOR, --quiet flags, and stdout/stderr routed to journald in daemon mode.

## One detection, many behaviors

The same command should behave differently when a person is watching and when it runs inside a pipeline or a CI job. Color, progress bars, prompts, table widths, and pagers all depend on that single detection, and getting it wrong is how a tool ends up writing escape sequences into a log file or hanging a build waiting for an answer; isatty checks on stdout and stdin drive the output decisions (w=0.39, weak, https://www.python-cli-toolcraft.com/advanced-input-parsing-user-experience/working-with-stdin-stdout-and-pipes/detecting-tty-and-adapting-output/). Terminal-detection logic for interactive shells, piped output, and CI/CD environments is its own documented discipline (w=0.40, weak, https://deska.dev/blog/terminal-detection-tty).

The three modes in this corpus land on all three points of that spectrum. Interactive mode has a TTY, so progress bars and prompts are correct behavior. Batch mode has none, and daemon mode has none plus a journald sink. The yubiOS convention (source ref: yubi-OS/yubiOS refs/mode-rootless-runtime-2026-09-01) encodes this as one row of the mode table: TTY yes in interactive, no with NO_COLOR=1 and --quiet in batch, no with journald in daemon.

## The batch hang is the canonical failure

The failure mode that defines the mode axis is the batch hang. Processes hang waiting for input on a non-existent interactive stream, and the fixes are narrow but critical: check terminal state at runtime with isatty or equivalent, strip or adjust ANSI codes based on detection, and provide flags to override interactivity (w=0.20, weak, https://hoop.dev/blog/solving-silent-terminal-failures-understanding-and-fixing-tty-pain-points). The same analysis documents the container twist: inside containers, TTY allocation alters program behavior, some CLI tools switch modes when they detect an interactive terminal, without a TTY you lose color output, progress bars, and prompt handling, and with a TTY in the wrong context you can deadlock automated jobs waiting for input that never comes (w=0.20, weak, https://hoop.dev/blog/mastering-tty-preventing-build-hangs-and-ci-pipeline-deadlocks).

A concrete recorded instance: a tool running in quiet mode still waited for a y/n answer after a git warning, breaking the non-interactive nature of quiet mode and hanging automated environments indefinitely (w=0.80, https://github.com/openai/codex/issues/1340). The structural fix is a non-interactive entrypoint invoked from scripts and CI jobs instead of an interactive TUI (w=0.82, https://learn.chatgpt.com/docs/non-interactive-mode). Well-behaved non-TTY tools implement the full fallback ladder: prompts resolve to flags, defaults, or optional values; a required value with no flag exits with a usage code rather than waiting; spinners stop; progress prints as sequential lines; ANSI styling is stripped (w=0.20, weak, https://www.oscli.dev/docs/non-interactive-and-ci).

## Daemon stdio: journald is the terminal

In daemon mode there is no terminal to detect, so the question becomes where the stream goes. journald is the systemd service for collecting and storing log data (w=0.64, https://developer.toradex.com/software/linux-resources/linux-features/persistent-journald-logging), and systemd itself, running as PID 1, provides the service management that routes unit output into it (w=0.82, https://systemd.io/). Operators inspect a unit's stdout and stderr through journald tooling rather than a console (w=0.09, weak, https://unix.stackexchange.com/questions/20399/view-stdoutstderr-of-systemd-service), though redirection to console or syslog identifiers remains possible with unit configuration (w=0.03, weak, https://stackoverflow.com/questions/37585758/how-to-redirect-output-of-systemd-service-to-a-file).

The practical constraint this places on rootless tooling in daemon mode: anything animated or prompt-driven is unusable, because its output lands in a log store nobody watches live and any prompt would block a service with no one to answer it. The yubiOS convention (source ref: yubi-OS/yubiOS refs/mode-rootless-runtime-2026-09-01) is therefore that daemon-facing invocations of rootless tools use line-oriented flags and that the rc=77 SKIP outcome is recorded in the journal as the unit's evidence trail.

## Why the same tool passes one mode and fails another

The detection story explains the cross-mode asymmetry recorded in the source ref. A tool that prompts only when stdin is a TTY behaves perfectly in interactive mode, hangs batch jobs (w=0.20, weak, https://hoop.dev/blog/solving-silent-terminal-failures-understanding-and-fixing-tty-pain-points), and hangs daemons. A tool that colors output unconditionally corrupts journald entries with escape sequences (w=0.39, weak, https://www.python-cli-toolcraft.com/advanced-input-parsing-user-experience/working-with-stdin-stdout-and-pipes/detecting-tty-and-adapting-output/). A tool that assumes a wide terminal emits broken tables into CI logs. None of these are bugs in a single mode; they are mode-dependent contracts, which is why the yubiOS rule requires exercising a rootless tool in at least two of the three modes before wiring it into a workflow (doc 08).

## Summary

TTY presence is the axis along which the three modes differ most visibly. Interactive mode can rely on detection being true (w=0.39, weak, https://www.python-cli-toolcraft.com/advanced-input-parsing-user-experience/working-with-stdin-stdout-and-pipes/detecting-tty-and-adapting-output/), batch mode must suppress prompts or hang (w=0.80, https://github.com/openai/codex/issues/1340), and daemon mode replaces the terminal with journald (w=0.64, https://developer.toradex.com/software/linux-resources/linux-features/persistent-journald-logging). NO_COLOR, --quiet, and line-oriented flags are the batch and daemon adaptations; a prompt in either of those modes is a defect, not an inconvenience.
