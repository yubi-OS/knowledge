# 02 - Composefs Kernel Floors

Scope: the kernel version floors per composefs mode: data-only OverlayFS at kernel 6.5 and above, the verity=require mount option at 6.6 and above, and file-backed EROFS at 6.12 and above, and how a digest bump re-tests each floor.

## Why the floor depends on the mode

composefs is not one kernel feature. It combines several underlying Linux features to provide read-only mountable filesystem trees stacked on top of an underlying lower filesystem (source: https://github.com/composefs/composefs, jev weight 0.91). The three ingredients are OverlayFS for the mount model, EROFS for the metadata image, and fs-verity for integrity verification (source: https://deepwiki.com/composefs/composefs, weak backing, jev weight 0.18). Because each ingredient landed in the kernel at a different time, the minimum kernel version depends on which composefs mode the build uses. That is why the yubiOS floor is a table of three modes rather than one number, and why a base-image digest bump that changes the kernel can break one mode while leaving the others intact.

## Mode 1: data-only OverlayFS, kernel 6.5 and above

The primary backing configuration composes an EROFS metadata image with an OverlayFS data-only layer. Kernel documentation describes OverlayFS as the mechanism that overlays one filesystem on top of another (source: https://www.kernel.org/doc/html/latest/filesystems/overlayfs.html, jev weight 0.95). The data-only layer support that composefs needs was added to OverlayFS in kernel 6.5 (source: https://blog.desdelinux.net/en/composefs-file-system-is-now-stable/, jev weight 0.68, corroborating source doc: refs/package-floor-verification-checklist-2026-08-04.md section 2.1). The yubiOS convention: pick the lowest-supported kernel in PINNED.md as the floor; production builds use the pinned digest's kernel, and the dev image may run a newer kernel as long as it stays at or above the floor (source doc: refs/package-floor-verification-checklist-2026-08-04.md section 2.1).

## Mode 2: verity=require, kernel 6.6 and above

The stronger mode enforces the composefs signed catalog at mount time: the verity=require mount option requires all files in the image to have valid fs-verity digests before the mount succeeds (source: https://deepwiki.com/composefs/composefs/2.2-mounting-images, weak backing, jev weight 0.13; mode floor source doc: refs/package-floor-verification-checklist-2026-08-04.md section 2.1). The composefs mount flow also supports validating the image against a specified fs-verity digest before mounting (same source, weak backing). Because verity enforcement depends on OverlayFS verity support that arrived after 6.5, the floor for this mode is 6.6. A digest bump whose new kernel sits between 6.5 and 6.6 keeps the primary mode alive but silently downgrades the enforcement mode: the mount works, the guarantee does not. This is the failure shape that makes the mode-specific table necessary rather than paranoid.

## Mode 3: file-backed EROFS, kernel 6.12 and above

The alternate backing configuration uses file-backed EROFS instead of the data-only OverlayFS arrangement. EROFS functionality meets composefs requirements starting with kernel 5.15 for the base filesystem, with the composefs-specific integration completed through the OverlayFS patches (source: https://blog.desdelinux.net/en/composefs-file-system-is-now-stable/, jev weight 0.68). The file-backed EROFS variant composefs uses requires kernel 6.12 (source doc: refs/package-floor-verification-checklist-2026-08-04.md section 2.1). The sealing design combines an EROFS image for metadata with a content-addressed object store for data, going further than fs-verity alone, which can only verify individual file contents, and avoiding the fixed-partition requirement of dm-verity (source: https://scrivano.org/posts/2026-06-05-sealing-with-composefs/, jev weight 0.50 in this dig's second query, weak in the first).

## Real-world deployment evidence

The floors are not speculative. Fedora CoreOS enabled composefs by default starting in Fedora 41, describing it as an overlay filesystem where the data comes from the usual ostree deployment and the metadata is in the composefs file (source: https://docs.fedoraproject.org/en-US/fedora-coreos/composefs/, jev weight 0.87). The ostree integration documents the same design: when ostree is compiled with composefs support, a composefs file corresponding to the deployment tree is generated by default (source: https://ostreedev.github.io/ostree/composefs/, jev weight 0.81). The ostree docs also name the security motivation in floor terms: if an older version of the OS has a security flaw, you cannot boot a new fixed signed initrd and have it boot the older flawed userspace, which is exactly the downgrade the verity=require mode is built to prevent (same source).

Tool-level support follows the same version lines. composefs requires overlayfs and EROFS support; fs-verity is optional; if the host kernel lacks these features, composefs cannot provide its intended guarantees and mounts will fail (source: https://zairalabs.ai/guide/tools/composefs/, weak backing, jev weight 0.23).

## Verification against a new digest

When a base-image digest rotates, the kernel version in the new image is checked with `rpm -q kernel` inside the pulled image and compared against the mode table above (source doc: refs/package-floor-verification-checklist-2026-08-04.md section 3.3). The pass criterion is not a single number: the check compares the new kernel against the floor required by the composefs mode the build actually uses. If the kernel regressed below the mode's floor, the bump is aborted, a new issue is filed, and the pin is not committed. A kernel that passes the primary mode floor but fails the verity=require floor gets the same treatment when the build uses enforced verification, because the catalog-enforcement guarantee is the point of the mode.
