# 04 - bootc Floor: Split Kernel and Rootfs

Scope: the bootc version floors that constrain the base image: `bootc container split-kernel-and-rootfs` at v1.16.4 and above, the composefs backend for `bootc install to-filesystem` at v1.16.3 and above, with v1.16.6 as the yubiOS target.

## Why bootc has its own floor

bootc is the mechanism that boots and upgrades the host system from container images (source: https://github.com/bootc-dev/bootc, jev weight 0.83). Because yubiOS's install-time flows call specific bootc subcommands that were added or stabilized in specific releases, the bootc floor is a feature floor rather than a general minimum. The yubiOS target is v1.16.6, and the build pipeline depends on v1.16.4 or above for the Phase 2 kernel-and-rootfs split (source doc: refs/package-floor-verification-checklist-2026-08-04.md section 2.3).

## The split-kernel-and-rootfs subcommand: v1.16.4 and above

The `bootc container split-kernel-and-rootfs` subcommand extracts the kernel and initramfs from the current root filesystem and places them in /kernel/<kernel-version>/ with filenames vmlinuz and initramfs.img; the man page also documents extracting kernel files from a mounted container rootfs for build-time use (source: https://www.mankier.com/8/bootc-container-split-kernel-and-rootfs, jev weight 0.57). The subcommand is defined as an operation executable as part of a container build, under the `bootc container` group of subcommands (source: https://www.mankier.com/8/bootc-container, weak backing, jev weight 0.25). This is the Phase 2 BLSConfig wiring dependency tracked as OMN-150: the sealed composefs Phase 2 install-time BLSConfig wiring requires bootc 1.16.4 or above (source doc: refs/package-floor-verification-checklist-2026-08-04.md sections 2.3 and 8). A digest bump shipping bootc below v1.16.4 removes the subcommand the split flow calls, so the check compares `rpm -q bootc` against v1.16.4 and aborts the bump on regression.

## The composefs backend for install: v1.16.3 and above

The second floor is the composefs storage backend stability line. `bootc install to-filesystem` is the install variant where the root filesystem alongside any necessary platform partitions is set up externally, and bootc installs into the prepared structure (source: https://www.mankier.com/8/bootc-install-to-filesystem, weak backing, jev weight 0.35). The upstream man source documents the finalize step: by default the installation finalizes the target filesystem by invoking fstrim and similar operations, finally mounting it readonly, with an option to skip those operations (source: https://github.com/bootc-dev/bootc/blob/main/docs/src/man/bootc-install-to-filesystem.8.md, jev weight 0.92). Fedora's bootc storage documentation describes the same pattern for advanced installs: you can set up the target block storage and filesystem however you desire via external tools, then have bootc install into it (source: https://docs.fedoraproject.org/en-US/bootc/storage/, jev weight 0.87).

The composefs backend for this install path is an experimental storage backend that uses composefs with EROFS images and fs-verity verification (source: https://deepwiki.com/bootc-dev/bootc/2.3.2-composefs-backend, weak backing, jev weight 0.57). The yubiOS floor for the composefs backend being stable in `bootc install to-filesystem --composefs-backend` is v1.16.3 (source doc: refs/package-floor-verification-checklist-2026-08-04.md section 2.3). Practitioner experience shows why the backend choice matters at install time: install tooling that assumes the ostree backend fails on composefs deployments, for example post-install steps that call ostree admin --print-current-dir to locate the deployment directory (source: https://github.com/dylanmtaylor/bootc-installer/blob/dev/docs/superpowers/specs/2026-03-29-composefs-fisherman-design.md, weak backing, jev weight 0.11).

## composefs is the default on Fedora and CentOS bootc

The context that makes these floors load-bearing: Fedora and CentOS bootc enable the use of composefs for the root filesystem by default, which is a key difference from other ostree-using variants (source: https://docs.fedoraproject.org/en-US/bootc/filesystem/, jev weight 0.90). This means the kernel floors in doc 02 and the bootc floors here are not independent checks that rarely bind at the same time. A single digest bump changes both the kernel and the bootc package, and the composefs mode the build depends on sits at the intersection: kernel must clear the mode floor, bootc must clear the backend floor, and both must hold simultaneously.

## Building derived images on a new base

When the digest rotates, derived images are rebuilt on the new base using the same layering model that made bootc adoption practical: the original Docker container model of using layers to model applications, applied to bootable host systems (source: https://docs.fedoraproject.org/en-US/bootc/building-containers/, jev weight 0.87). For size and reproducibility, the bootc-base-imagectl rechunk subcommand splits the filesystem into content-addressed, reproducible layers with precomputed SELinux labeling (source: https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/10/html/using_image_mode_for_rhel_to_build_deploy_and_manage_operating_systems/generating-a-custom-minimal-base-image, jev weight 0.90). The rechunk step is relevant to floor verification because it operates on the built image after the base is resolved, so a floor regression introduced by the new digest surfaces before or during this step, not after.

## Verification implication

The pre-bump check for bootc is `rpm -q bootc` against the v1.16.4 floor, with the post-bump cascade re-running the same check on the rebuilt dev image (source doc: refs/package-floor-verification-checklist-2026-08-04.md sections 3.3 and 4.2). On fail, the bump is aborted and a new issue is filed, exactly as for kernel and systemd regressions. The v1.16.6 target is the preferred state; v1.16.4 is the hard abort line because below it the split-kernel-and-rootfs subcommand is missing.
