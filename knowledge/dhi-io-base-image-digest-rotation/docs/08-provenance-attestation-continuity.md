# Provenance and attestation continuity

Scope: Keeping SLSA provenance, Sigstore signatures, and transparency-log coverage continuous across a rotation: verifying the new base image digest carries its attestations.

## The continuity question a rotation must answer

Every attestation is bound to a specific image digest. A rotation changes the digest, which means every verification that was true of the old pin is vacuously true of nothing until re-established against the new one. Continuity, in this doc, means: the NEW digest carries the same classes of attestations the old one did, verified before the pin lands, so the attestation story of downstream builds does not silently degrade.

## SLSA provenance, and where the spec stands

SLSA provenance is an in-toto attestation that describes how an artifact was produced: "the verifiable information about software artifacts describing where, when and how something was produced" [S1]. The v1.0 provenance predicate uses `predicateType: https://slsa.dev/provenance/v1` within the in-toto attestation framework, and its model is explicit about the pieces a verifier checks: the builder.id identifies the build platform, buildType encapsulates the build process, externalParameters are untrusted and MUST be verified downstream, and resolvedDependencies captures the dependencies fetched during the build, such as the specific git commit a repository URI resolved to [S1].

Two spec-level facts worth recording accurately. First, the SLSA site instructs consumers to always use the predicateType URI string rather than what appears in the URL bar, because the URI always resolves to the latest minor version [S1]. Second, the v1.0 provenance page itself is marked "Status: Retired", with version 1.2 named as the current version [S1]. A rotation procedure that checks provenance should therefore verify against the current spec version, not hardcode v1.0 assumptions.

The spec also gives the linkage rule that makes rotation verifiable: record the digest in the provenance and use a separate provenance attestation to link that digest back to version control [S1]. A base image whose provenance does not bind its own digest cannot support this chain.

Google Cloud documents the verification half end to end for a real platform: extract, decode, and verify SLSA build provenance attestations generated by Image Builder inside Artifact Registry [S2]. That is the concrete shape of "the new digest carries its provenance": extract the attestation from the candidate digest, decode it, verify the signature and the subject digest match.

## in-toto as the metadata envelope

The in-toto attestation format is becoming the standard for supply chain metadata, supporting not just SLSA provenance but also SBOMs, vulnerability scans, and custom predicates, with verification wired into admission controllers, deployment scripts, or pull-based GitOps workflows [S3] (weight 0.52, authoritative). For a rotation, that means the continuity check is uniform: the same in-toto envelope carries provenance, SBOM, and scanner attestations for both the old and new digest, so one verification routine covers all of them.

## Rekor and the transparency log

Sigstore's Rekor provides an immutable, tamper-resistant, transparent ledger of signatures and software metadata [S4]. The project documentation describes the API surface: a RESTful server for validation, a transparency log for storage, and a CLI to make and verify entries, query the log for inclusion proofs, perform integrity verification of the log, or retrieve entries by public key or artifact [S5] [S6].

Kyverno's documentation records the integration detail that matters for rotation: cosign uses Rekor, a transparency log service to store signatures, and in Cosign 2.0 verifies Rekor entries for both key-based and identity-based signing [S7]. In practice, a candidate digest that was signed under keyless mode carries its Rekor inclusion evidence with it; verifying the new digest therefore re-confirms its transparency-log entry as part of the standard cosign verify flow (see doc 05).

## The continuity checklist for a rotation

1. Enumerate the attestation classes the OLD digest carried: provenance, SBOM, vulnerability scan, any custom predicates.
2. For the candidate digest, extract and verify each class [S2] [S3].
3. Verify the provenance binds the candidate digest as its subject [S1].
4. Confirm signature verification includes the Rekor/transparency-log check [S7].
5. Record the attestation verification in the rotation commit so the git history shows the new pin was attested at rotation time.
