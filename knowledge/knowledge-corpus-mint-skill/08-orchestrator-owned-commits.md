# 08. Orchestrator-owned commits

Scope: Why the orchestrator rather than each subagent owns the single atomic commit in a mint: avoiding branch races across parallel agents, one reviewable PR, and wave-based cadence for multi-corpus runs.

When several author subagents run in parallel against one repository, the commit topology is a design decision, not an accident. The mint assigns the commit to the orchestrator: subagents return markdown, and the orchestrator assembles one atomic tree containing all docs plus the research DB, then lands it on one branch and one draft PR. This is a deliberate inversion of the refresh-sweep pattern, where each of 14 agents pushed its own disjoint branch.

The orchestration-pattern literature frames why. Microsoft's Azure Architecture Center documents the fundamental orchestration patterns for AI agent architectures, including sequential, concurrent, group chat, handoff, and magentic patterns (weight 0.94, https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns). A mint's shape is the concurrent pattern with a centralized collector: agents run concurrently, but every output converges at one point. Atomic Agents' orchestration guide makes the same distinction actionable: multi-agent pipelines chain agents, dynamic routing sends queries to specialists, parallel execution runs agents concurrently, and composition combines agents into larger behaviors (weight 0.76, https://eigenwise.github.io/atomic-agents/guides/orchestration.html). The mint is a composition of a parallel execution stage followed by a single sequential commit stage.

The failure mode being avoided is well documented on the git side. A tool built specifically for this problem, clash, exists to avoid merge conflicts across git worktrees for parallel AI coding agents (weight 0.75, https://github.com/clash-sh/clash), which is direct evidence that N agents committing to overlapping refs is a real operational hazard, not a hypothetical one. Practical guides describe the mitigations agents use when they do share a repo: git worktrees per agent, tmux sessions, and a shared instructions file that partitions responsibility (weight 0.16, weak backing, https://self.md/guides/parallel-ai-agents/; weight 0.44, weak backing, https://baeseokjae.github.io/posts/multi-agent-coding-workflow-2026/). The mint sidesteps the entire worktree problem by construction: no subagent holds a checkout, so there is nothing to conflict over. Coordination-protocol guides make the same point from the negative side, that orchestrating multiple agents without conflicts, deadlocks, or cascading failures is the hard engineering problem of multi-agent systems (weight 0.11, weak backing, https://vinayakajyothi.com/blog/2026-05-09-multi-agent-coordination-protocols/).

The second benefit is reviewability. One atomic commit per corpus means the PR diff is exactly one corpus: its docs, its research DB, its README. A reviewer sees a complete unit with a single verification line, rather than 14 partially-overlapping branches where the corpus only becomes coherent after all of them merge. In a mint where every doc's claims are cross-indexed against a shared archive.json, atomicity is not cosmetic: splitting the landing across branches would let a merged doc reference archive entries that have not landed yet.

The third benefit is the wave cadence at run scale. When a directive requires minting dozens of corpora, the orchestrator runs waves of parallel mints, verifies each wave's PRs after they land, merges, and records the wave in a log. The wave record is append-only, which keeps the run auditable while its scale grows. Coordination guides covering multi-agent work at scale converge on the same hygiene: explicit work items, blocking dependencies, and a human review gate before anything irreversible (weight 0.33, weak backing, https://gascity.com/guide/coordinate-multiple-ai-coding-agents/).

## Sub-claims

1. Concurrent agent execution with a centralized collector is a documented orchestration pattern family member (weight 0.94, https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns).
2. Composition of a parallel execution stage with a single sequential commit stage is a standard agent-composition shape (weight 0.76, https://eigenwise.github.io/atomic-agents/guides/orchestration.html).
3. Merge conflicts across parallel agent workspaces are common enough to have spawned dedicated CLI tooling (weight 0.75, https://github.com/clash-sh/clash).
4. Worktree-per-agent plus shared instruction files is the standard mitigation when agents do share a repo; the mint avoids it by giving subagents no checkout at all (weight 0.16, weak backing, https://self.md/guides/parallel-ai-agents/; weight 0.44, weak backing, https://baeseokjae.github.io/posts/multi-agent-coding-workflow-2026/).
5. Conflict-free multi-agent coordination is identified as the core engineering challenge, which argues for designs that remove shared mutable state (weight 0.11, weak backing, https://vinayakajyothi.com/blog/2026-05-09-multi-agent-coordination-protocols/).
6. Run-scale hygiene is explicit work items, blocking dependencies, and a human review gate (weight 0.33, weak backing, https://gascity.com/guide/coordinate-multiple-ai-coding-agents/).
