# 07. Landing a corpus with the Git Data API

Scope: Landing a corpus in a GitHub repo without cloning: the blob-tree-commit-ref chain, draft PR creation, directory collision checks, and post-push verification by re-fetching and parsing every pushed file.

A mint lands its corpus in the target repository without a working tree: everything goes through GitHub's REST Git database API. The object model is standard git. A Git blob is the object type used to store the contents of each file in a repository, and the file's SHA-1 hash is computed and stored in the blob object (weight 0.72, https://docs.github.com/en/rest/git/blobs). The Git database REST API exists to interact with raw Git objects and to list and update Git references, including branch heads and tags (weight 0.54, https://docs.github.com/rest/reference/git). GitHub's own guide describes the full write chain in five steps: get the current commit SHA, get its tree SHA, create blobs for each new file, create a new tree, create a new commit object with the current commit SHA as parent and the new tree SHA, and finally update the branch reference to point at the new commit SHA (weight 0.59, https://github.com/github/docs/blob/main/content/rest/guides/using-the-rest-api-to-interact-with-your-git-database.md). These low-level object moves are the same operations git itself performs; the git manual classifies the commands that move objects and references between repositories as the plumbing layer (weight 0.73, http://mirrors.edge.kernel.org/pub/software/scm/git/docs/).

For a mint the chain has one guard at the front: a GET on the target directory against the default branch before writing anything. If the corpus directory already exists, the mint stops with a collision report instead of mixing into someone else's corpus. Because sibling mint agents run in parallel against the same repo, this check plus the branch-based landing is what makes concurrent mints safe: each mint creates its own branch, so two agents cannot race on the same ref.

Publishing happens through a pull request, and the PRs API documents the surface: you can list, view, edit, create, and merge pull requests using the REST API (weight 0.68, https://docs.github.com/en/rest/pulls/pulls; endpoint listing at weight 0.90, https://docs.github.com/en/rest/pulls). The mint creates its PR as a draft with a structured body carrying the outline table, the metrics used, the jev usage stats, per-doc source counts, the redo log, the gaps, and the verification line. Draft status is the review gate: the corpus is fully landed and verifiable before it is ever marked ready.

Post-push verification is the step that makes the landing trustworthy. Every pushed research-db JSON file is re-fetched from raw.githubusercontent and parsed, and the PR files endpoint is queried to confirm the research-db files actually appear in the PR diff. A mint whose research-db is missing from the PR is a failed mint, regardless of whether the docs landed. This closes the loop on a real failure class: pushing content as base64-encoded text instead of plain UTF-8 produces files that "land" but do not parse as data.

One operational constraint comes from the tooling environment rather than the API: the entire blob, tree, commit, ref, and PR chain must run in a single shell call when the driving environment has ephemeral state between calls, because the SHAs gathered in step 1 are the inputs for step 2. Bodies larger than about 100 KB go through stdin rather than shell arguments.

## Sub-claims

1. A Git blob stores file content with its SHA-1 hash computed and stored in the blob object (weight 0.72, https://docs.github.com/en/rest/git/blobs).
2. The REST API interacts with raw Git objects and updates references (weight 0.54, https://docs.github.com/rest/reference/git).
3. The write chain is commit SHA, tree SHA, blobs, tree, commit with parent, then ref update (weight 0.59, https://github.com/github/docs/blob/main/content/rest/guides/using-the-rest-api-to-interact-with-your-git-database.md).
4. The PRs API supports list, view, edit, create, and merge operations (weight 0.68, https://docs.github.com/en/rest/pulls/pulls; weight 0.90, https://docs.github.com/en/rest/pulls).
5. Git plumbing commands move objects and references between repositories, which is what the API chain replicates (weight 0.73, http://mirrors.edge.kernel.org/pub/software/scm/git/docs/).
6. Post-push verification re-fetches and parses every pushed JSON file and checks the PR diff for the research-db files (mint contract, applied in this run's final verification line).
