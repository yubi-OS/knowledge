# 02 - RHEL sealed images: the enterprise convergence point

Scope: Red Hat sealed images for image-mode RHEL, the Technology Preview that extends OS integrity from boot through runtime via composefs and fs-verity with a signed UKI, and what it does and does not cover compared to an owner-held hardware key design.

## What shipped

Red Hat's documentation chapter on cryptographic sealing of bootc images, marked Technology Preview, describes the mechanism plainly: a RHEL bootc container image is sealed by computing a cryptographic digest of the root file system and embedding it in a signed Unified Kernel Image. The sealed image provides end-to-end integrity verification from firmware through the file system at boot time ([RHEL 10 docs, Chapter 12, Technology Preview](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/10/html/using_image_mode_for_rhel_to_build_deploy_and_manage_operating_systems/cryptographic-sealing-of-bootc-images-technology-preview), weight 0.92). The same chapter notes that sealed images deploy with standard methods, and that when the image includes a UKI and systemd-boot the system automatically detects the composefs backend ([same docs chapter](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/10/html/using_image_mode_for_rhel_to_build_deploy_and_manage_operating_systems/cryptographic-sealing-of-bootc-images-technology-preview), weight 0.94).

Red Hat's engineering blog frames the same design as a trust-chain story: Secure Boot and a signed UKI already verify the boot chain covering bootloader, kernel, and initramfs; sealed images extend verification into the immutable OS image itself with file-level precision. Using composefs and fs-verity, a cryptographic digest of the OS container image is embedded directly in the signed UKI at build time, and at runtime every file added to the image is individually verified against that digest ([Red Hat blog, Trust at every layer](https://www.redhat.com/en/blog/how-sealed-images-red-hat-enterprise-linux-extend-os-integrity-boot-runtime), weight 0.79).

## The substrate underneath

Sealed images are a feature of image mode for RHEL, which is the downstream product of the upstream bootc Fedora project. Image mode was included as part of RHEL 9.6 and 10 and uses the bootc tool to encapsulate runtimes, drivers, dependencies, and applications ([developers.redhat.com image mode page](https://developers.redhat.com/products/rhel/image-mode), weight 0.88). The RHEL 9 documentation introduces image mode and its build and test workflow for bootc-based images ([RHEL 9 docs, Introducing image mode](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/9/html/using_image_mode_for_rhel_to_build_deploy_and_manage_operating_systems/introducing-image-mode-for-rhel_using-image-mode-for-rhel-to-build-deploy-and-manage-operating-systems), weight 0.94). Red Hat's positioning on adoption is candid: image mode is best suited for workloads where planned reboots are acceptable, or where high availability is designed with rolling updates across multiple instances, and package-based RHEL with live patching remains the path for non-disruptive kernel updates ([developers.redhat.com blog, 2026-06-15](https://developers.redhat.com/blog/2026/06/15/security-getting-harder-heres-why-image-mode-rhel-helps), weight 0.80).

The sealing primitive itself comes from the composefs project, which combines several underlying Linux features to provide read-only mountable filesystem trees stacking on top of an underlying lower filesystem ([composefs/composefs](https://github.com/composefs/composefs), weight 0.88). The community-side deploy and verification path, including running sealed bootc VMs with bcvk and checking that the full security chain is active, is documented in the bootc project blog ([bootc blog, deploying sealed images](https://bootc.dev/blog/2026-may-07-sealed-images-deploying/), weight 0.69), with the redhat-cop sealing example showing UEFI Secure Boot verifying the UKI signature against enrolled keys before the kernel starts with `composefs=<digest>` on the command line ([redhat-cop/rhel-bootc-examples sealing](https://github.com/redhat-cop/rhel-bootc-examples/tree/main/sealing), weight 0.84).

## Where the trust anchor lives

The sealed-image flow as documented relies on Secure Boot keys enrolled on the machine and a UKI signed with a build key ([redhat-cop sealing example](https://github.com/redhat-cop/rhel-bootc-examples/tree/main/sealing), weight 0.84). Nothing in the surveyed documentation points at a user-held removable token as the root of this chain: the signing identity is a build-side key, verified through the platform's Secure Boot enrollment, which is the enterprise-friendly arrangement. Related Red Hat work extends UKIs with addons to support Confidential Virtual Machines in RHEL while preserving the security footprint ([Red Hat blog, Extending UKIs using addons](https://www.redhat.com/en/blog/extending-red-hat-unified-kernel-images-using-addons), weight 0.71), which shows where the trust-chain investment is heading.

## Why this is the closest enterprise cousin

The primitive set is the same one an image-mode OS with hardware-rooted integrity uses: bootc-compatible OCI image, signed UKI, composefs digest over the root filesystem, verification enforced at mount time. The differences are in the primitive chosen for filesystem integrity (fs-verity per file here, versus a block-level verity layer) and in who holds the key that anchors the chain (a build and enrollment arrangement versus an owner-held hardware token). For tracking upstream convergence, the RHEL sealed-image story is the highest-visibility public statement of this design space as of this scan. Low-weight results from this dig ([scrivano.org](https://scrivano.org/posts/2026-06-05-sealing-with-composefs/), weight 0.30; a reddit index page, weight 0.03) were not used as backing for any claim above.
