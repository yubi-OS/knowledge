# 01 - The bootc composefs backend: the upstream sealed-image mechanism

Scope: upstream bootc composefs backend, how sealed images are produced with a composefs digest embedded in the signed UKI command line, the backend's experimental-to-stabilization status, and fsverity versus dm-verity as the sealing primitive.

## What the backend is

The bootc project ships an alternative storage backend built on composefs, the composite filesystem that stacks a read-only mountable filesystem tree on top of an underlying lower filesystem ([composefs/composefs](https://github.com/composefs/composefs), weight 0.88). Third-party documentation of the bootc tree describes the composefs backend as an experimental storage backend that uses composefs with EROFS images and fsverity verification, adding enhanced integrity guarantees, native UKI support, and sealed-image capabilities compared to the default OSTree-based path ([DeepWiki bootc 2.3.2](https://deepwiki.com/bootc-dev/bootc/2.3.2-composefs-backend), weight 0.56, weak backing).

The upstream project's own docs are direct about maturity: the composefs backend is experimental and on-disk formats are subject to change. They also note a separate `--composefs-backend` option for `bootc install` that selects a composefs backend apart from sealed images, and that this option is not as heavily tested ([bootc experimental-composefs docs](https://bootc.dev/bootc/experimental-composefs.html), weight 0.93). The bootc project overall is the mechanism that boots and upgrades systems via container images, where the container image itself contains the Linux kernel under /usr/lib/modules and the base userspace runs directly on the target rather than inside a container ([bootc-dev/bootc](https://github.com/bootc-dev/bootc), weight 0.79; [bootc.dev](https://bootc.dev/), weight 0.77).

## How the seal is constructed

The sealed-image build assembles a UKI containing the kernel, the initramfs, and a kernel command line that includes `composefs=<digest>`. The UKI is signed with a Secure Boot key and embeds a composefs digest that covers every file in the operating system ([bootc blog, building sealed images, 2026-05-06](https://bootc.dev/blog/2026-may-06-sealed-images-building/), weight 0.76). The same post documents a chicken-and-egg problem that is not immediately obvious: because the composefs digest is embedded in the UKI's kernel command line, and the UKI itself lives inside the image under /boot, building a sealed image requires careful sequencing of digest computation and UKI assembly ([bootc-dev.github.io blog source](https://github.com/bootc-dev/bootc-dev.github.io/blob/main/content/blog/2026-may-06-sealed-images-building.md), weight 0.65).

The follow-up post covers deploying and verifying a sealed image to a virtual machine and checking that the full security chain is active, using bcvk, a tool for running bootc VMs ([bootc blog, deploying sealed images, 2026-05-07](https://bootc.dev/blog/2026-may-07-sealed-images-deploying/), weight 0.69).

## The verified boot chain at runtime

A worked example from the Red Hat ecosystem shows the full chain on a CentOS Stream 10 bootc host: UEFI Secure Boot verifies the UKI signature against enrolled keys, the kernel starts with `composefs=<digest>` on the command line, and the initramfs mounts the root as a composefs overlay with `verity=require` ([redhat-cop/rhel-bootc-examples sealing example](https://github.com/redhat-cop/rhel-bootc-examples/tree/main/sealing), weight 0.84). Red Hat's own documentation chapter confirms the deploy path: when the image includes a UKI and systemd-boot, the system automatically detects the composefs backend, and sealed images deploy with standard methods for compatibility with target systems ([RHEL 10 docs, cryptographic sealing of bootc images, Technology Preview](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/10/html/using_image_mode_for_rhel_to_build_deploy_and_manage_operating_systems/cryptographic-sealing-of-bootc-images-technology-preview), weight 0.94).

## fsverity as the sealing primitive

Both upstream-adjacent sources agree that the bootc composefs seal rests on fs-verity, a per-file integrity primitive, rather than dm-verity, a block-device-level primitive. The DeepWiki description ties the backend to fsverity verification ([DeepWiki](https://deepwiki.com/bootc-dev/bootc/2.3.2-composefs-backend), weight 0.56, weak backing), and a community sealed-boot experiment for secureblue describes bootc's composefs native backend as providing fs-verity ([SRugina/secureblue-sealed](https://github.com/SRugina/secureblue-sealed), weight 0.58). A distribution-aware UKI build walkthrough covering kernel, initrd, command line, Secure Boot signing, inspection, rollout, and rollback verification rounds out the tooling picture ([danielcosenza.com UKI howto](https://danielcosenza.com/posts/lx-howto-unified-kernel-image/), weight 0.66).

## Convergence read

The upstream mechanism an image-mode OS project converges on is exactly this: signed UKI embedding a composefs digest of the root filesystem, verified from firmware through the filesystem at boot. A project that instead seals with dm-verity at the block level is using a different primitive over the same trust chain, and the bootc composefs backend is the natural upstream convergence point if a friendlier upstream story is ever needed. Low-weight results from this dig ([botmonster UKI guide](https://botmonster.com/self-hosting/unified-kernel-images-systemd-boot-signed-linux/), weight 0.25; [scrivano.org sealing walkthrough](https://scrivano.org/posts/2026-06-05-sealing-with-composefs/), weight 0.33; [agentic-workflows-ci-sandbox docs](https://github.com/bootc-dev/agentic-workflows-ci-sandbox/blob/main/docs/src/experimental-composefs.md), weight 0.33) were not used as backing for any claim above.
