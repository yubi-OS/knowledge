# 04 - Competing immutable-OS stacks with a sealed or trusted boot story

Scope: the public immutable-OS projects that ship a sealed or trusted boot story, secureblue and its sealed variant, and Kairos with its trusted-boot installation path, and how their primitive stacks compare on signed UKI, sealing primitive, and the hardware root of the chain.

## secureblue and secureblue-sealed

secureblue describes itself as a security-focused desktop and server Linux operating system built to maximally increase defenses against exploitation of both known and unknown vulnerabilities while avoiding usability sacrifices where possible ([secureblue.dev](https://secureblue.dev/), weight 0.61). It is built with BlueBuild and shipped as a set of OCI bootable containers, using Fedora Atomic Desktop base images as the starting point ([secureblue/secureblue](https://github.com/secureblue/secureblue), weight 0.69). The project's FAQ makes the architectural bet explicit: it leverages bootable container technology to build on top of Fedora Atomic, avoiding the need to become a distro in the traditional sense, and it has benefited by shipping as bootable OCI container images ([secureblue FAQ](https://secureblue.dev/faq), weight 0.52).

The sealed variant is a separate experiment. SRugina/secureblue-sealed describes itself as an experiment in getting secureblue to boot from a UKI via systemd-boot, with bootc's composefs native backend providing fs-verity. The README itself flags a caveat worth recording: "sealed" is a slight misnomer, since the UKI and systemd-boot are not Secure Boot signed, to keep the focus on the rest of the setup ([SRugina/secureblue-sealed](https://github.com/SRugina/secureblue-sealed), weight 0.58). So the sealed variant stacks the same primitive pair (signed-UKI-style boot path and composefs/fs-verity root seal) as the enterprise and upstream stories, but with the firmware signature step deliberately unset, meaning its chain of trust stops short of the firmware-anchored link.

## Kairos trusted boot

Kairos, the edge Kubernetes and immutable Linux project, documents a Trusted Boot installation mode that combines Secure Boot, full disk encryption, and measured boot to protect systems from tampering ([Kairos docs, Trusted Boot Installations](https://kairos.io/docs/v4.2.0/installation/trustedboot/), weight 0.87). Its provider docs add operational maturity signals: a fresh UKI install and a UKI state reset both converge with no manual step, and this was validated on a secure-boot VM with an emulated TPM. The same release fixed bundled image import on UKI nodes where the read-only root filesystem was world-writable by mode, and air-gapped trusted boot installs work ([Kairos provider docs, Trusted boot](https://kairos.io/provider-kubernetes-docs/trusted-boot/), weight 0.76). The mention of an emulated TPM in its own validation notes shows where the hardware root sits in Kairos's design: a TPM, not a user-held token.

Two third-party deepwiki summaries of Kairos's secure boot and TPM integration ([deepwiki kairos 6.2](https://deepwiki.com/kairos-io/kairos/6.2-secure-boot-and-tpm-integration), weight 0.29; [deepwiki kairos-docs 4.2](https://deepwiki.com/kairos-io/kairos-docs/4.2-trusted-boot-implementation), weight 0.38) and a QA gist ([gist.github.com ci-robbot](https://gist.github.com/ci-robbot/82756ef3a8d7c27c5fe2c3de3bf8bb74), weight 0.15) were collected but fall below the authoritative threshold and are not used as backing. One result ([kairosacademies.org](https://www.kairosacademies.org/), weight 0.58) is off-topic (a school, not the OS project) and despite its numeric weight is not cited for any claim. Immutablue's site ([immutablue.io](https://immutablue.io/), weight 0.59) names another immutable Linux offering but its collected snippet carries no verifiable technical claims, so it is listed only as a landscape entry.

## Comparison read

Across the surveyed projects the stack layers line up: an image-based root (bootc OCI images for secureblue, Kairos's own image pipeline), a unified kernel image boot path (systemd-boot UKI in secureblue-sealed, UKI in Kairos), and a sealed root filesystem (fs-verity via composefs in secureblue-sealed, measured boot plus full disk encryption in Kairos). The differentiator is consistently the anchor of the chain. secureblue-sealed leaves the firmware-signature link unset; Kairos roots its chain in a TPM; the enterprise RHEL story roots it in enrolled Secure Boot keys ([see doc 02](02-rhel-sealed-images.md)). None of the surveyed projects puts the root of the chain in a user-held removable hardware token, and none of their collected documentation discusses a YubiKey or FIDO2 token in the platform-integrity role. That absence is the space where an owner-held-key design diverges from the public state of the art.
