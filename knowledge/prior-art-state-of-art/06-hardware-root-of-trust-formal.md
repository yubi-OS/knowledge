# 06 - Hardware root of trust: the formal and industrial frame, and the confidential-computing boundary

Scope: the standards bodies, kernel documentation, and industry treatments that define the hardware root of trust primitives (secure boot, measured boot, attestation) that image-mode OS projects build on, and the confidential-computing boundary where that design space ends.

## The standards layer

The Trusted Computing Group is the not-for-profit organization formed to develop, define, and promote open, vendor-neutral, global industry specifications supportive of a hardware-based root of trust for interoperable trusted computing platforms, with the Trusted Platform Module as its core technology ([trustedcomputinggroup.org](https://trustedcomputinggroup.org/), weight 0.83). Its TPM 2.0 Library specification, Family 2.0, Revision 01.83 from March 2024, is standardized through ISO/IEC JTC 1 ([TCG TPM Library specification](https://trustedcomputinggroup.org/resource/tpm-library-specification/), weight 0.89). This is the normative base every TPM-rooted design inherits.

The Linux kernel's own TPM documentation covers the pieces a Linux integrator works with: the TPM event log, the UEFI event log, PCR-based measurement, establishing initial trust with the TPM, and null primary key certification in userspace ([docs.kernel.org TPM documentation](https://docs.kernel.org/security/tpm/index.html), weight 0.93).

## The industry frame: secure boot, measured boot, attestation

Microsoft's documentation gives the clearest industrial articulation of the three-boot-primitive ladder: Secure Boot, Trusted Boot, and Measured Boot block malware at every stage, with the PC's firmware logging the boot process and Windows sending that log to a trusted server that can objectively assess the PC's health; both Secure Boot and Measured Boot are only possible on PCs with UEFI 2.3.1 and a TPM chip ([Microsoft Learn, Secure the Windows boot process](https://learn.microsoft.com/en-us/windows/security/operating-system-security/system-security/secure-the-windows-10-boot-process), weight 0.94). The cloud-side complement is documented for Azure: firmware measured boot and host attestation to verify host integrity and security before workloads run ([Microsoft Learn, measured boot and host attestation](https://learn.microsoft.com/en-us/azure/security/fundamentals/measured-boot-host-attestation), weight 0.92).

The 0pointer blog post "Brave New Trusted Boot World" is the design-side counterpart, putting the Unified Kernel Image at the center of the proposed construction for the Linux side of the same frame ([0pointer blog, Brave New Trusted Boot World](http://0pointer.net/blog/brave-new-trusted-boot-world.html), weight 0.76). A security-education blog series treats hardware trust as the foundation layer after privilege escalation and rootkits ([tharunaditya.github.io](https://tharunaditya.github.io/blog/2026/02/09/syssec-05-secure-boot/), weight 0.59), and Schneier's TPM archive aggregates analysis of the TPM as a hardware-based root of trust protecting cryptographic keys from privileged system and physical attacks ([schneier.com TPM tag](https://www.schneier.com/tag/tpm/), weight 0.75).

## The confidential-computing boundary

Confidential computing extends the same trust chain into memory-encryption and remote-attestation territory with AMD SEV-SNP and Intel TDX. A peer-reviewed ACM paper provides an empirical analysis of the two leading confidential VM technologies, reviewing their microarchitectural components and evaluating memory management, computational and I/O performance, and attestation ([ACM DL 10.1145/3726854.3727280](https://dl.acm.org/doi/10.1145/3726854.3727280), weight 0.90). Lower-weight collected articles cover the operator-facing side of the same space (verifying SEV-SNP and TDX host prerequisites, confidential containers on Kubernetes) at weights 0.15 to 0.37 and are not used as backing ([oneuptime](https://oneuptime.com/blog/post/2026-09-12-verify-sev-snp-tdx-host-prerequisites/view), [systemshardening.com](https://www.systemshardening.com/articles/kubernetes/confidential-containers/), [stealthcloud.ai](https://stealthcloud.ai/cloud-paradigms/confidential-computing-deep-dive/)).

The boundary matters for scoping: confidential computing roots its guarantees in vendor-managed silicon attestation (SEV-SNP, TDX) rather than in a user-held token, and its attestation model targets workload-level isolation rather than OS-image integrity. A project whose attestation story is about platform and image integrity should not conflate its design space with confidential-computing attestation; the ACM survey shows those are distinct (though adjacent) fields with different trust anchors ([ACM DL](https://dl.acm.org/doi/10.1145/3726854.3727280), weight 0.90).

## What the frame implies

The formal frame is settled: a standards-defined TPM root of trust, kernel-side event logs and PCR measurement, an industry ladder of secure boot plus measured boot plus remote attestation, and UKIs as the Linux boot-chain carrier. The formal literature treats the platform root as something soldered to the platform. Nothing in the surveyed standards, kernel, or industry documentation describes substituting a user-held removable hardware token for the platform root; the root-of-trust discussions all assume the TPM's fixed position. That leaves the owner-held-token variant outside the formal frame, which is the gap a novel design would occupy.
