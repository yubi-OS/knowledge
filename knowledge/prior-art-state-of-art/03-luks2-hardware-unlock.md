# 03 - LUKS2 hardware unlock: the upstream state through systemd-cryptenroll

Scope: the upstream state of LUKS2 hardware unlock, centered on systemd-cryptenroll (systemd 248 and later), which enrolls FIDO2, TPM2, and PKCS#11 tokens, and the distro-level support built on it.

## The canonical upstream mechanism

The systemd man page defines the tool directly: systemd-cryptenroll is a tool for enrolling hardware security tokens and devices into a LUKS2 encrypted volume, which may then be used to unlock the volume during boot ([freedesktop.org man page for systemd-cryptenroll](https://www.freedesktop.org/software/systemd/man/251/systemd-cryptenroll.html), weight 0.98). The feature's introduction is documented in detail by the 0pointer blog post covering systemd 248: with that release, the systemd-cryptsetup component responsible for assembling encrypted volumes during boot gained direct support for unlocking encrypted storage with three types of security hardware, TPM2, FIDO2, and PKCS#11 ([0pointer blog, Unlocking LUKS2 volumes with TPM2, FIDO2, PKCS#11 security hardware on systemd 248](https://0pointer.net/blog/unlocking-luks2-volumes-with-tpm2-fido2-pkcs11-security-hardware-on-systemd-248.html), weight 0.95).

The FIDO2 path has one hard requirement called out in the same post: the FIDO2 token must implement the hmac-secret extension, which is the mechanism that lets the token derive a secret the LUKS volume can be unsealed with ([0pointer blog](https://0pointer.net/blog/unlocking-luks2-volumes-with-tpm2-fido2-pkcs11-security-hardware-on-systemd-248.html), weight 0.95). The same post walks how the pieces fit together in the FIDO2 case specifically, and notes this is likely what you want if you have a FIDO2 token with hmac-secret support.

## Enrolled token types and what they buy

Community documentation summarizes the enrollment surface: systemd-cryptenroll allows enrolling smartcards, FIDO2 tokens, and Trusted Platform Module security chips into LUKS devices, as well as regular passphrases, and these devices are later used to unlock the volume at boot ([ArchWiki, systemd-cryptenroll](https://wiki.archlinux.org/title/Systemd-cryptenroll), weight 0.80; [same page, first collection](https://wiki.archlinux.org/title/Systemd-cryptenroll), weight 0.50). A practical guide (weaker source, weight 0.54) describes adding TPM2, FIDO2, PKCS#11, and recovery-key unlock methods to LUKS2 volumes, storing token metadata in the LUKS2 JSON token area, and wiring boot-time unlock through crypttab ([golinuxcloud systemd-cryptenroll guide](https://www.golinuxcloud.com/systemd-cryptenroll-luks2-tpm2-fido2-linux/), weight 0.54, weak backing; the man7.org copy of the man page, weight 0.45, is below the authoritative threshold and is not used as backing).

An in-org synthesis of the 0pointer material adds the security-property framing: the three token types buy three different security properties, with FIDO2 tokens via the hmac-secret extension turning a plug-in USB device into a possession factor carried on a keyring, with zero token modification and zero per-volume setup of the token itself ([yubi-OS/knowledge, 0pointer/04-luks2-hardware-unlock](https://github.com/yubi-OS/knowledge/blob/main/knowledge/0pointer/04-luks2-hardware-unlock.md), weight 0.65).

## What the upstream state covers, and what it does not

The upstream mechanism is a disk-unlock mechanism. It enrolls a hardware token as one unlock factor among several (TPM2, FIDO2, PKCS#11, recovery key, passphrase) for a LUKS2 volume, and stores the binding in the volume's JSON token area so the initramfs and systemd-cryptsetup can act on it at boot ([freedesktop man page](https://www.freedesktop.org/software/systemd/man/251/systemd-cryptenroll.html), weight 0.98; [golinuxcloud](https://www.golinuxcloud.com/systemd-cryptenroll-luks2-tpm2-fido2-linux/), weight 0.54, weak backing). Two design decisions sit on top of this mechanism in any OS project that adopts it, and neither is upstream's to make. First, whether hardware unlock is the default or one option among several. Second, whether the token's role stops at disk unlock or extends into a broader platform-identity role above the unlock role. The upstream state as surveyed is neutral on both: the mechanism exists, is documented, and is available to every distro shipping systemd 248 or later, which is precisely why the mechanism itself carries no differentiation for an OS project. Any differentiation must come from the design decisions above it. A community script for TPM2 auto-unlock on LUKS2 ([justanotherkiwi/LUKS2-TPM-Auto-Unlock](https://github.com/justanotherkiwi/LUKS2-TPM-Auto-Unlock), weight 0.30) and a low-weight tutorial ([dev.to](https://dev.to/lyraalishaikh/stop-typing-luks-passphrases-at-every-boot-practical-systemd-cryptenroll-on-linux-49nm), weight 0.16) were collected but not used as backing for any claim above.
