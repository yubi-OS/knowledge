# 07 - The owner-held YubiKey as platform identity root: why the scan finds no competitor

Scope: whether any public project treats a user-held hardware token (YubiKey, FIDO2) as the platform identity root rather than only a disk-unlock factor, why the mainstream designs all root in TPM2, and what this scan concludes about novelty.

## The convergence baseline

The substrate converges on a fixed arrangement: the platform identity root is a TPM. The RHEL sealed-image chain anchors in Secure Boot keys enrolled on the machine ([redhat-cop/rhel-bootc-examples sealing](https://github.com/redhat-cop/rhel-bootc-examples/tree/main/sealing), weight 0.84). Kairos's trusted boot is explicitly Secure Boot, full disk encryption, and measured boot, validated with an emulated TPM ([Kairos trusted boot docs](https://kairos.io/docs/v4.2.0/installation/trustedboot/), weight 0.87). The standards layer defines the root of trust as a platform-fixed TPM under TCG specification ([trustedcomputinggroup.org](https://trustedcomputinggroup.org/), weight 0.83), and the kernel-side mechanics assume the TPM's fixed position with PCR measurement and event logs ([docs.kernel.org TPM docs](https://docs.kernel.org/security/tpm/index.html), weight 0.93). Microsoft's boot-process documentation states Secure Boot and Measured Boot are only possible on PCs with UEFI 2.3.1 and a TPM chip ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/security/operating-system-security/system-security/secure-the-windows-10-boot-process), weight 0.94). Even the confidential-computing frontier keeps the anchor in vendor silicon ([ACM DL SEV-SNP and TDX analysis](https://dl.acm.org/doi/10.1145/3726854.3727280), weight 0.90).

## Where YubiKeys do appear upstream

YubiKeys do have documented roles in boot and disk security, but each is adjacent to the platform-identity role. The System Transparency project documents signing EFI applications with a YubiKey 5 for its secure boot flow ([System Transparency docs, YubiKey 5](https://docs.system-transparency.org/st-1.3.0/docs/how-to/secure-boot/sign-efi-applications/yubikey/), weight 0.81), which is YubiKey as a signing tool held by an operator, not as the platform's identity root. A community tutorial stacks YubiKey-based full disk encryption with self-signed UEFI Secure Boot and YubiKey authentication for user login ([sandrokeil/yubikey-full-disk-encryption-secure-boot-uefi](https://github.com/sandrokeil/yubikey-full-disk-encryption-secure-boot-uefi), weight 0.68), which is YubiKey as disk-unlock factor and login factor. The upstream FIDO2 hmac-secret disk-unlock mechanism in systemd 248 covers the same unlock-factor territory ([0pointer blog on systemd 248](https://0pointer.net/blog/unlocking-luks2-volumes-with-tpm2-fido2-pkcs11-security-hardware-on-systemd-248.html), weight 0.95). In the other direction, tpm-fido shows a TPM being used to back a WebAuthn/U2F software token ([psanford/tpm-fido](https://github.com/psanford/tpm-fido), weight 0.67), the inverse of substituting a removable token for the TPM. The FIDO Alliance's own device-onboarding specification for placing FDO credentials in a TPM likewise assumes the TPM as the credential holder ([FIDO Alliance FDO in TPM spec](https://fidoalliance.org/specs/FDO/securing-fdo-in-tpm-v1.0-rd-20231010/securing-fdo-in-tpm-v1.0-rd-20231010.html), weight 0.75). FIDO2 as a standard is framed by its strongest backer as strong authentication for user sign-in, not platform identity ([Microsoft Security, What is FIDO2](https://www.microsoft.com/en-us/security/business/security-101/what-is-fido2), weight 0.83).

## The subject of the scan

The one project in the scan whose repository states the owner-held positioning is the subject itself: its repository README describes a FIDO2-first immutable OS with the HSM/U2F key as the root of trust, where the YubiKey provides the signing, unlock, SSH, PAM, and application-2FA boundary while TPM and fTPM measurement remain separate platform-integrity signals ([yubi-OS/yubiOS](https://github.com/yubi-OS/yubiOS), weight 0.52). This is listed for transparency: a corpus built by the project about the project cannot treat its own repo as independent prior art.

## The novelty read

This scan's collected set covers the RHEL and bootc sealed-image stories, the secureblue and Kairos trusted-boot stories, the systemd-cryptenroll mechanism, the TCG and kernel TPM standards layer, and the confidential-computing boundary, and none of it documents a project using a user-held removable token as the platform identity root. Stated as a scoped finding rather than an absolute claim: within this scan's query set and result set, no public project stacks the owner-held key in that role. The mechanism ingredient (FIDO2 hmac-secret in systemd-cryptenroll, systemd 248) has existed since 248 shipped ([0pointer blog](https://0pointer.net/blog/unlocking-luks2-volumes-with-tpm2-fido2-pkcs11-security-hardware-on-systemd-248.html), weight 0.95), and YubiKey-as-signing-key exists in at least one upstream flow ([System Transparency](https://docs.system-transparency.org/st-1.3.0/docs/how-to/secure-boot/sign-efi-applications/yubikey/), weight 0.81). The composition of those ingredients into a platform-identity root is what the scan cannot find elsewhere. Two residual risks temper the claim: the scan is bounded by its queries and dates, so absence of evidence is not evidence of absence, and the enterprise gravity toward TPM2 is strong across every surveyed stack, which could pull the same composition into a mainstream project later. A low-weight LUKS2-plus-FIDO2 setup gist ([gist.github.com Syderitic](https://gist.github.com/Syderitic/23b9c22cb772e1b0e674ed4bb5a3abef), weight 0.19), YouTube results (weights 0.09 to 0.21), and a Yubico vendor page ([yubico.com](https://www.yubico.com/), weight 0.53) were collected but not used as backing for claims above.
