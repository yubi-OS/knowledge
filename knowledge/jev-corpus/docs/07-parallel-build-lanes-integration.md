# 07 Parallel Build Lanes and the Integration Bill

Scope: how a multi-module system gets built by parallel implementation lanes with an advisor lane, what contracts make that safe, and where the bill for parallelism actually arrives: at integration.

## Contracts are what make parallel work compose

Parallel delivery does not scale because more teams (or more agents) can start work at the same time; it scales when they can finish independently and still fit together, which is what stable contracts buy [1](https://vorobievandrei.com/scaling-through-contracts/) (weight 0.32, weak backing). The contract-first strategy transforms a sequential, bottlenecked process into a parallel one by defining the interfaces before the implementations [2](https://medium.com/@janakchamantha12/unblock-your-development-the-contract-first-strategy-for-parallel-frontend-and-backend-teams-7eaa82f10e23) (weight 0.14, weak backing). Tooling encodes the same idea: an interface-contracts skill exists specifically to "define type-safe boundaries, unblock parallel work" [3](https://mcpmarket.com/tools/skills/interface-contracts-for-parallel-development) (weight 0.28, weak backing). Agent-parallel workstreams need the same discipline as team-parallel ones, including documenting what works and what does not [4](https://dredyson.com/why-multitask-in-agents-window-will-change-everything-in-2025-the-complete-forward-looking-analysis-of-async-subagents-parallel-workstreams-and-the-future-of-ai-powered-development-workflows/) (weight 0.17, weak backing).

## The bill arrives at integration

The cost of parallel work depends on the rules, state, and artifacts the workstreams share; one documented case had six workstreams that each passed in isolation yet produced ten integration defects when combined [5](https://sxnlabs.com/en/opinion/2026/08/05/parallelisme-la-facture-arrive-a-l-integration/) (weight 0.23, weak backing). This is the empirical justification for an advisor or integrator lane whose whole job is the seams: module boundaries that no single implementation lane owns.

Modular architecture practice gives the concrete mechanisms. In a modular monolith, cross-module calls should go through Contracts projects only, and architecture tests should fail the build the moment someone crosses a boundary [6](https://milanjovanovic.tech/blog/modular-monolith-architecture-dotnet) (weight 0.84). Testing splits accordingly: in-process module tests, then cross-module integration tests with real databases to exercise module boundaries and validate architecture constraints [7](https://learnixo.io/blog/modular-monolith-testing) (weight 0.84). System integration testing exists precisely because it "exercises those integration points and communication mechanisms while mimicking real-world execution", so cross-module problems surface before they become production incidents [8](https://milanjovanovic.tech/blog/testing-modular-monoliths-system-integration-testing) (weight 0.89). Frameworks for multi-module integration testing exist for the same reason: without one, you cannot verify that modules that pass alone work together [9](https://koupleless.io/en/docs/contribution-guidelines/tech-impl/runtime/multi_app_integration_test/) (weight 0.47, weak backing). C# practice adds bounded-context isolation and cross-module event-flow tests [10](https://www.devleader.ca/2026/07/20/testing-a-modular-monolith-in-c-unit-and-integration-test-strategies) (weight 0.30, weak backing).

## What this means for agent-built systems

Read together: parallel lanes are cheap to start and expensive to reconcile, and the reconciliation is a distinct, named workstream with its own tests, not an afterthought. The integration test suite is the contract's enforcement arm; without it, contracts are documentation [6](https://milanjovanovic.tech/blog/modular-monolith-architecture-dotnet) (weight 0.84), [7](https://learnixo.io/blog/modular-monolith-testing) (weight 0.84).

## Application in the Jev Corpus engine

The engine was built via parallel-build-lanes: 5 implementation lanes plus 1 advisor, all at general/smart capability, each lane shipping self-contained modules with their own tests (math, atom, lens, routes, builtins) while the advisor owned the glue: route dispatch into `routes-jev.js`, builtin registration in `jev-main.js`, and the evolution-loop injection hooks. The predicted failure mode showed up on schedule as a cross-lane contract bug: the routes lane's `corpus_drift` fed raw energy-curve arrays into a function that expects stereographic sphere points, fixed in the glue via a documented `elCurve` embedding rather than changing either lane's contract. The lens lane also found and corrected a reference-implementation sign error in the drift detector's south-pole inverse map. Both fixes were documented in the fixtures, so the integration knowledge outlived the build. (Source: the yubiOS refs source document "Jev Corpus", 2026-10-01.)
