# 06 Parity Testing Against a Reference Implementation

Scope: the discipline that keeps a ported math implementation honest: fixtures generated from the reference, pinned tolerances, a parity gate that enforces the published number, and the rule that a port never re-derives the math.

## What parity testing is

When an implementation is ported to a new language or platform, parity testing verifies that the port produces numerically equivalent results to the original reference across defined granularities, from individual ops to end-to-end behavior [1](https://github.com/NVIDIA-NeMo/Automodel/blob/main/skills/parity-testing/SKILL.md) (weight 0.77). The kernel-level version of the practice validates every operation by loading the port and the reference, running identical operations in both, and comparing the results [2](https://c-kernel-engine.github.io/C-Kernel-Engine/pytorch-parity.html) (weight 0.55). Port-validation guidance organizes the work into three tiers: correctness (numerical accuracy), performance (throughput parity), and integration (no regressions) [3](https://github.com/AMD-AGI/Primus/blob/main/skills/port-validation-guide/SKILL.md) (weight 0.71). Porting case studies document the same structure at project scale: component-level verification plus end-to-end correlation metrics between the C++ port and the original PyTorch reference models [4](https://deepwiki.com/mudler/depth-anything.cpp/6.3-numerical-parity-and-quantization-accuracy) (weight 0.38, weak backing), and numerical parity across model versions and architectural backends to protect against graph-level regressions [5](https://deepwiki.com/localai-org/LocalVQE/4.2-regression-tests-and-fixtures) (weight 0.30, weak backing). ESM2 porting work emphasizes parity verification across different granularities, from individual layers to the full model [6](https://deepwiki.com/patrick-kidger/esm2quinox/4.1-test-suite-and-parity-verification) (weight 0.38, weak backing).

## The parity gate and pinned references

The strongest form of the discipline turns the published number into the test. A parity gate should enforce the number you publish: keep one reference output file, pinned to a specific reference-framework version and snapshot, with the published value embedded as a hard limit, and one gate script that runs the non-reference binary on every test case comparing per-output-element results [7](https://dev.to/nivdvir/your-parity-gate-must-enforce-the-number-you-publish-a-testing-methodology-for-porting-ml-models-j4g) (weight 0.36, weak backing). This makes the claim ("our port matches to 1e-9") falsifiable in CI rather than aspirational.

## Tolerances and fixtures

Choosing a tolerance is a decision, not a formality: numerical tolerances for regression tests must reflect trade scale, the numerical method, and noise sources, balancing stability against necessary change [8](https://www.quantwithvahab.com/glossary/numerical-tolerances-for-regression-tests) (weight 0.15, weak backing). Reproducibility guidance treats the numerical tolerance as one of the configurable knobs of a statistical system, alongside spread, probability, and sample size [9](https://thefintechbuilder.com/financial-mathematics-statistics-and-data-foundations/statistical-computing-and-reproducibility/fixtures-numerical-tolerances-and-property-tests/) (weight 0.22, weak backing). Fixture infrastructure can be automated: test suites define configuration of hardware targets via flags and an automated fixture system for device and datatype management, with numerical validation logic verifying kernel correctness [10](https://deepwiki.com/gongyisheng/inference-kernel/4.1-test-fixtures-and-numerical-tolerances) (weight 0.28, weak backing). (One search hit under "fixtures" concerns mechanical checking gauges and is unrelated to software testing; it is excluded here.)

## The never-re-derive rule

The subtle failure mode in porting math is not a wrong constant; it is a well-meaning re-derivation. If the port re-derives the algorithm from the paper, divergence between port and reference becomes undetectable in principle, because there is no third thing to compare against. The alternative, used by the Jev Corpus engine: generate fixtures by running the actual Python reference (`rsi_descent.py`, `collapse.py`, the tautology classifier), embed them in the port, and assert equality within a floor tolerance. The published audit anchor (z 12.13 to +21.68 dBc) is itself pinned as a fixture. (Source: the yubiOS refs source document "Jev Corpus", 2026-10-01.)

## Application in the Jev Corpus engine

The engine's test evidence is organized exactly along these tiers: 158 tests across 6 suites, with math parity at a 1e-9 fixture tolerance (worst observed deviation 1e-15), curveball margin preservation, atom deltas asserted non-negative and throwing on violation per the reference's `atom_delta_nonneg` property, 21 exact-verdict tautology fixtures generated from the actual Python, and route-level tests for idempotency, auth, and purity. Each module carries its own `selfTest` so the deployed worker can re-verify parity against the embedded fixtures at runtime, not just in CI. (Source: the yubiOS refs source document "Jev Corpus", 2026-10-01.)
