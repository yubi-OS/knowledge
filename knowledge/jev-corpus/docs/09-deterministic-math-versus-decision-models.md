# 09 Deterministic Math Engines Versus Decision Models

Scope: the separation between deterministic, reproducible computation (the corpus math) and probabilistic decision layers (the LLM decision model), why the boundary must be explicit, and how orchestration of the two kinds is done.

## The distinction

Traditional enterprise systems are deterministic: given the same input, they produce the same output every time. AI systems are probabilistic: they may produce different outputs for identical inputs, with behavior emerging from learned patterns rather than explicit rules [1](https://www.rcmohan.com/frameworks/deterministic-probabilistic) (weight 0.39, weak backing). The divide in machine learning is fundamental and shapes how models make predictions and quantify uncertainty [2](https://mljourney.com/probabilistic-vs-deterministic-machine-learning-algorithms-understanding-the-fundamental-divide/) (weight 0.11, weak backing). Comparative guides frame the same split for system design: deterministic versus probabilistic approaches differ in decision-making, accuracy, predictability, use cases, costs, and business impact [3](https://altaitools.com/deterministic-vs-probabilistic-ai/) (weight 0.14, weak backing), and modern practice blends "probabilistic creativity and deterministic logic" rather than choosing one [4](https://geeksforgeeks.org/artificial-intelligence/ai-for-geeks-week2/) (weight 0.29, weak backing).

The synthesis position is orchestration: deterministic and probabilistic components should be compared and orchestrated deliberately so each kind runs where it is reliable, rather than being fused into one layer [5](https://kestra.io/resources/ai/deterministic-vs-probabilistic) (weight 0.67).

## Reproducibility: making the deterministic side verifiable

For the deterministic side to be trustworthy, it must be reproducible in the strong sense. Reproducible builds are "a set of software development practices that create an independently-verifiable path from source to binary code", elevating deterministic builds by making the build process independently verifiable by anyone [6](https://reproducible-builds.org/) (weight 0.95). The practical recipe: a reproducible pipeline produces the same model and metrics from the same inputs, achieved by pinning seeds, dependencies, data versions, and code together; determinism on accelerators is a separate, harder problem because many GPU kernels are nondeterministic by default [7](https://appliedaiprep.com/concepts/reproducible-pipelines) (weight 0.82). Reproducible-builds practice includes patching toolchains to remove timestamps and versioning datasets and seeds for ML artifacts [8](https://devsecopsschool.com/blog/reproducible-builds/) (weight 0.24, weak backing). A research synthesis documents the convergence of signed provenance, scope-deterministic pipelines, and quorum-style validation, while noting integration gaps and scalability trade-offs [9](https://www.ijcser.com/admin/uploads/OMGa67.pdf) (weight 0.54). Even with mature workflow management systems, reproducibility in scientific computing remains challenging, which is why the discipline must be designed in rather than assumed [10](https://www.frontiersin.org/journals/bioinformatics/articles/10.3389/fbinf.2026.1824590/full) (weight 0.82).

## Why the boundary matters in an agent architecture

The boundary matters because the two kinds of components fail differently. A deterministic function that returns different values for the same input is broken, and parity tests can prove it is or is not [6](https://reproducible-builds.org/) (weight 0.95). A decision model that returns different scores for the same input is normal, and must be governed by calibration, confidence reporting, and logging instead [1](https://www.rcmohan.com/frameworks/deterministic-probabilistic) (weight 0.39, weak backing). Mixing them is an anti-pattern with a specific failure signature: nondeterminism leaks into the deterministic layer (a cached score silently changes a computed verdict) or false precision leaks out of the probabilistic layer (a model's guess presented as a computed fact). Keeping them separate means each layer's failure can be detected with the right tool: parity fixtures for the math, logged decisions with probabilities and confidence for the model [5](https://kestra.io/resources/ai/deterministic-vs-probabilistic) (weight 0.67).

## Application in the Jev Corpus engine

The engine encodes this boundary explicitly: the corpus modules (`jev-corpus-math`, `jev-corpus-atom`, `jev-corpus-lens`) are deterministic JavaScript, parity-tested against the project's Lean/Python reference and never re-derived, while jev-1.13 remains the only decision layer in the system. Audit and lens results are data only; they never authorize anything. The invariant is stated as a design rule in the source: the math never authorizes, the decision layer decides, and the gate executes. Honest failure paths complete the separation: when a cycle lacks the history to compute a metric, the system records an error field rather than letting either layer invent a number.
