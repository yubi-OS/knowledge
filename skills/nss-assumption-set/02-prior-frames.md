# 02 - The four prior-work frames

Scope: the four bodies of prior work the Assumption set axis draws on and what each contributes to gap-finding: Design by Contract (Eiffel/Meyer), SPARK Ada contracts (GNATprove), rely/guarantee reasoning (Cliff Jones), and requirements engineering (Parnas/Clements, NASA SWE, ISO/IEC/IEEE 29148).

## Design by Contract (Eiffel, Bertrand Meyer)

The source doc names Design by Contract the closest direct precedent (source doc: yubi-OS/yubiOS skills/nss-assumption-set/SKILL.md). The term was coined by Meyer in connection with the design of Eiffel and first described in the late 1980s (https://en.wikipedia.org/wiki/Design_by_contract, jev weight 0.32, weak backing). The contract page of the original Eiffel documentation defines the three obligation types: preconditions (`require`) are what the caller must satisfy, postconditions (`ensure`) are what the routine guarantees, and class invariants (`invariant`) are properties preserved by every exported routine and ensured by every creation procedure (https://archive.eiffel.com/doc/manuals/technology/contract/, jev weight 0.55).

The source doc extends this mapping to gap-finding: a precondition maps to what the caller, operator, or CI must already have installed, configured, or preserved; a postcondition maps to what the artifact promises the user will obtain; an invariant maps to what must remain true across edits, executions, states, or versions; a contract violation is a concrete usability, correctness, or documentation gap; and the contract participant is the person, tool, environment, or neighboring artifact responsible for the assumption (source doc). Meyer's own books page confirms Object-Oriented Software Construction, the foundational contract text, as the second-edition Prentice Hall work the field cites (https://bertrandmeyer.com/books/, jev weight 0.33, weak backing). The single most common gap-finding error the source doc flags in this frame is silently turning a missing postcondition into a user obligation (source doc).

## SPARK Ada contracts (GNATprove)

SPARK 2014 expresses contracts using Ada 2012's built-in aspect syntax, with GNATprove as the main verification tool (https://en.wikipedia.org/wiki/SPARK_(programming_language), jev weight 0.38, weak backing). The AdaCore course material places SPARK's value in strengthening Ada's dynamic checks and exceptions into statically verified contracts (https://learn.adacore.com/courses/Ada_For_The_Embedded_C_Developer/chapters/05_SPARK.html, jev weight 0.53).

The source doc uses GNATprove's call-side and body-side model as the assumption set axis expressed as proof: at the call site, GNATprove assumes the called subprogram's `Pre` holds; in the body, it verifies the body establishes `Post` for all inputs satisfying `Pre` (source doc). Two SPARK ideas carry over directly:

- The four-way diagnostic: a failed proof, or a failed assumption-set audit, may mean an incorrect implementation, a missing contract, an imprecise contract, or an automation limitation. The first is not the default.
- The four-way kind of assumption: problem-domain assumptions (the sensor reports temperature within plus or minus 0.5 degrees C), execution-environment assumptions (the kernel supports landlock, TPM 2.0 is present), language and tool semantics assumptions (the parser is LL(1)), and proof-tractability assumptions (we ignore unrelated globals for now). The source doc requires gap-finding to preserve this distinction because a missing domain assumption is qualitatively different from a missing environment assumption even though both look identical in a flat list (source doc).

## Rely/Guarantee reasoning (Cliff Jones)

Classical rely/guarantee reasoning extends pre/post reasoning to concurrency. A component's rely condition states what interference from the environment it assumes; its guarantee condition states how the component may change shared state. The environment's guarantees must satisfy the component's relies and vice versa (source doc). The primary literature confirms this shape: Hayes and Jones's SETSS lecture introduces rely/guarantee reasoning about concurrency as the compositional way to reason about interference (http://homepages.cs.ncl.ac.uk/cliff.jones/publications/SETSS-17.pdf, jev weight 0.56), and Coleman and Jones's technical report surveys how rely/guarantee conditions record interference in ways that provide compositional development of concurrent systems (http://homepages.cs.ncl.ac.uk/cliff.jones/publications/NU-TRs/CS-TR-1029.pdf, jev weight 0.54).

For gap-finding, the frame's value is environmental behavior assumptions: another service preserves an API or schema, a scheduler does not run two migrations concurrently, credentials remain available, a filesystem is durable, a queue preserves ordering, an operator performs a restart within a stated interval (source doc). A document is incomplete if it states what the procedure guarantees but not what concurrent services, operators, or infrastructure must guarantee in return.

## Requirements engineering (Parnas, Clements, NASA SWE, ISO 29148)

The requirements-engineering tradition makes the environment a first-class citizen of the assumption set. Parnas and Clements' ideal requirements document includes computer/platform specification, input/output interfaces, output behavior, timing constraints, accuracy constraints, likely changes, and undesired-event handling; their Four Variable Model separates environmental facts (NAT) from required behavior (REQ). NASA SWE-050 and SWE-184 enumerate environmental constraints, assumed technology availability, budgetary restrictions, operational modes, hardware/software/operator roles, precedence, failure modes, timing constraints, and assumptions used in deriving requirements (source doc).

ISO/IEC/IEEE 29148:2018 specifies the required processes of requirements engineering and the characteristics of requirement statements, which is the standards-based anchor for treating assumptions, constraints, interfaces, and environment requirements as documented information (https://www.iso.org/standard/72089.html, jev weight 0.59; https://standards.ieee.org/ieee/29148/6937/, jev weight 0.58). The resulting distinctions the source doc enforces: assumption (a fact about the environment), requirement (a behavior the system owes), implementation fact (an internal decision), and evidence gap (no calibration specification or test establishes the environmental claim). A `## Assumption set` section that conflates these is worse than no section (source doc).
