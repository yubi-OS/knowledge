# 07. yubiOS integration: secure time for fTPM and measured boot

Scope: where the CNTPCT-backed secure clock plugs into yubiOS: tamper-resistant timestamps for fTPM NV counters and the measured-boot event log, and the skills it composes with.

Primary source: yubi-OS/yubiOS skills/drm-gpu-quota-secure-time/SKILL.md (the "source doc").

## The two yubiOS use cases

The source doc names the relevance directly: CNTPCT-based secure time is useful for anything that needs tamper-resistant timestamps ahead of a real RTC or attestation service. It gives two examples: bounding replay windows for fTPM NV counters, and timestamping the ADR-018/019 ARM64 fTPM measured-boot event log with a time value that normal-world userspace cannot roll back (source doc, section 5).

The measured-boot case is the stronger one. The fTPM trusted application, the Microsoft TPM 2.0 reference implementation running under OP-TEE, includes Measured Boot support: it can read a TPM event log compatible with section 5 of the TCG EFI Protocol Specification, and the event log is read and extended during TA initialization (jev 0.39, weak backing, https://github.com/OP-TEE/optee_ftpm). The event-logging subsystem processes pre-existing event logs generated by firmware during the boot process and replays them into the TPM by extending the appropriate Platform Configuration Registers, which is what enables attestation and verification of the platform's boot integrity (jev 0.2, weak backing, https://deepwiki.com/OP-TEE/optee_ftpm/8.1-event-logging-and-measured-boot). A timestamp on those log entries that comes from a REE-controlled clock would let normal-world software rewrite history; a CNTPCT-read timestamp does not.

## The composition rule

The source doc's pairing instruction matters: check the `ftpm-optee-tpm` and `arm-trusted-firmware-optee` skills before assuming this is a standalone feature (source doc, section 5). It is a config bit inside the same OP-TEE build those skills already cover, not a separate subsystem with its own build, deployment, or maintenance surface. Concretely: the yubiOS firmware stack brings up TF-A, OP-TEE, and the fTPM TA; the CNTPCT force-on rides along in the OP-TEE platform config; nothing new is provisioned.

## What the TEE core API guarantees

The `gpd.tee.systemTime.protectionLevel` property that CNTPCT mode raises is part of the GlobalPlatform TEE Internal Core API specification. Version 1.4 (GPD_SPE_010) clarified how clock skew between real world time and System Time is specified, differentiating behavior between different values of the protectionLevel property, and clarified that clock skew on the value returned by `TEE_GetREETime()` is out of scope of the specification (jev 0.89, https://globalplatform.org/specs-library/tee-internal-core-api-specification/). For yubiOS, that distinction is the contract: `TEE_GetREETime()` is untrusted REE time, `TEE_GetSystemTime()` under CNTPCT is the protected one, and event-log timestamping code should use the latter.

## Design cautions

Three cautions bound the design space. First, secure time is monotonic within a running system, not continuous across reboots: a maintainer discussion notes that persisting time through secure storage would mean a write on every time query, so restoring wall time at boot needs a secure RTC or another boot-time mechanism (jev 0.63, https://github.com/OP-TEE/optee_os/issues/5973). Replay-window bounding with CNTPCT works for runtime counters, not for proving an absolute wall-clock date. Second, the protectionLevel semantics are property-value dependent, so any yubiOS code claiming level 1000 behavior should assert the config bit is actually set rather than assuming it. Third, this doc's fTPM references carry weak backing (0.39 and 0.2), so before implementing, verify the fTPM event-log details against the `ftpm-optee-tpm` skill and the optee_ftpm repository directly.

## What this doc does not cover

The GPU quota half of the skill has no CNTPCT dependency: per-cgroup VRAM accounting and the SMC lockout design are unrelated to secure time. This doc exists because the source doc is explicit that the secure-time half earns its place in yubiOS only through the fTPM and measured-boot consumers; without them it would be an unused config flag.
