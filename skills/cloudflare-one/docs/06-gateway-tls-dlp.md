# 06 - Gateway, TLS, and DLP

Scope: Gateway traffic policies and their evaluation semantics, TLS inspection and root CA deployment, Do Not Inspect exceptions, and DLP profiles and their activation path.

Grounding spine: source doc `yubi-OS/yubiOS skills/cloudflare-one/SKILL.md`.

## Gateway's role and rule types

Gateway is the traffic inspection and filtering layer; Access is the application authorization layer, and the source doc requires using both when the requirement spans identity-aware app access and network or web security (source doc). Traffic controls to assess before configuring: DNS categories, HTTP URL and path inspection, L4 ports and protocols, egress IP requirements, custom lists, and allow or block exceptions, with the [Gateway traffic policy docs](https://developers.cloudflare.com/cloudflare-one/traffic-policies/) to be retrieved for current selectors and order of enforcement (source doc).

Gateway has 4 policy types with different evaluation semantics: DNS, Network, HTTP, and Egress (source doc). The current [order of enforcement](https://developers.cloudflare.com/cloudflare-one/traffic-policies/order-of-enforcement/) docs state that order of precedence refers to the priority of individual policies within the DNS, network, or HTTP policy builder, and that Gateway evaluates policies in ascending order beginning with the lowest value (weight 0.96). A dated drift note worth carrying: a [learning-path page](https://developers.cloudflare.com/learning-paths/secure-internet-traffic/understand-policies/order-of-enforcement/) records that on 2025-07-14 Gateway began evaluating network-level policies before application-level policies, verifying the network path to an origin server before accepting a connection, a change affecting accounts that apply HTTP policies (weight 0.82). The source doc's instruction to "retrieve current evaluation docs before changing rule order" is therefore not decoration; the evaluation order itself has changed mid-life of this deployment pattern.

Two selector semantics from the source doc: `dns.domains` matches a domain and subdomains while `dns.fqdn` is exact-match only; and DNS pre-resolution and post-resolution selectors do not behave like a single strict precedence list, so retrieve current evaluation docs before changing rule order (source doc). Gateway Network policies are strict L4 controls, and identity-aware L4 matching requires authenticated device context (source doc). When groups are involved, check the [Gateway identity selectors](https://developers.cloudflare.com/cloudflare-one/traffic-policies/identity-selectors/) and [SCIM provisioning](https://developers.cloudflare.com/cloudflare-one/team-and-resources/users/scim/) docs (source doc).

## TLS inspection

HTTP inspection and DLP for encrypted web traffic require TLS inspection and planned Do Not Inspect exceptions (source doc). What enabling it does, per the current docs: when TLS decryption is turned on, Gateway decrypts all HTTPS traffic, applies HTTP policies, then re-encrypts the request with a user-side certificate, and Cloudflare prevents traffic interference by decrypting, inspecting, and re-encrypting HTTPS requests in memory only in its data centers ([TLS decryption](https://developers.cloudflare.com/cloudflare-one/traffic-policies/http-policies/tls-decryption/), weight 0.94).

Certificate trust is the prerequisite: TLS inspection requires a trusted private root certificate to inspect and filter encrypted traffic; a Cloudflare root certificate is the simple path appropriate for testing or proof of concept when deployed to devices (weight 0.74, [TLS inspection learning path](https://developers.cloudflare.com/learning-paths/secure-internet-traffic/build-http-policies/tls-inspection/)). For production, the recommendation in the [enable TLS decryption](https://developers.cloudflare.com/learning-paths/replace-vpn/configure-device-agent/enable-tls-decryption/) learning path is to upload your own root certificate, since a single existing certificate streamlines IT management (weight 0.78; the same content lives in the [cloudflare-docs source file](https://github.com/cloudflare/cloudflare-docs/blob/production/src/content/docs/learning-paths/replace-vpn/configure-device-agent/enable-tls-decryption.mdx), weight 0.84). The source doc's ordering rule is hard: deploy the Cloudflare root CA to managed devices before enabling inspection, and put certificate-pinned apps on Do Not Inspect exceptions before broad TLS inspection (source doc). Self-signed internal applications also need either a Do Not Inspect policy or an untrusted certificate Pass through policy to keep users connected (weight 0.78).

## Do Not Inspect ordering

The source doc states: HTTP Do Not Inspect rules run before HTTP Allow, Block, and Isolate behavior; a later block rule will not override an earlier inspection bypass (source doc). This is the inversion that surprises operators: bypass wins over enforcement by design. Community discussion of Do Not Inspect exists ([community thread](https://community.cloudflare.com/t/do-not-inspect-setting/494526), weight 0.09) but is weak-backing; the ordering claim rests on the source doc plus the current traffic-policy docs.

## DLP

The source doc's DLP mechanics: DLP profiles are detection definitions only. They do nothing until referenced by Gateway HTTP policies or CASB scan settings. Rules with body inspection may be evaluated multiple times in a single pass (source doc). The rollout sequence the skill prescribes: start DLP with payload logging where appropriate, tune false positives, then block (source doc). The assessment prompts to collect first: sensitive data types, channels to inspect, TLS inspection readiness, DLP profiles, payload logging requirements, and false-positive tolerance, retrieving the [DLP docs](https://developers.cloudflare.com/cloudflare-one/data-loss-prevention/) before creating enforcement (source doc).

The dependency chain is the load-bearing insight: DLP over HTTPS requires TLS inspection, which requires root CA trust, which requires Do Not Inspect exceptions for pinned apps. Skipping a link silently disables enforcement. The staged-rollout guardrail applies to all of it: start broad block, allow, DLP, and TLS policies disabled and limited to a pilot with specific target users or groups unless the user approves a wider rollout (source doc).
