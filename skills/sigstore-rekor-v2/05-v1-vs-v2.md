# 05 - Rekor v1 vs Rekor v2 and the migration path

Scope: the property-by-property comparison between Rekor v1 and v2, what changed at GA, why the in-toto attestation format is unchanged, and how to migrate a pipeline forward-only.

## The comparison

The source doc (yubi-OS/yubiOS skills/sigstore-rekor-v2/SKILL.md) lays out six properties side by side:

| Property | Rekor v1 | Rekor v2 |
|---|---|---|
| Log structure | Single Merkle tree per checkpoint | Many small tile-sharded Merkle trees |
| Checkpoint | Single global checkpoint | Per-tile checkpoint signed by witness quorum |
| Compromise blast radius | Single root key, entire log | Single witness, at most one tile |
| Inclusion proof | Single Merkle path | Tile-scoped Merkle path plus tile chain |
| Endpoint discovery | Hardcoded in client | TUF SigningConfig |
| Status | Maintenance mode (v1.3.x) | GA (v2.x) |

The status row is corroborated upstream: the Rekor repository states plainly that Rekor v1 is in maintenance mode and that a new version designed to be easy to maintain and cheaper to operate is in active development, building on the Certificate Transparency ecosystem's tile work (https://github.com/sigstore/rekor, weight 0.95). The rekor-tiles repository confirms v2's identity as the tile-backed backend transition (https://github.com/sigstore/rekor-tiles, weight 0.81; https://blog.sigstore.dev/rekor-v2-alpha/, weight 0.81).

## The GA announcement and what it promised

The Sigstore blog announced Rekor v2 GA under the title "Rekor v2 GA - Cheaper to run, simpler to maintain" (https://blog.sigstore.dev/rekor-v2-ga/, weight 0.83). The operational promises in the announcement: Rekor v1 continues to run in parallel with Rekor v2, and clients using the publicly distributed SigningConfig and TrustedRoot files automatically and seamlessly transition to using Rekor v2 and verifying entries (https://blog.sigstore.dev/rekor-v2-ga/, weight 0.83).

Drift note, dated 2026-10-06: the source doc states Rekor v2 GA "as of 2026-05". Dig sources date the GA announcement earlier: a mirror of the announcement blog is dated 2025-10-10 (https://github.com/api-evangelist/sigstore/blob/main/blogs/2025-10-10-rekor-v2-ga---cheaper-to-run-simpler-to-maintain.md, weight 0.11, weak backing), and a third-party migration document states Sigstore Rekor v2 went GA on 6 October 2025 with Rekor v1 entering maintenance mode the same day under a 1-year deprecation notice (https://github.com/contrario/nous/blob/main/docs/REKOR_V2_MIGRATION.md, weight 0.07, weak backing). Both dig sources are low-weight mirrors or third-party summaries, so the discrepancy is recorded here but not resolved. The maintenance-mode status itself is agreed by all sources (https://github.com/sigstore/rekor, weight 0.95).

## The in-toto format is unchanged

The migration is log-side only. Both Rekor versions accept the same `_type: https://in-toto.io/Statement/v1` envelope with `predicateType: https://slsa.dev/provenance/v1` (source doc). Cosign's attestation creation and signing flow is built on this format independently of the log version (https://docs.sigstore.dev/cosign/verifying/attestation/, weight 0.67). Blob attestation and verification support, via `cosign attest-blob` and `cosign verify-blob-attestation`, was added in the cosign 2.0 release and carries across log generations (https://blog.sigstore.dev/cosign-2-0-released/, weight 0.67).

This is why the YAML in-toto statement format being unchanged is the single most important fact for migration planning: no attestation content needs to be rewritten to move to v2. Only the log endpoint and the inclusion-proof format differ (source doc).

## Forward-only migration

The migration discipline from the source doc:

1. Do not migrate from Rekor v1 to v2 by re-signing existing entries. The v1 entries are still verifiable on v1's log.
2. The migration is forward-only: new entries go to v2.
3. Old entries stay on v1; the verifier handles both logs transparently.

The GA announcement's parallel-run commitment is the mechanism that makes this safe: v1 keeps running and serving while clients transition through the TUF-distributed SigningConfig and TrustedRoot files (https://blog.sigstore.dev/rekor-v2-ga/, weight 0.83). Third-party adopters followed the same shape; the NVIDIA AICR contributor guide describes signing keyless attestations to Rekor v2 by default as an example of a post-GA deployment posture (https://docs.nvidia.com/aicr/contributor-guide/rekor-v-2-signing/, weight 0.16, weak backing).

## Anti-patterns at the boundary

1. Rekor v1 for new deployments. Rekor v1 is in maintenance mode; new deployments should target v2, and v1 is used only when verifying pre-existing entries (source doc).
2. Re-signing v1 entries into v2. It is unnecessary work and the verifier handles both logs (source doc).
3. Working with Fulcio. Logging certificates is Fulcio's job, with Fulcio v2 having its own certid-transparency log separate from Rekor (source doc).

## yubiOS mapping

yubiOS's SLSA L3 attestations and evidence bundles target Rekor v2 as their transparency log (source doc). The v1 reference lives in the `slsa-provenance` skill; this corpus is the dedicated v2 reference. A pipeline migrating today should: leave historical v1 entries in place, publish all new attestations to v2, and let the TUF-driven client discovery switch the verification path automatically.
