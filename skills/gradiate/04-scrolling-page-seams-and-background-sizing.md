# 04: Scrolling-Page Seams and Background Sizing

**Scope:** Preventing viewport-height tiling seams on scrolling pages with `background-repeat: no-repeat` and `background-size: 100% 100%`, and avoiding `background-attachment: fixed` unless the user asks for it.

**Ground source:** `yubi-OS/yubiOS skills/gradiate/SKILL.md`

**Dig:** 2 searXNG queries, 10 results, each clef-weighted (noul metric, true = primary source). 2 results scored >= 0.5; 8 scored < 0.5. Both strong results came from the second query (`background-attachment`); the seam query returned only weak or off-topic results.

Outline validation (clef `score` metric): **1.5454** (probabilities: padding 0.0852, marginal 0.2842, load-bearing 0.6306; confidence 0.2285).

## 1. The ground-source rule

Workflow step 5: "Apply the CSS to the page background. On a scrolling page add background-repeat: no-repeat and background-size: 100% 100%. Without them the gradient tiles and leaves a seam at each viewport height."

Guideline 6: "Don't add background-attachment: fixed unless asked."

Note that the generator's example CSS (doc 06) emits only `background-color` and `background-image`. The 2 sizing declarations are an application-time addition for scrolling pages; they are not part of the designer's `buildCss` output as shown in the ground source.

## 2. Why the seam appears

The ground source states the symptom (a seam at each viewport height) and the fix; it does not explain the mechanism, and the dig did not return an authoritative source that does. What the dig did return:

- A forum thread titled "Gradient background repeats despite having 'no-repeat' when I scroll" documents that practitioners hit this exact symptom (https://stackoverflow.com/questions/66962541/gradient-background-repeats-despite-having-no-repeat-when-i-scroll, clef weight: 0.3420, weak backing, clef weight < 0.5). The snippet carries only the title and dates, not the diagnosis.
- MDN on `repeating-linear-gradient()` describes a different function that "repeats the color stops infinitely in all directions so as to cover its entire container" (https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/gradient/repeating-linear-gradient, clef weight: 0.2766, weak backing, clef weight < 0.5). This is adjacent, not the cause: the skill uses plain `linear-gradient()`, and its seam comes from tiling the whole image, not from repeating stops. W3Schools covers the same adjacent function (https://www.w3schools.com/CSSref/func_repeating-linear-gradient.php, clef weight: 0.1588, weak backing, clef weight < 0.5).

Because the mechanism is not source-backed in this dig, this doc does not assert one. The operational rule from the ground source stands on its own: tiling is the failure, and the 2 declarations below stop it.

## 3. The 2-line fix

```css
.gradient-bg {
  /* generated by gradiate */
  background-color: #0B1026;
  background-image:
    linear-gradient(90deg, #DB46F566 0%, #DB46F500 50%, #5FD9F266 100%),
    linear-gradient(180deg, #FFC85766 0%, #FFC85700 50%, #DB46F566 100%);
  /* added for scrolling pages, per SKILL.md step 5 */
  background-repeat: no-repeat;
  background-size: 100% 100%;
}
```

What each line does, stated at the level of the declaration names:

- `background-repeat: no-repeat` stops the image from tiling, so there is no second copy to meet the first at a seam.
- `background-size: 100% 100%` stretches the image to cover the full element on both axes, so removing the repeat does not leave an uncovered strip below the first tile.

The 2 go together; one without the other either still tiles or leaves bare `background-color` showing. Keep the semicolons: doc 05 covers how a single missing semicolon drops the declaration silently.

## 4. Why not `background-attachment: fixed`

MDN defines the property: `background-attachment` "sets whether a background image's position is fixed within the viewport, or scrolls with its containing block" (https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/background-attachment, clef weight: 0.7980). `fixed` can look like an alternate seam fix, since a viewport-pinned image never scrolls into a second tile. The skill rejects it as a default for reasons the dig supports:

- CSS-Tricks: "background-attachment: fixed simply stops working when a repaint is needed, like when a mobile browser's address bar goes away on scroll," with the browser then adjusting "the background according to the largest possible viewport" (https://css-tricks.com/the-fixed-background-attachment-hack/, clef weight: 0.5279).
- Forum reports of `fixed` failing on mobile, especially iOS devices (https://stackoverflow.com/questions/26372127/background-fixed-no-repeat-not-working-on-mobile, clef weight: 0.0693, weak backing, clef weight < 0.5; https://stackoverflow.com/questions/65517655/background-attachment-fixed-not-working-in-mobile-devices, clef weight: 0.0882, weak backing, clef weight < 0.5).

There is also a design reason inside the skill itself: the center-fade frame (doc 02) is meant to frame the page content. Pinning it to the viewport changes it into a window overlay, which is a different visual than the one the user asked for. So `fixed` is reserved for explicit requests (Guideline 6).

## 5. Checklist

1. Generated CSS applied unchanged (Guideline 2).
2. On scrolling pages, `background-repeat: no-repeat` and `background-size: 100% 100%` added.
3. No `background-attachment: fixed` unless requested.
4. Scroll to the bottom of a tall page in a real browser and look for a seam at each viewport height; then run the computed-style check in doc 05.
