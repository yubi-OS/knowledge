# 04 - Audit artifacts: PSS admission logs and OPA decision logs

Scope: the two evidence surfaces the skill contributes to the P6 audit primitive: Pod Security Admission logs on the Kubernetes leg and OPA decision logs on the Rego leg, plus the audit machinery that turns policy into collectible records.

Per the source doc (`yubi-OS/yubiOS skills/least-privilege-pod-security-standards/SKILL.md`), the skill maps to 10-primitive axes with P6 audit/evidence carried by PSS admission logs and OPA decision logs. A least-privilege policy that denies nothing and logs nothing is invisible; these two log surfaces are what make the skill's enforcement claims verifiable after the fact.

## Kubernetes audit logging

Kubernetes auditing provides a security-relevant, chronological set of records documenting the sequence of actions in a cluster, covering activities generated by users, by applications using the Kubernetes API, and by the control plane itself, and it lets cluster administrators answer what happened, when it happened, and who initiated it (https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/, jev weight 0.76). Pod Security Admission enforcement decisions flow through the API server, so admission rejections and audit-mode violations surface in this record stream.

The audit and warn modes are the collection mechanism on the PSS side: they let an operator collect important security insights about pods without breaking existing workloads, and the upstream best-practice guidance is to enable them for all namespaces at the target level and version (https://kubernetes.io/docs/setup/best-practices/enforcing-pod-security-standards/, jev weight 0.85). In the yubiOS reading, an audit-mode namespace is an instrument running in evidence mode: every violation it records is an admission decision that would have been a denial under enforce.

As a platform reference point, OpenShift ships pod security admission with the privileged profile enforced globally and the restricted profile used for audit (weak backing, weight 0.49, https://docs.openshift.com/container-platform/4.11/authentication/understanding-and-managing-pod-security-admission.html). The pattern of enforce at one level and audit at the next is a drift-reduction technique the yubiOS skill inherits.

## OPA decision logs

On the Rego leg, OPA can periodically report decision logs to remote HTTP servers, through custom plugins, or to console output, in any combination (https://www.openpolicyagent.org/docs/management-decision-logs, jev weight 0.73). Each decision-log event contains the policy that was queried, the input to the query, bundle metadata, and other information that enables auditing and offline debugging of policy decisions (https://www.openpolicyagent.org/docs/management-decision-logs, jev weight 0.73).

That event shape is what makes the Rego leg auditable in the P6 sense: the record is not just a denial line but the full policy, input, and bundle state, so a reviewer can replay the decision. This matters for the yubiOS evidence chain because the same decision records can be packaged into evidence bundles alongside other telemetry.

## Gatekeeper audit: the batch complement

Gatekeeper adds a second, batch-shaped evidence surface. Its audit component performs periodic evaluations of existing resources against constraints, detecting pre-existing misconfigurations that were created before a constraint existed or that slipped past admission (https://open-policy-agent.github.io/gatekeeper/website/docs/audit/, jev weight 0.84). Audit results can be gathered at three levels of detail, including Prometheus metrics such as `gatekeeper_audit_last_run_time`, which reports the start time of the last audit run and the number of violations (https://open-policy-agent.github.io/gatekeeper/website/docs/audit/, jev weight 0.84).

For admission-time records specifically, the Gatekeeper project's own issue history records that piping logs into a log service such as ELK, Splunk, Stackdriver, or Loggly allows querying audit events, and that admission-time logs require the `--log-denies` flag, which writes admission logs to stdout, with the caveat that enabling admission logs can greatly increase log volume (weak backing, weight 0.45, https://github.com/open-policy-agent/gatekeeper/issues/897).

## The P6 pairing in practice

The two legs produce two complementary artifacts. PSS admission and Kubernetes audit logging give a chronological API-server record of what the admission controller decided and why a pod was rejected or warned. OPA decision logs give a policy-complete record of what rules fired against what input. A yubiOS least-privilege claim is strongest when both are collected: the first shows the cluster-level outcome, the second shows the rule-level reasoning. The source doc places both under P6, which is why the skill's description names them explicitly as audit artifacts rather than leaving them as an implementation detail.
