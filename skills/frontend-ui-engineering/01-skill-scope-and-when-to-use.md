# 01 Skill Scope and When to Use

**Internal-record subtopic, no dig.** This doc is grounded in the source doc alone: `yubi-OS/yubiOS skills/frontend-ui-engineering/SKILL.md` (the primary source of record for the whole corpus). Every claim below cites that path; there are no external sources to weight.

## Scope line

The frontend-ui-engineering skill exists to build production-quality user interfaces that are accessible, performant, and visually polished (source doc). Its stated goal is sharper than that: UI should look like it was built by a design-aware engineer at a top company, not like it was generated by an AI. That means real design system adherence, proper accessibility, thoughtful interaction patterns, and no generic "AI aesthetic" (source doc).

The skill is a discipline document, not a framework tutorial. Its examples are React-flavored (tsx snippets, Tailwind class names, React Query hooks), but the rules it encodes are stack-agnostic: colocate component files, compose instead of configure, keep state as local as possible, never skip loading, error, and empty states, and verify with a fixed checklist before calling UI done (source doc).

## When to use

The source doc names 5 trigger conditions, and each one is a concrete engineering situation rather than a vague "make it look nice":

1. **Building new UI components or pages.** Fresh components are where the AI aesthetic creeps in first: default palettes, oversized rounding, placeholder copy. The skill demands design system adherence from the first line (source doc).
2. **Modifying existing user-facing interfaces.** Changes inherit the existing design system. The skill forbids introducing off-scale values or raw hex colors into a codebase that already has tokens (source doc).
3. **Implementing responsive layouts.** Responsive behavior is designed mobile first and expanded upward, never retrofitted (source doc; see doc 06).
4. **Adding interactivity or state management.** New state gets placed on the skill's state ladder at the lowest rung that works (source doc; see doc 03).
5. **Fixing visual or UX issues.** A fix is not done when it looks right on one screen; it is done when the verification checklist passes (source doc; see doc 08).

## What "production quality" means here

The skill decomposes the goal into 3 verifiable properties:

- **Accessible.** Every component must meet WCAG 2.1 AA: keyboard operable, labeled, focus managed, with meaningful empty and error states (source doc; expanded in doc 05). The skill's common-rationalizations table answers the "accessibility is a nice-to-have" excuse directly: it is a legal requirement in many jurisdictions and an engineering quality standard (source doc).
- **Performant.** The skill treats shadow-heavy design as a rendering cost on low-end devices, prefers skeletons over spinners for content, and uses optimistic updates for perceived speed (source doc; expanded in doc 07).
- **Visually polished.** Polished means consistent with the project's spacing scale, type hierarchy, and semantic color tokens, with 4.5:1 contrast for normal text and 3:1 for large text (source doc; expanded in doc 04).

## What the skill is not

The skill's scope is bounded by its own frontmatter description: building or modifying user-facing interfaces, components, layouts, state, and UX fixes (source doc). Anything beyond that boundary is a different skill's job. The source doc's own closing guideline says every use stays inside the frontmatter description's scope; it does not cover, for example, choosing a CSS framework, building a design token pipeline, or running accessibility audits at the CI level. Those belong to adjacent skills.

## The anti-goal: the AI aesthetic

The most distinctive part of the skill's scope statement is what it is against. The source doc devotes a full table to AI-generated UI's recognizable defaults: purple/indigo everything, excessive gradients, maximum rounding, generic hero sections, lorem ipsum copy, oversized padding, stock card grids, and shadow-heavy depth (source doc). The reason is not taste for its own sake: models default to visually "safe" palettes that make every app look identical, and placeholder copy hides layout problems that real content reveals (source doc). The full table and its production-quality replacements are expanded in doc 04.

## Component boundaries the skill sets

Two hard numbers appear in the scope material and are enforced as red flags later in the doc: components with more than 200 lines should be split, and props should not be drilled more than 3 levels deep (source doc). The skill treats these as structural triggers: when a component crosses the line, the response is a split or a restructure, not a bigger file (source doc; see docs 02 and 03).

## Summary

The skill's scope is: any UI work, from a single component to a full page, where the output must be production quality. The 5 triggers cover the whole UI lifecycle. The 3 quality properties (accessible, performant, visually polished) are each backed by concrete sections of the source doc, and the corpus's remaining docs expand them one by one.
